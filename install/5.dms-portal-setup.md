# 5. DMS Portal 설치·구성

이 문서는 운영자/사용자용 웹 UI인 **DMS Portal**(`src/portal/`)을 Kubernetes에 설치·구성하는 절차를 다룬다.
Portal은 **DMS의 `/api/v1/` HTTP API만 소비하는 별도 애플리케이션**이다. DMS backend(`src/dms/`)나 DB를
직접 건드리지 않으므로, `1.install-dms-on-pvs.md`로 DMS control plane이 이미 동작 중인 상태를 전제로 한다.

명령은 DMS repository root에서 실행한다고 가정한다.

```bash
cd <dms-repo-root>
```

## 0. Portal 개요

- **구조**: FastAPI BFF(`src/portal/backend/`) + Vite/React SPA(`src/portal/frontend/`). 하나의 컨테이너
  이미지가 빌드된 SPA 정적 자산과 BFF API(`/api/...`)를 같은 포트(`8090`)로 서빙한다.
- **통신 경계**: 브라우저는 **BFF만** 호출하고, BFF가 DMS `/api/v1/...`를 호출한다. 브라우저는 DMS
  자격증명(토큰/인증서)을 절대 갖지 않는다. DMS와 통신하는 코드는 `backend/dms_client.py` 한 곳뿐이다.
- **역할 모델**: 로그인 방식 = 역할(role).
  - `operator` — **ID/비밀번호** 로그인(운영자 전용, 다중 계정). 운영자 콘솔 제공.
  - `user` — **회사 AD 계정** 로그인(현재 더미 stand-in). 사용자 인터페이스 제공.
- **현재 기능**:
  - **스토리지 인벤토리**(`storage_mapping` 조회·등록·수정·sanity 재검사·삭제). DMS의 storage-mapping API를
    그대로 미러링한다(2.dms-rm-api-fs / 3.dms-rm-api-k8s 참고). 목록·상세의 **readiness 표시는 backend 종류에
    따라 축(axis)이 다르다** — §0.2 참고.
  - **데이터 백업**(DM `sync` 미러 백업 — 배치 미리보기→승인→실행). 이 기능은 **포탈 DB**(§0.3)를 요구하며,
    별도 운영 문서 `6.dms-portal-data-backup.md`에서 다룬다.
  - **종합 대시보드**(읽기 전용 운영 모니터링 — 스케줄러·큐/작업·worker node·요청·조치 필요). DMS
    `operations/*` 읽기 API를 소비하며(신규 엔드포인트 1개 추가), 별도 운영 문서 `7.dms-portal-dashboard.md`에서 다룬다.
- **배포 위치**: DMS와 **별도 namespace `dms-portal`**에 둔다(엔드유저를 마주하는 다른 신뢰 등급이므로
  control plane과 RBAC/NetworkPolicy/lifecycle을 분리). Portal Pod는 어떤 클러스터 변경 권한도 갖지 않으며,
  kubeconfig/SSH secret도 mount하지 않는다.

수정·참고할 파일:

- `src/portal/deploy/Dockerfile` — multi-stage(node SPA build → python runtime) 이미지
- `src/portal/deploy/kubernetes/portal.yaml` — Namespace/Secret/Deployment/Service(NodePort)

## 0.1 설치 전에 정할 값

| 항목 | 예시 | 어디에 사용 |
| --- | --- | --- |
| Portal namespace | `dms-portal` | 모든 portal manifest namespace |
| Container registry | `registry.example.internal` | portal image push/pull |
| Portal image tag | `registry.example.internal/dms-portal:2026-06-23-abcdef0` | Deployment image |
| DMS API base (BFF→DMS) | `http://dms-api.dms.svc.cluster.local` | `PORTAL_DMS_API_URL` |
| DMS shared token | `DMS_AUTH_SHARED_TOKEN`과 동일 값 | `PORTAL_DMS_TOKEN` |
| DMS audit actor 기본값 | `operator` | `PORTAL_DMS_ACTOR` |
| 세션 서명 시크릿 | `openssl rand -hex 32` 출력 | `PORTAL_SESSION_SECRET` |
| 운영자 계정 | `admin:<strong-pw>,ops2:<strong-pw>` | `PORTAL_OPERATOR_USERS` |
| 포탈 DB(선택) | DMS Postgres 재사용 시 `DMS_DATABASE_URL`과 동일 값 | `PORTAL_DB_URL` (§0.3, 데이터 백업·DB 로그인) |
| 외부 노출 방식 | NodePort `30090` 또는 ingress+TLS | Service / Ingress |

> **인증 profile 주의.** 현재 BFF는 DMS에 **shared bearer token + `x-dms-actor` 헤더** profile로 접속한다
> (`PORTAL_DMS_TOKEN` + `PORTAL_DMS_ACTOR`). 이는 `DMS_AUTH_SHARED_TOKEN`을 사용하는 DMS와 맞는다. DMS가
> mTLS-only profile(`DMS_REQUIRE_MTLS_HEADER=true`, ingress `auth-tls-verify-client: on`)로만 노출돼 있으면
> 현재 BFF는 client certificate을 제시하지 않으므로 그 ingress를 통과할 수 없다. 이 경우는 §9를 참고한다.

## 0.2 스토리지 인벤토리의 readiness 표시 (fs vs CSI)

스토리지 인벤토리 목록의 `readiness` 열과 매핑 상세의 `readiness` 행은 **매핑 backend 종류에 따라 서로 다른
축으로 표시된다**. 이 구분은 DMS sanity 모델을 그대로 반영한 것으로, 어느 쪽도 별도 설정이 필요하지 않다.

- **filesystem 매핑**(`backend_type` = `cephfs` / `gpfs` / `wekafs`) — 노드에서 RM/DM agent가 도는
  유형이므로 **RM · DM · INV** 세 점(dot)으로 표시한다. 각각 storage-mapping sanity의
  `readiness.resource_management` / `data_management` / `inventory` 값(Ready/Degraded/Unknown/Failed)을
  색으로 나타내고, 점에 마우스를 올리면 `RM: <상태>`처럼 해당 축 상태가 툴팁으로 뜬다. 상세 화면에는
  추가로 **Agent 관측**(fresh/stale 리포트 수, rm/dm readiness 및 후보 노드 수) 블록이 보인다.

- **CSI(k8s namespace-quota) 매핑**(`backend_type`이 위 fs 집합이 아닌 값 — 예: `ceph-csi` / `gpfs-csi` /
  `weka-csi` 등 free-form 라벨) — agent가 없는 유형이라 RM/DM/INV 대신 단일 **QUOTA** 점으로 표시한다.
  이 QUOTA 축은 DMS가 새로 노출하는 **ResourceQuota mutation transport 검증** 결과
  (`readiness.kubernetes_mutation`, Ready/Failed/Unknown)를 색으로 보여준다. 즉 "이 매핑의 per-mapping
  `kubectl` / `ssh-kubectl` 경로가 대상 클러스터에 도달해 ResourceQuota를 적용할 권한이 있는가"를 검사한
  결과다. QUOTA 점의 툴팁에는 다음이 한 줄로 표시된다.

  ```text
  QUOTA: <상태> · <mode>[ @ <control_host>] · can-i: <yes/no/unknown>
  ```

  - `<mode>` — 적용 경로(`kubectl` 직접 도달 또는 `ssh-kubectl` SSH 후 kubectl). 매핑의 per-mapping
    `mutation_mode`(없으면 전역 `DMS_KUBERNETES_MUTATION_MODE`)에서 온다.
  - `@ <control_host>` — `ssh-kubectl`일 때 RM worker가 SSH하는 대상 클러스터 control 호스트(설정된 경우만).
  - `can-i: <…>` — `kubectl auth can-i`로 본 ResourceQuota 변경 권한(create/patch/delete 모두 허용이면
    `yes`, 도달했으나 거부면 `no`, 미확인이면 `unknown`).

  CSI 매핑 상세 화면에는 QUOTA 축 외에 **Quota mutation transport** 블록이 따로 나와
  `mode` / `control_host` / `reachable` / `can_mutate` / `can-i(create/patch/delete)` / `detail`을
  자세히 보여준다(DMS sanity 응답의 `sanity_result.mutation_observed`).

> 이 transport 검증이 실패하면 해당 매핑 sanity가 **Failed**가 되고, DMS planner가 그 매핑에 대한
> namespace-quota 요청을 자동 차단한다(`_reject_unsafe_storage_mapping`). 즉 QUOTA 점이 빨간색(Failed)이면
> 그 스토리지로의 quota 변경 요청은 받아들여지지 않는다.

## 0.3 포탈 DB (선택 — 데이터 백업 / DB 로그인)

포탈은 기본적으로 **상태가 없는** API 클라이언트지만, **데이터 백업** 기능과 **DB 기반 운영자 로그인**을 쓰려면
포탈 전용 Postgres(`PORTAL_DB_URL`)가 필요하다.

- **미설정(`PORTAL_DB_URL` 없음)** — 스토리지 인벤토리 등 DMS-연동 기능은 그대로 동작한다. 로그인은
  `PORTAL_OPERATOR_USERS`(env 저장소)로 처리되고, **데이터 백업 route는 `503`** 으로 비활성된다.
- **설정** — 포탈이 기동 시 `PORTAL_DB_SCHEMA`(기본 `portal`) 스키마에 자신의 테이블(operator_users /
  backup_batches / backup_requests)을 자동 생성한다. 운영자 로그인은 DB가 source of truth가 되며(최초 1회
  `PORTAL_OPERATOR_USERS`로 시드), 데이터 백업 탭이 활성화된다.

DMS Postgres를 **전용 스키마로 재사용**할 수 있다(테스트베드는 `dms` DB의 `portal` 스키마). 스키마 준비·연결
문자열·env·운영자 사용법은 전부 **`6.dms-portal-data-backup.md`** 에서 다룬다. 아래 §3~§4는 배포 시 필요한
`PORTAL_DB_URL` 주입만 짚는다.

## 1. 사전 조건

- DMS control plane이 동작 중이고 Portal Pod에서 DMS API에 도달 가능해야 한다. in-cluster service
  (`http://dms-api.dms.svc.cluster.local`) 또는 NodePort(`http://<node-ip>:30080`) 중 도달 가능한 경로를
  쓴다. NetworkPolicy로 `dms-api`가 특정 namespace만 허용한다면 `dms-portal`을 허용 목록에 포함해야 한다.
- DMS shared token(`DMS_AUTH_SHARED_TOKEN`)을 알고 있어야 한다(BFF가 DMS 호출 시 사용).
- Portal node에서 image pull이 가능한 registry가 있어야 한다.
- 관리 workstation 도구: `kubectl`, `docker`, `openssl`, `curl`, `jq`.

도달성 사전 점검(예: in-cluster service):

```bash
kubectl --context dms -n dms get svc dms-api
# Portal namespace에서 임시 Pod로 확인 (DMS 이미지에 curl이 없으면 healthz는 200을 반환)
kubectl --context dms -n dms run dms-portal-netcheck --rm -i --restart=Never \
  --image=registry.example.internal/dms-portal:CHANGE_ME \
  --command -- python -c "import httpx;print(httpx.get('http://dms-api.dms.svc.cluster.local/healthz',timeout=5).status_code)"
```

## 2. Portal image build 및 push

빌드 컨텍스트는 **repository root**다. Dockerfile이 node로 SPA를 빌드한 뒤 python runtime에 BFF와 정적
자산을 함께 담는다.

```bash
export PORTAL_IMAGE="registry.example.internal/dms-portal:$(git rev-parse --short HEAD)"
docker build -f src/portal/deploy/Dockerfile -t "$PORTAL_IMAGE" .
docker push "$PORTAL_IMAGE"
```

이미지가 정상 기동하는지 빠르게 확인할 수 있다(SPA 미빌드가 아니면 `/healthz`가 200).

```bash
docker run --rm -e PORTAL_ALLOW_INSECURE_DEFAULTS=1 -p 18090:8090 "$PORTAL_IMAGE" &
sleep 3 && curl -fsS http://127.0.0.1:18090/healthz && echo
kill %1
```

> `PORTAL_ALLOW_INSECURE_DEFAULTS=1`은 로컬 점검용이다. BFF는 dev 기본 세션 시크릿으로는 기동을 거부하므로,
> 이 플래그 없이 빠른 점검을 하려면 `-e PORTAL_SESSION_SECRET=<임의값>`을 준다(§4.2, §7).

운영에서는 원본을 직접 수정하기보다 복사본을 만든다.

```bash
cp src/portal/deploy/kubernetes/portal.yaml /tmp/dms-portal.yaml
```

### 3.1 image tag 교체

```bash
sed -i "s#pkg-01:5000/dms-portal:v[0-9]*#$PORTAL_IMAGE#g" /tmp/dms-portal.yaml
```

### 3.2 환경변수(Deployment env) 확인

Deployment의 `env`에서 DMS 연동과 세션 보안 값을 환경에 맞춘다. 전체 변수는 `src/portal/backend/config.py`가
정의하며, 주요 항목은 다음과 같다.

| 변수 | 기본값 | 설명 |
| --- | --- | --- |
| `PORTAL_DMS_API_URL` | (없음) | DMS API base. 미설정이면 DMS 연동 route가 503. |
| `PORTAL_DMS_TOKEN` | (없음) | DMS shared bearer token(Secret으로 주입). |
| `PORTAL_DMS_ACTOR` | `operator` | DMS audit 기본 actor. BFF가 요청마다 로그인한 운영자 username으로 override. |
| `PORTAL_DMS_TIMEOUT_SECONDS` | `15` | DMS HTTP 호출 timeout. |
| `PORTAL_DMS_VERIFY_TLS` | `true` | DMS가 https일 때 TLS 검증 여부. |
| `PORTAL_SESSION_SECRET` | (dev 기본값) | 세션 쿠키 서명키(Secret으로 주입). dev 기본값이면 기동 거부. |
| `PORTAL_SESSION_HTTPS_ONLY` | `true` | 세션 쿠키 Secure 플래그. **평문 HTTP 노출이면 `false`로**. |
| `PORTAL_SESSION_MAX_AGE_SECONDS` | `28800` | 세션 수명(초). |
| `PORTAL_OPERATOR_USERS` | `admin:admin1234` | 운영자 ID/PW 저장소(Secret으로 주입). `user:pw,user2:pw2`. DB 설정 시 최초 1회 시드. |
| `PORTAL_ALLOW_INSECURE_DEFAULTS` | `false` | dev 기본 세션 시크릿 기동 허용(로컬 dev 전용). |
| `PORTAL_DB_URL` | (없음) | 포탈 DB Postgres URL(Secret으로 주입). 미설정이면 데이터 백업 route 503 + env 로그인 폴백. §0.3. |
| `PORTAL_DB_SCHEMA` | `portal` | 포탈 테이블 스키마(연결 `search_path`). |

> 데이터 백업 전용 변수(`PORTAL_BACKUP_*`)는 `6.dms-portal-data-backup.md` §3에서 다룬다(기본값으로 충분).

템플릿 기본값:

```yaml
env:
  # 평문 HTTP NodePort로 노출하면 세션 쿠키가 Secure-only면 안 된다. TLS 프런트엔드 도입 시 제거(기본 true).
  - name: PORTAL_SESSION_HTTPS_ONLY
    value: "false"
  # in-cluster DMS API (node-IP 비의존)
  - name: PORTAL_DMS_API_URL
    value: "http://dms-api.dms.svc.cluster.local"
  - name: PORTAL_DMS_ACTOR
    value: "operator"
```

### 3.3 Secret placeholder

`Secret/portal-secrets`의 값은 **전부 placeholder**다. 실제 자격증명을 git working tree/commit에 남기지
않는다. 실값은 §4.2에서 라이브 Secret에 주입한다.

```yaml
stringData:
  PORTAL_SESSION_SECRET: "REPLACE_WITH_SESSION_SECRET"
  PORTAL_OPERATOR_USERS: "REPLACE_WITH_OPERATOR_CREDS"
  PORTAL_DMS_TOKEN: "REPLACE_WITH_DMS_TOKEN"
  PORTAL_DB_URL: "REPLACE_WITH_DB_URL"   # 데이터 백업/DB 로그인용. 안 쓰면 비워 둔다(§0.3).
```

## 4. 배포

### 4.1 apply

```bash
kubectl --context dms apply -f /tmp/dms-portal.yaml
kubectl --context dms -n dms-portal get deploy,svc,secret
```

이 시점의 Pod는 placeholder 시크릿을 들고 있으므로(세션 시크릿이 dev 기본값은 아니지만 placeholder 문자열),
다음 단계에서 실값을 주입한 뒤 재기동한다.

### 4.2 Secret 실값 주입 (out-of-band)

세 시크릿을 라이브 Secret에 한 번에 patch한다. 세션 시크릿은 새로 랜덤 생성한다.

```bash
SESSION_SECRET="$(openssl rand -hex 32)"
DMS_TOKEN="REPLACE_WITH_DMS_AUTH_SHARED_TOKEN"   # DMS의 DMS_AUTH_SHARED_TOKEN과 동일 값

kubectl --context dms -n dms-portal patch secret portal-secrets --type merge -p "$(cat <<JSON
{"stringData":{
  "PORTAL_SESSION_SECRET":"${SESSION_SECRET}",
  "PORTAL_OPERATOR_USERS":"admin:REPLACE_WITH_STRONG_OPERATOR_PW",
  "PORTAL_DMS_TOKEN":"${DMS_TOKEN}"
}}
JSON
)"
```

데이터 백업/DB 로그인을 쓰면 `PORTAL_DB_URL`도 함께 주입한다(테스트베드는 DMS DB 재사용 — `6.dms-portal-data-backup.md` §2~§3 참고).

```bash
DBURL="$(kubectl --context dms -n dms get secret dms-secrets -o jsonpath='{.data.DMS_DATABASE_URL}' | base64 -d)"
kubectl --context dms -n dms-portal patch secret portal-secrets --type merge \
  -p "{\"stringData\":{\"PORTAL_DB_URL\":\"${DBURL}\"}}"
```

> **재패치 주의.** `kubectl apply -f portal.yaml`을 다시 실행하면 이 값들이 다시 placeholder로 덮인다.
> manifest를 apply할 때마다 위 patch(`PORTAL_DB_URL` 포함)를 다시 수행하고 §4.3으로 재기동한다.

### 4.3 rollout

Secret 변경은 자동 재기동을 트리거하지 않으므로 명시적으로 재기동한다.

```bash
kubectl --context dms -n dms-portal rollout restart deploy/dms-portal
kubectl --context dms -n dms-portal rollout status deploy/dms-portal --timeout=120s
```

## 5. 외부 노출 / 접근

### 5.1 NodePort (간단/테스트베드)

템플릿 Service는 NodePort `30090`이다(기존 DMS API NodePort `30080`과 충돌하지 않는다). 클러스터 노드에
직접 도달 가능한 네트워크에서는 브라우저로 바로 접근한다.

```bash
kubectl --context dms -n dms-portal get svc dms-portal
# http://<node-ip>:30090
```

### 5.2 원격 노드에서 접근 (port-forward / SSH 터널)

클러스터 노드망에 직접 닿지 못하는 노트북 등에서 볼 때는, 클러스터에 도달 가능한 호스트에서 port-forward를
모든 인터페이스에 바인드한다.

```bash
# 클러스터에 도달 가능한 호스트에서 (tmux 등으로 상주 권장)
kubectl --context dms -n dms-portal port-forward --address 0.0.0.0 svc/dms-portal 30090:80
# 그 호스트의 IP로 접근: http://<host-ip>:30090
```

또는 SSH 로컬 포워딩:

```bash
# 노트북에서
ssh -L 30090:<node-ip>:30090 <user>@<reachable-host>
# http://localhost:30090
```

> port-forward는 대상 pod에 고정되므로, rollout으로 pod가 교체되면 끊긴다. 끊기면 명령을 다시 실행한다.

### 5.3 (운영) Ingress + TLS

운영에서는 NodePort 대신 ingress + 서버 TLS로 노출하고, 사용자 인증(AD/OIDC)을 BFF에 붙인다. TLS로
서빙하면 `PORTAL_SESSION_HTTPS_ONLY`를 `true`(기본값)로 두어 세션 쿠키를 Secure-only로 만든다. ingress
manifest는 환경에 맞춰 별도로 작성한다(host, TLS secret, Service `dms-portal:80` 백엔드).

## 6. 설치 검증

```bash
BASE="http://<node-ip>:30090"   # 또는 port-forward/터널 주소
JAR="$(mktemp)"

# 1) health (dms_configured=true 여야 함)
curl -fsS "$BASE/healthz"; echo

# 2) 운영자 로그인 (PORTAL_OPERATOR_USERS의 계정)
curl -fsS -c "$JAR" -X POST "$BASE/api/auth/login" \
  -H 'content-type: application/json' \
  -d '{"username":"admin","password":"REPLACE_WITH_STRONG_OPERATOR_PW"}'; echo

# 3) storage mapping 목록 (DMS 연동 + 토큰 동작 확인)
curl -fsS -b "$JAR" "$BASE/api/operator/storage-mappings" | jq 'length'

# 4) 역할 게이트: AD(user) 세션은 operator API에서 403
JAR2="$(mktemp)"
curl -fsS -c "$JAR2" -X POST "$BASE/api/auth/login/ad" >/dev/null
curl -s -o /dev/null -w "user->operator API: %{http_code}\n" -b "$JAR2" "$BASE/api/operator/storage-mappings"
```

기대값:

- `/healthz` → `{"status":"ok","dms_configured":true}` (포탈 DB를 쓰면 `"db_configured":true`도 포함)
- 운영자 로그인 → `{"user":{...,"role":"operator"}}`
- 목록 → DMS에 등록된 storage mapping 개수
- AD 사용자 → operator API `403`

> 데이터 백업까지 쓰면 `db_configured:true`를 확인하고, 데이터 백업 탭의 동작 검증은
> `6.dms-portal-data-backup.md` §3(기동 확인)·§6(worked example)을 따른다.

## 7. 보안 주의사항

- **시크릿을 commit하지 않는다.** manifest의 `PORTAL_SESSION_SECRET`/`PORTAL_OPERATOR_USERS`/`PORTAL_DMS_TOKEN`은
  placeholder로 두고, 실값은 라이브 Secret에 patch로만 주입한다(§4.2).
- **세션 시크릿은 강한 랜덤값**(`openssl rand -hex 32`)을 쓴다. 커밋된/알려진 서명키는 운영자 세션 위조
  벡터다. BFF는 dev 기본 세션 시크릿으로는 기동을 거부한다(`PORTAL_ALLOW_INSECURE_DEFAULTS=1`로만 우회).
- **평문 HTTP 노출 시** `PORTAL_SESSION_HTTPS_ONLY=false`가 필요하지만, 이는 세션 쿠키가 평문으로 오가
  스니핑/재전송 위험이 있다. 운영에서는 TLS로 서빙하고 `true`(기본값)로 되돌린다.
- **운영자 비밀번호**는 강한 값으로 설정/회전한다(`admin/admin1234`는 데모용이다).
- Portal Pod에 DMS 토큰 외의 control-plane 자격증명(kubeconfig/SSH key 등)을 주지 않는다. Portal은 순수
  API 클라이언트이며 모든 변경은 DMS API를 통해서만 일어난다.

## 8. 자주 발생하는 문제

### `/healthz`의 `dms_configured`가 false

`PORTAL_DMS_API_URL`이 비어 있다. Deployment env를 확인한다(§3.2).

### DMS 연동 route가 `503 dms_not_configured` / `502 dms_unreachable`

- `503`: `PORTAL_DMS_API_URL` 미설정.
- `502`: Portal Pod에서 DMS API에 도달 불가. service DNS/NodePort 도달성과 NetworkPolicy를 확인한다(§1).

### DMS 호출이 `401`

`PORTAL_DMS_TOKEN`이 DMS의 `DMS_AUTH_SHARED_TOKEN`과 다르다. §4.2로 재주입 후 재기동한다. (DMS가 mTLS-only
profile이면 §9를 본다.)

### 운영자 로그인 `401`

`PORTAL_OPERATOR_USERS`에 해당 계정이 없거나 비밀번호가 다르다. 라이브 Secret 값을 확인한다.

### Pod가 `CrashLoopBackOff`로 기동 실패

로그에 `PORTAL_SESSION_SECRET is unset/default`가 보이면, 세션 시크릿이 dev 기본값(또는 미주입)이다.
§4.2로 실값을 주입하고 재기동한다.

```bash
kubectl --context dms -n dms-portal logs deploy/dms-portal --tail=50
```

### apply 후 갑자기 DMS 호출 `401` / 로그인 불가

`kubectl apply`가 Secret을 placeholder로 덮었다. §4.2 재패치 + §4.3 재기동.

### 데이터 백업 탭이 `503` / `/healthz`의 `db_configured`가 false

`PORTAL_DB_URL`이 비어 있다(또는 placeholder). §4.2로 실값을 주입하고 재기동한다. DB 연결·스키마·백업 관련
트러블슈팅은 `6.dms-portal-data-backup.md` §7을 본다.

## 9. 운영(production) 배포 고려사항 — DMS mTLS profile

현재 BFF는 DMS에 **shared bearer token + `x-dms-actor`** profile로만 접속한다(`backend/dms_client.py`).
DMS가 운영 mTLS profile(`DMS_REQUIRE_MTLS_HEADER=true` + ingress `auth-tls-verify-client: on`)로만 노출돼
있으면 다음 중 하나가 필요하며, 현재 portal 코드만으로는 충족되지 않는다(향후 공동구현 항목).

- **(a) BFF에 client certificate 지원 추가** — BFF가 portal 전용 client cert을 제시해 DMS mTLS ingress를
  통과하고, 로그인한 운영자 신원을 actor로 전달. DMS의 actor/audit 계약을 그대로 사용.
- **(b) in-cluster 경로 + 신뢰 경계** — BFF가 DMS Service(`dms-api.dms.svc`)에 직접 접속하고, DMS의
  `DMS_REQUIRE_MTLS_VERIFIED_HEADER` 처리와 NetworkPolicy 신뢰 경계로 보호. 이때 사용자별 actor 전달은
  DMS 측 변경이 필요할 수 있다.

이 중 무엇을 택할지는 `CLAUDE.md`의 Portal 작업 규칙(필요 시 backend 변경을 이슈로 제기 후 공동구현)에 따라
DMS owner와 합의한다.
