# DMS Data Management API — `sync` (dsync/nsync)

> 이 문서는 주로 **`sync`** 연산을 다루되, **scan/rm/sync 전 연산의 요청·응답 API 예시는 §14**(testbed 실측 응답)에 정리한다.
> DM은 RM과 단일 컨트롤플레인(API·planner·operational DB·요청 수명주기)을 공유하되, **실행은
> Volcano/MPI 잡**으로 분리된다. 본 문서는 요청 제출부터 최종 결과까지 전체 workflow, Volcano
> 스케줄링, 노드간 MPI 호스트 파악, 프로세스/노드 수 기본값·설정·검사, sanity/readiness,
> 권한 모델, 설정 레퍼런스를 정리한다.

---

## 0. 한 줄 요약

`sync` = 파일시스템 경로 간 데이터 복제. planner가 요청을 `data_job`(worker_role=DM)으로 만들고,
`dms-dm-worker`가 **Volcano 잡**(단일/다중 노드 MPI)으로 `dsync`(mpifileutils, Open MPI)를 실행한다.
**파괴적이므로 preview→confirm 게이트**를 통과해야 실제 복제가 일어난다. 잡 프로세스는 요청자의
**POSIX 신원(uid/gid)** 으로 실행된다.

## 1. 구성요소와 역할

| 컴포넌트 | 종류 | sync에서의 역할 | 데이터 접촉 |
|---|---|---|---|
| `dms-api` | Deployment | 요청 수신·검증·`202` 영속화, 토큰 인증 | ✗ |
| `dms-planner` | Deployment | 요청→`data_job`+`plan`(worker_role=DM), 스토리지 sanity/readiness 가드 | ✗ |
| `dms-dm-worker` | Deployment | plan 클레임→preflight→**Volcano 잡 생성·폴링**→결과 분류·기록 (오케스트레이터) | ✗(artifact만 읽음) |
| `dms-dm-agent` | DaemonSet | 노드별 prober. mount/tool/identity/credential/network **증거 리포트** | ✗ |
| **job pod** | VolcanoJob/MPIJob | `dsync`를 **요청자 uid/gid로 실제 실행** (mpifileutils 이미지) | ✅ |
| Volcano | volcano-system | job pod를 큐(`dms-data`)에 **gang-schedule** + 파드간 SSH/DNS(plugins) | ✗ |
| `dm_identity_denylist` | operational DB | requester/owner/group **kill-switch + admission block**(유일한 영속 DM 신원 상태, 기본 빈값=전체 허용) | — |
| PostgreSQL | pkg-01 | `requests→plans→runs→results` + `data_jobs` + `agent_reports` | — |
| 공유 artifact 경로 | CephFS | preview/execution의 rank-script·로그·summary (worker·job 공유 RWX) | — |

**핵심 분업**: agent=증거(이 노드가 이 유저로 잡을 돌릴 수 있나?), worker=오케스트레이션(데이터 비접촉),
**job pod만 실제 데이터 접촉**(요청자 uid/gid로).

> **신원 해석은 저장된 매핑이 아니라 컨트롤플레인의 read-only LDAP 조회**다. dm-worker가 preflight에서
> `owner_username`을 LDAP로 검색(RM이 쓰는 동일 디렉토리)해 uid/gid/groups를 해석하고 pod securityContext
> (`runAsUser`/`runAsGroup`/`fsGroup`)를 세팅한다. 영속되는 DM 신원 상태는 `dm_identity_denylist`(admission
> kill-switch)뿐이다.

## 2. 전체 workflow (제출 → 최종 결과)

```
[1] POST /api/v1/data-management/sync        → 검증 → 202 Persisted
[2] planner: data_job + plan(worker_role=DM) + sanity/readiness 가드
        (sync는 plan precondition: preview_required=true, safe_paths_only=true)
[3] dm-worker preflight (_sync_preflight)
        - `owner_username`을 LDAP로 read-only 조회하여 uid/gid/groups 해석 (+ denylist admission 확인)
          (LDAP 다운 시 `ldap_unavailable`로 fail-closed)
        - fresh DM agent report에서 후보 노드 선정 (mount/dsync tool/identity/cred/net)
        - 툴 선택: same-node src+dst → dsync / cross-node → nsync
        - 리소스 모델 (queue/priority_class/노드수/프로세스수 clamp)
        - ★ POSIX 권한 프로브 잡 (요청자 uid/gid로 read/execute/write 검사)
[4] preview 단계 (VolcanoJob): dsync --dryrun (실복제 X) → summary + fingerprint
        → job state = ConfirmPending
[5] POST /jobs/{id}:confirm (preview_observed_hash fingerprint 검증)
[6] execution 단계 (VolcanoJob): dsync (실복제) → summary
[7] dm-worker: terminal 기록 (Succeeded 등) + observability 이벤트
```

**요청 페이로드(`DataJobRequest`, `extra="forbid"`):**
```json
POST /api/v1/data-management/sync   (Bearer + x-dms-actor)
{
  "requester_id": "cocoa.song",
  "owner_username": "cocoa.song",                  // (선택) 실제 POSIX 신원. 미지정 시 requester_id 사용. LDAP 조회 키.
  "source":      {"storage_name": "cephfs-dms", "path": "dms/dsync-test/src"},
  "destination": {"storage_name": "cephfs-dms", "path": "dms/dsync-test/dst"},
  "priority": "Mid",                               // High/Mid/Low (대소문자 무관) 또는 정수
  "resources": {"node_count": 1, "processes_per_node": 1},
  "memo": "..."
}
```
- 경로는 **storage-relative**(앞에 `/` 금지, `..` 금지 — `reject_unsafe_relative_path`). **기준점은 `DMS_DM_PATH_BASE`**:
  기본 `mount_path`(예 `/cephfs`) 기준, `managed_root` 설정 시 **managed_root**(예 `/cephfs/dms`) 기준 — planner가 요청
  path 앞에 managed_root suffix를 붙여 변환한다(§14.9). 원본은 `request_payload`에 보존, volcano/preflight는 불변.
  (legacy: `storage_name` + `source_path`/`destination_path` 평면 필드도 same-storage sync에서 수용.)
- `owner_username`: **RM의 파일시스템 owner 모델을 그대로 미러링**. `requester_id`는 자유형 논리 id이자
  `owner_username`의 **기본값**이고, 요청이 `owner_username`(실제 POSIX 신원)을 주면 그 값으로 오버라이드한다.
  preflight LDAP 조회는 이 `owner_username`을 키로 uid/gid/groups를 해석한다.
- `priority`: `High/Mid/Low` 대소문자 무관(`label.lower()==known.lower()`) → 정수 200/100/50. raw mpirun 옵션/SSH키/hostfile 직접 지정 금지.

**상태 폴링:** `GET /api/v1/operations/requests/{id}` → `.request.status`,
또는 `GET /api/v1/data-management/sync/jobs/{job_id}` → `.job.state`
(`PreflightRunning → PreviewRunning → ConfirmPending → Running → Succeeded/Failed`).

## 3. preview → confirm 게이트 (파괴 방지)

- planner가 sync plan에 `preview_required=true`, `safe_paths_only=true`를 박는다.
- **preview**: `dsync --dryrun`으로 복제 없이 인벤토리만 산출 → `result_summary.preview.summary`
  (`file_count`, `directory_count`, `total_bytes`, `dry_run=true`) + **fingerprint** 기록 → `ConfirmPending`.
- **confirm**: `POST /api/v1/data-management/jobs/{id}:confirm`
  ```json
  { "confirm": true, "preview_observed_hash": "sha256:<preview fingerprint>" }
  ```
  - `DMS_DM_CONFIRM_REQUIRE_PREVIEW_FINGERPRINT=true`(기본)면 fingerprint 일치 필수(중간 변경 감지).
    불일치 → 거부, preview 만료 → `PreviewExpired`.
- **confirm 없이는 절대 execution 없음.** 이 게이트를 우회/약화하지 말 것.

> zsh 주의: colon 엔드포인트는 반드시 `"${jid}:confirm"`(브레이스)로 호출. `"$jid:confirm"`은 zsh
> 수식어로 변형되어 404가 난다.

## 4. POSIX 권한 모델 (성공/실패의 핵심)

잡 pod는 **요청자 uid/gid로 실행**된다(`runAsUser=mapping.uid`, `runAsGroup=mapping.gid`,
`fsGroup=mapping.gid`). **supplementary group은 적용되지 않으므로 접근은 primary gid + 소유권으로만 결정**된다.

**preflight POSIX 권한 프로브**: preview 본 잡 전에 요청자 uid/gid로 실행되는 pod가
`read_source`, `execute_source`, `write_destination_parent`, `execute_destination_parent`를 검사한다.
실패 시 **`posix_permission_denied`로 PreflightFailed**(부작용 없음). 이 프로브는 **툴 토폴로지를 인지**한다:

- **dsync (동일 노드)**: source·destination 마운트가 같은 노드에 있으므로 **단일 pod**가 두 마운트를
  hostPath로 올려 source·destination을 한 번에 검사한다.
- **nsync (분리 노드)**: source·destination이 **서로 disjoint한 노드 집합**에 마운트되므로 어떤 단일 노드도
  두 마운트를 가질 수 없다. 따라서 **역할별로 분리된 두 pod**를 띄운다 — `source` pod는 source 노드 1개에
  핀해 `read_source`만, `destination` pod는 destination 노드 1개에 핀해 `write_destination_parent`만
  검사하고, **둘 다 통과해야 Ready**다(`runtime_permission_check.role_checks.{source,destination}`).
  (스토리지 단위 POSIX 뷰는 그 스토리지를 마운트한 모든 노드에서 동일하므로 역할별 대표 노드 1개 검사로 충분 —
  멀티노드 MPI에서도 동일.)

**dsync 실행 성공 조건 (non-root 요청자):** `dsync`는 dest를 source와 동일하게(소유권·권한·타임스탬프
포함) 맞춘다. non-root는 타 유저로 chown/utime이 불가하므로:
- **source는 요청자가 읽을 수 있어야** 하고(소유 또는 그룹),
- **destination은 요청자가 소유해야** 한다(dest dir utime + dest 파일 소유권 설정).
- 가장 안전한 정상 케이스: **source·destination 모두 요청자 소유**(group은 공통 그룹).

요약: "요청자가 source를 읽고 destination을 소유" → 성공. 그렇지 않으면 preflight 또는 execution에서 권한 실패.

## 5. Volcano 스케줄링

- **큐**: 모든 DM 잡은 단일 Volcano 큐 `dms-data`(정책 `default_queue`)에 제출. (큐 Open, weight 1.)
- **PriorityClass**: 잡 pod의 `priorityClassName`은 정책 `default_priority_class`(=`dms-normal`) 단일값.
  3-tier PriorityClass 존재: `dms-low`(50) / `dms-normal`(100) / `dms-high`(200) = `DATA_PRIORITY_LABELS`.
  (요청 `priority`는 정수로 job/PodGroup priority에 반영되나, 현재 priorityClassName은 정책 단일값.)
- **Gang scheduling**: 각 잡은 PodGroup으로 묶이고 `minAvailable = worker_pod_count(+launcher 1)`.
  전원 스케줄 가능할 때만 동시 기동(부분 기동 방지). 자원 부족 시 `PodGroupPending/Unschedulable`로 대기.
- **MPIJob vs native VolcanoJob**: `DMS_DM_SCHEDULER_BACKEND=auto`(기본) → MPIJob 먼저 시도,
  불가 시 native VolcanoJob fallback. 잡은 **launcher 1 + worker N** 구조.
- **파드간 통신 plugin**: VolcanoJob `plugins: {ssh: [], svc: []}` →
  - `ssh`: launcher↔worker SSH 키/`authorized_keys` 자동 주입(Open MPI rsh launch).
  - `svc`: 파드 hostname DNS + worker host 목록(`/etc/volcano/worker.host`) 주입.

## 6. 노드간 MPI 호스트 파악 + 프로세스/노드 수

### 6.1 호스트 파악(host discovery)
- Volcano `svc` plugin이 **worker pod 호스트명을 `/etc/volcano/worker.host`**(env `DMS_MPI_HOSTFILE`)에 주입.
  (nsync는 `source_worker.host`/`destination_worker.host`로 역할 분리.)
- launcher 스크립트가 그 목록을 읽어 `getent hosts`로 IP 해석 후 **mpirun hostfile**(`<host> slots=<processes_per_node>`)을 생성.
- launcher는 `OMPI_MCA_plm_rsh_agent='ssh -o StrictHostKeyChecking=no ...'`로 worker에 rsh launch,
  `mpirun --allow-run-as-root --mca pml ob1 --mca btl tcp,self --mca btl_tcp_if_exclude lo -np <process_count> <rank_script>` 실행.
- rank script는 root면 `runuser -u <요청자> -- dsync ...`로 **권한을 요청자로 강등**해 실행.

### 6.2 프로세스/노드 수 — 기본값·clamp·설정
DM **정책(operational DB, 연산별)** 이 기준이고 요청 `resources`로 상한 내 조정한다.

| 항목 | 기본 | 최대 | 요청 필드 | 설정(부트스트랩 env) |
|---|---|---|---|---|
| worker 노드 수 | 3 | 3 | `resources.node_count` | `DMS_DM_POLICY_DEFAULT_WORKER_NODES` / `..._MAX_WORKER_NODES` |
| 노드당 프로세스 | 3 | 10 | `resources.processes_per_node` | `DMS_DM_POLICY_DEFAULT_PROCESSES_PER_NODE` / `..._MAX_...` |

- **clamp 규칙**(`_clamp_policy_count`): 요청값 미지정 → 기본값. 요청값 > 최대 → 최대로 clamp(+`clamp_reasons`).
  요청값 ≤ 최대 → 그대로. (1 같은 작은 값은 그대로 허용.)
- `process_count = worker_pod_count × processes_per_node`. launcher 1개 별도.
- **적격 노드 부족** 시 `insufficient_eligible_nodes`로 Rejected(적격 노드 = fresh DM agent가
  mount+dsync tool+identity 모두 Ready로 보고한 노드).
- 정책 조회/수정: `GET/PUT /api/v1/data-management/policies[/{operation}]`.

> 권장(검증): 검증은 `node_count=1, processes_per_node=1`(launcher+worker 1쌍)로 시작하면 단순하다.
> 다중노드는 §7의 **공유 artifact 경로**가 반드시 충족돼야 rank-script를 worker가 읽는다.

## 7. 전제조건 (sync 동작에 반드시 필요)

1. **dm-worker** 운영(replicas≥1), 컨트롤플레인과 동일 이미지.
2. **Volcano** 설치(scheduler/controller/admission/CRD) + **큐 `dms-data`** + **PriorityClass `dms-normal`**(+low/high).
3. **`dms-dm-agent` DaemonSet**(`DMS_AGENT_WORKER_ROLE=DM`) — 노드별 DM 증거 리포트. 없으면
   preflight가 `no_ready_dm_candidate`.
4. **mpifileutils job 이미지**(`DMS_DM_JOB_IMAGE`): `dsync/dcp/dscan/drm/nsync` + Open MPI `mpirun` +
   OpenSSH client/server 포함. `install/docker/Dockerfile.mpifileutils`로 빌드.
   **요청자 POSIX 유저가 이미지에서 해석돼야**(잡 스크립트가 `chown <username>` 수행) — 베이크 또는 LDAP NSS.
5. **dm-agent도 dsync 툴을 PATH에 가져야**(agent `probe_tools`는 `shutil.which()`로 존재 확인) +
   요청자 유저를 `getpwnam`으로 해석(identity 증거). → agent 이미지 = dms CLI + mpifileutils + 유저.
   (`DMS_AGENT_IDENTITY_USERS`에 프로빙할 유저 나열.)
6. **공유 RWX artifact 경로**(`DMS_DM_ARTIFACT_BASE_URI`): launcher가 쓴 rank-script를 다른 노드의
   worker가 읽어야 하므로 **노드 공유 파일시스템**이어야 한다(CephFS 권장: `file:///cephfs/dms/artifacts`).
   **dm-worker와 job pod 양쪽에 마운트**(worker는 summary 읽기, job은 rank/로그 쓰기).
   - **마운트포인트를 `HostToContainer`(rslave)로**: 공유 FS의 **마운트포인트**(서브경로 아님)를
     `mountPropagation: HostToContainer`로 마운트한다. dm-worker는 장수 오케스트레이터라, 서브경로를 기본
     (`None`) propagation으로 bind하면 host가 세션 중 공유 FS를 재마운트할 때 bind가 stale돼 새 artifact를
     못 본다. 마운트포인트를 rslave로 받으면 host 재마운트가 전파돼 **재기동 없이** 복구된다(노드 `/`·마운트
     포인트가 `shared` 전제). job pod 볼륨(source/dest/target/artifact)도 동일. → §13.2.
   - **nsync(분리 노드) 필수 조건**: nsync는 source·destination이 **서로 다른 스토리지/노드 집합**에 있으므로,
     artifact 스토리지는 source도 destination도 아닌 **모든 참여 노드(source 노드 + destination 노드)에 공통
     마운트된 별도 공유 스토리지**여야 한다(예: source=`cephfs-third`@w1–3, dest=`cephfs-secondary`@w4–5,
     artifact=`cephfs-dms`@w1–5). 공통 마운트가 없으면 launcher가 쓴 rank-script를 다른 역할의 worker가 읽지
     못해 `mpirun ... could not access ... rank.sh`로 전 rank가 기동 실패한다. (dsync는 source=dest 노드가
     동일하므로 같은 스토리지가 artifact를 겸할 수 있다.)
   - **보안 모델 (artifact 권한)**:
     - **베이스 디렉토리 = `root:root 0755`** (world-writable `1777` 금지). 베이스 레벨에 `<job_id>/`를
       만드는 건 **root로 도는 launcher뿐**(preflight probe pod는 `test`/`printf`만).
     - **per-job artifact = 요청자 소유 only**: launcher가 `umask 077` + `_chown_artifact_line`(요청자 chown +
       `u+rwX,go-rwx`)로 잠근다 → **타 테넌트 job pod가 공유 FS에서 못 읽음**.
     - **dm-worker는 root로 실행**(`securityContext.runAsUser:0`)하여 잠긴 `summary.json`을 읽는다.
       dm-worker는 **읽기전용 오케스트레이터**(FS 쓰기 0, `kubectl`은 SA 토큰, summary는 **심볼릭링크
       containment 가드**(`_artifact_path_within`)로 읽음)라 root가 그 읽기 외 권한을 주지 않는다.
       (api/planner/rm-worker는 비-root uid 65532 유지.)
     - rank-script/hostfile(`mpi/`)은 root launcher가 쓰고 root orted가 읽으므로 `0700` root로 잠가도 동작.
7. **LDAP 신원 해석(read-only)**: dm-worker가 preflight에서 `owner_username`을 LDAP로 조회해
   uid/gid/groups를 해석한다(저장 매핑 없음, RM과 동일 디렉토리). `DMS_LDAP_*` env 설정 필수.
   LDAP 다운 시 `ldap_unavailable`로 **fail-closed**(stale 신원 없음). `dm_identity_denylist` admission도 함께 검사.
8. **스토리지 DM readiness = Ready**: 스토리지 매핑 sanity가 DM 증거를 인지해야 planner가 통과(아래 §8).
9. **filesystem backend는 `managed_root` 명시 필수**(cephfs/wekafs/gpfs): storage mapping `backend_template`에
   managed_root가 있어야 등록된다(없으면 등록 시 422; 암묵 `{mount_path}/dms` 기본 제거; mount_path 아래여야 함).
   CSI/quota 등 비-filesystem은 제외. `DMS_DM_PATH_BASE=managed_root` 모드의 path 기준점이 된다. → §14.9.

## 8. Sanity / Readiness (주기성)

- 스토리지 매핑 row에 `sanity_status` / `readiness{resource_management,data_management,inventory}` /
  `sanity_result` / `sanity_checked_at`가 저장된다. planner는 이 **저장값**을 읽어
  `_reject_unsafe_storage_mapping`에서 가드(`Failed`/`Unknown` sanity 또는 DM readiness≠Ready → 거부:
  `missing_dm_readiness`).
- readiness는 fresh agent 리포트(inventory)에서 산출(`_role_readiness`: 해당 storage를 mount한 DM 후보
  존재 → `Ready`).
- **수동 트리거**: 스토리지 매핑 `POST`/`PATCH`, `POST /api/v1/resource-management/storage-mappings/{name}:check`.
- **자동 갱신 (구현됨)**: `readiness`는 fresh agent 증거의 캐시이므로 stale로 흐른다(stale "Missing"은
  정상작업 차단, stale "Ready"는 증거소실 후에도 admit). 3계층으로 자동·양방향 갱신한다 — 전부 기존
  `sanity_service.check_mapping`을 재사용(로직 포크 없음, RM 불변):
  - **① 주기 reconciler** (`dms sanity-reconciler --loop`, `install/kubernetes/sanity-reconciler.yaml`):
    `DMS_SANITY_RECONCILE_INTERVAL_SECONDS`(기본 30s)마다 전 스토리지 sanity 재실행→readiness 갱신.
    heartbeat 기반 livenessProbe로 자가수복, per-storage 결함격리.
  - **② 이벤트 갱신** (`DMS_SANITY_EVENT_RECOMPUTE_ENABLED`, 기본 off): DM agent 리포트 수신 시 해당
    스토리지 readiness 즉시 재계산.
  - **③ planner staleness 게이트** (`DMS_SANITY_PLANNER_GATE_ENABLED`, 기본 off, **DM 한정**): readiness가
    "Ready"여도 `sanity_checked_at`이 `DMS_SANITY_TTL_SECONDS`(기본 120s)보다 오래면 fail-closed
    (`dm_readiness_stale`). reconciler가 죽어도 정합성 보존(③이 ①의 fail-safe).

> 배포 순서: ③ 게이트를 켜기 전 reconciler를 먼저 배포·확인할 것. reconciler 없이 게이트만 켜면
> `sanity_checked_at`이 TTL을 넘는 순간 DM이 fail-closed된다. (그래서 ③ 기본 off.)

| API 검증 | unknown 필드, `/`·`..` 경로, storage 누락 | `422/400` (영속화 안 됨) |

### 10.1 신원 해석 (LDAP, preflight read-only)

|---|---|---|

| `DMS_LDAP_URI` | — | LDAP 서버 URI(`ldap(s)://host:port`). |
| `DMS_LDAP_BASE_DN` | — | 디렉토리 base DN. |

### 10.2 DM-side 신원 denylist (kill-switch)

`dm_identity_denylist`(`subject_type, subject, reason, created_at, created_by`)가 **유일한 영속 DM 신원 상태**다.
기본 **빈값=전체 허용**. requester/owner는 LDAP 조회 **전**, group은 조회 **후**(그룹은 조회 후에만 알 수 있으므로) 검사.

| 메서드 | 엔드포인트 | 동작 |
|---|---|---|
| `PUT` | `/api/v1/data-management/identity-denylist/{subject_type}/{subject}` (body `{"reason":"..."}`) | 차단 등록 → `200 {"status":"Denied"}` |
| `DELETE` | `/api/v1/data-management/identity-denylist/{subject_type}/{subject}` | 차단 해제 → `200 {"status":"Allowed"}` (없으면 `404`) |
| `GET` | `/api/v1/data-management/identity-denylist` | 목록 |

- `subject_type ∈ {requester, owner, group}` (그 외 `400`). 차단된 신원의 요청은 preflight `identity_denied`로 `Rejected`.

### 10.3 dm-worker observability 이벤트 (신원)

- `data_job_identity_resolved` (INFO): LDAP 조회로 uid/gid/groups 해석 성공.
- `data_job_identity_not_found` / `data_job_identity_lookup_failed` / `data_job_identity_denied` (WARN):
  각각 `ldap_identity_not_found` / `ldap_unavailable`·`ldap_not_configured` / `identity_denied`에 대응.
- denylist API: `dm_identity_denylist_added` / `dm_identity_denylist_removed`.
- `data_job_privileged_identity_resolved` (WARN): privileged 경로로 uid/gid 0 신원 합성(§10.4).
- API 게이트: `data_job_privileged_authorized` / `data_job_privileged_denied` (WARN; actor·principal·reason 기록).

### 10.4 운영자 root 실행 (privileged requester)

운영자가 임의 사용자 데이터를 이관·정리하려면 root(uid 0)로 mpifileutils를 실행해야 할 때가 있다. 기본은
**비활성**이며(=오늘과 동일하게 `requester_id=root`는 `ldap_identity_not_found`로 거부), 켜면
`requester_id`(또는 `owner_username`)가 권한 목록에 속한 요청을 **uid/gid 0으로 합성 실행**한다 — LDAP
조회와 uid floor를 우회하고, job pod는 `runAsUser:0`(`runAsNonRoot` 미설정)로 뜬다.

트리거는 **`requester_id=root`**(또는 `owner_username=root`)이지만, 실제 인가는 API edge에서 이뤄진다:

| 통제 | 동작 | 설정 |
|---|---|---|
| feature flag | 꺼지면 전체 no-op(오늘과 동일) | `DMS_DM_ALLOW_ROOT_REQUESTER` (기본 `false`) |
| 권한 requester 집합 | 이 집합과 일치할 때만 root 합성 | `DMS_DM_PRIVILEGED_REQUESTERS` (기본 `root`) |
| **mTLS operator 강제** | root 요청은 **mTLS-verified operator**(actor가 `mtls:` 접두)만 허용. 평문 actor 채널의 root 요청은 `403` | `DMS_REQUIRE_MTLS_VERIFIED_HEADER=true` 전제 |
| operator allowlist | 특정 operator actor만 허용 | `DMS_DM_PRIVILEGED_OPERATORS` (csv, 비우면 verified operator 전체) |
| scope allowlist | root 잡이 건드릴 storage/경로 제한 | `DMS_DM_PRIVILEGED_SCOPES` (csv, `storage` 또는 `storage:prefix`; 비우면 전체) |
| denylist kill-switch | root도 denylist로 즉시 차단 | `identity-denylist` API(§10.2) — 합성 **이전** 검사 |
| 합성 uid/gid | privileged 신원 값 | `DMS_DM_PRIVILEGED_UID` / `_GID` (기본 `0` / `0`) |

```jsonc
// DMS_DM_ALLOW_ROOT_REQUESTER=true + mTLS-verified operator cert로 호출
POST /api/v1/data-management/sync
{ "requester_id": "root",
  "source":      { "storage_name": "cephfs-ops", "path": "migrations/src" },
  "destination": { "storage_name": "cephfs-ops", "path": "migrations/dst" } }
// → 202 Persisted → preflight가 uid/gid 0 합성(identity_provider:"privileged") → job pod runAsUser:0
```

> **보안 전제(중요).** 이 기능의 안전성은 **"누가 DMS DM API를 호출할 수 있는가"** 로 환원된다.
> `requester_id`는 클라가 채우는 인증 안 된 필드이므로, DMS DM API를 **신뢰된 operator(mTLS)로 한정**하고
> `DMS_REQUIRE_MTLS_VERIFIED_HEADER=true` 경로에서만 root 요청을 받아야 한다. 평문 `x-dms-actor` 채널로
> root가 닿을 수 있으면 권한상승 구멍이 된다.

- **preview→confirm 게이트는 root에서도 우회되지 않는다**(sync/rm). preflight POSIX 프로브는 uid 0이라 통과.
- flag가 꺼져 있으면 root 요청은 합성되지 않고 worker가 `ldap_identity_not_found`로 거부한다(§9).
- 비-privileged 일반 사용자는 영향 없음 — LDAP 경로·uid floor(`DMS_DM_MIN_UID`)·`runAsNonRoot:True` 모두 유지.
- **agent에 root identity 프로빙 불필요**: privileged 합성 신원은 어느 노드/이미지에서나 해석되므로(`getpwnam("root")` 항상 성공) 후보 선정이 agent identity 증거를 요구하지 않는다(`DMS_AGENT_IDENTITY_USERS`에 root 추가 불필요). job pod(launcher/worker)는 read-only `/root/.ssh`의 Volcano MPI 키를 root로 직접 사용한다.

## 13. 운영 주의사항 (Caveats)

라이브 검증에서 실제로 부딪힌 함정들. 새 환경 구축·디버깅 시 먼저 확인.

### 13.1 POSIX 권한 (가장 흔한 실패 원인)
- 잡은 **요청자 uid/gid로 실행**되고 **supplementary group은 적용 안 됨**(primary gid + 소유권만). 
- **dsync는 non-root에서 dest를 source와 동일하게 맞추려다 utime/chown으로 exit 1** → **source는 요청자가
  읽을 수 있고, destination은 요청자가 소유**해야 완전 성공. "그룹 읽기만"으로는 dest dir utime에서 실패.
  정상 케이스 = src·dst 모두 요청자 소유(group은 공통).
- 음성(권한없음) 케이스는 preflight 권한 프로브 잡에서 `posix_permission_denied`로 **execution 전 차단**(부작용 0).

### 13.2 artifact (공유 FS + 보안)
- **공유 RWX 파일시스템 필수**, **dm-worker·job pod 양쪽 마운트**. 노드-로컬 hostPath면 멀티노드에서
  rank-script 공유 실패 + dm-worker가 summary 못 읽음. (CephFS 권장: `file:///cephfs/dms/artifacts`.)
- **베이스 디렉토리 = `root:root 0755`**(world-writable `1777` 금지). per-job artifact는 launcher `umask 077`
  + 요청자 chown으로 **요청자-only**(world-read 0). **dm-worker는 root**(`runAsUser:0`)로 잠긴 artifact를 읽음.
- dm-worker는 읽기전용 오케스트레이터이나, root 사용 시 **심볼릭링크 containment 가드**(`_artifact_path_within`)로
  요청자가 심은 심링크를 차단. dm-worker 자신의 메타데이터 쓰기는 `umask 077`(cli)로 0600.
- **bind-mount stale 방지 (`HostToContainer`)**: dm-worker는 공유 FS의 **마운트포인트**(`/cephfs` 등, 서브경로
  아님)를 `mountPropagation: HostToContainer`(rslave)로 마운트한다. 서브경로를 기본(`None`) propagation으로 bind
  하면 host가 세션 중 공유 FS를 언/재마운트할 때 컨테이너 bind가 옛 마운트에 고정(stale)돼 다른 노드 artifact를
  못 읽는다(scan은 `summary artifact is missing or invalid`로 실패). 마운트포인트를 rslave로 받으면 host 재마운트가
  전파돼 **재기동 없이** 복구(노드 `/`·마운트포인트가 `shared` 전제). job pod의 hostPath 볼륨(source/dest/target/
  artifact)도 동일 propagation. 부팅 fstab 마운트라 평상시엔 무관, 세션 중 마운트 변경에만 관여.

### 13.3 이미지 (요청자 baked + mpifileutils)
- **job 이미지**: mpifileutils(`dsync/dcp/dscan/drm/nsync`) + Open MPI + OpenSSH + **요청자 POSIX 유저 baked**
  (`useradd`). 잡 스크립트가 `chown <username>` + `runuser`를 쓰므로 이름해석 필수.
- **dm-agent 이미지**: dms CLI + mpifileutils(agent `probe_tools`가 `which`로 툴 존재 확인) + 요청자 유저 baked
  (`probe_identities`가 `getpwnam`). `DMS_AGENT_IDENTITY_USERS`에 프로빙할 유저 나열.
- **`umask 077` 주의**: job 이미지가 `useradd -M`(홈 없음)이면 launcher가 홈을 root 0700으로 만들어 SSH client가
  개인키를 못 읽음 → launcher/worker가 **홈 디렉토리도 요청자 chown**(구현됨). (멀티노드 cross-node SSH의 핵심.)

### 13.4 Volcano / 잡 라이프사이클
- **terminal 잡의 leftover VolcanoJob/worker pod가 큐·gang 용량을 점유**해 다음 잡을 `Pending`으로 막는다.
  → `DMS_DM_JOB_DELETE_ON_TERMINAL=true` 권장, 또는 수동 `kubectl delete vcjob`.
- **워커 재배포 중 lease 핸드오프**: in-flight 잡을 claim한 워커가 죽으면 plan lease(기본 300s) 만료까지 새
  워커가 못 받아 잡이 멈춘 듯 보임. 재배포는 idle일 때, 또는 lease 만료를 기다릴 것.
- preview/execution은 **별도 VolcanoJob**(launcher 1 + worker N). mpirun은 `runuser`로 **요청자**로 실행되고
  worker sshd는 root(MPI rsh용)이며 실제 dsync는 요청자로 runuser-강등.

### 13.5 readiness
- dm-agent를 새로 붙이면 storage readiness가 stale `Missing`으로 남아 `missing_dm_readiness` 거부 가능 →
  `:check` 수동 실행, 또는 **sanity-reconciler 배포**(§8)로 자동 갱신.

### 13.6 클라이언트 함정
- **zsh colon 엔드포인트**: `:confirm`/`:cancel`/`:check`는 반드시 `"${jid}:confirm"`(브레이스). `"$jid:confirm"`은
  zsh 수식어로 변형되어 404.
- **fingerprint 위치**: `GET /data-management/sync/jobs/{id}`는 잡을 **최상위**로 반환 →
  `result_summary.preview.fingerprint`(중간 `job` 래퍼 없음). list/request의 sha256 정규식은 빈문자열 해시
  (resource_key)를 잡으니 쓰지 말 것.
- confirm에 `preview_observed_hash`(preview fingerprint) 필요(`DMS_DM_CONFIRM_REQUIRE_PREVIEW_FINGERPRINT=true`).

### 13.7 비-root 컴포넌트
- **api/planner/rm-worker는 비-root(uid 65532)**. **dm-worker만 root**(잠긴 artifact 읽기용, 읽기전용
  오케스트레이터라 추가 권한 없음). RM worker는 비-root지만 storage 노드에 **SSH + 원격 sudo**로 권한 행사.

## 14. API 예시 (전 연산 — testbed 실측 응답)

> 모든 요청은 `Authorization: Bearer <token>` + `x-dms-actor: <name>` 헤더 둘 다 필수(§3). 베이스 경로는
> `http(s)://<api-host>:<port>/api/v1/data-management`. 아래 응답은 testbed(`cephfs-dms`, 요청자 `cocoa.song`)
> 실측을 발췌한 것(긴 필드 `…`로 생략). **POST 제출은 `202 {request_id, status:"Persisted", …}`** 를 반환하며
> **job_id가 아니다** — 이후 `GET …/{op}?requester_id=…` 목록에서 `request_id`로 job을 찾거나
> `GET …/{op}/jobs/{job_id}`로 상세를 폴링한다(`state` 필드).

### 14.9 managed_root path base (`DMS_DM_PATH_BASE=managed_root`)

기본은 `mount_path` 기준(위 예시들). `DMS_DM_PATH_BASE=managed_root`(글로벌, planner 재기동 필요)로 켜면 요청
path를 **managed_root 기준**으로 적고, planner가 storage별 managed_root suffix(`relpath(managed_root, mount_path)`)를
prepend해 변환한다. **volcano/preflight/result/스크립트는 불변**(변환된 path가 여전히 mount_path 상대 경로이므로).

```jsonc
// managed_root 모드 — cephfs-dms는 managed_root=/cephfs/dms (suffix "dms")
POST /api/v1/data-management/scan
{ "requester_id": "cocoa.song", "target": { "storage_name": "cephfs-dms", "path": "scan-test" } }
//                                                                 ^^^^^^^^^ "dms/" 생략 (managed_root 기준)

// 결과: planner가 "dms/scan-test"로 변환 → /cephfs/dms/scan-test 스캔
{ "state": "Succeeded",
  "normalized_target": { "path": "dms/scan-test" },          // 변환된 (mount_path 상대) 경로
  "result_summary": { "summary": { "scan_root": "dms/scan-test", "file_count": 5 } },
  "request_payload": { "target": { "path": "scan-test" } } }  // 원본 보존 (resource_key·conflict 키도 원본)
```
> **전제 — filesystem backend(cephfs/wekafs/gpfs) storage mapping은 `managed_root` 명시 필수**(등록 시 422;
> 암묵 `{mount_path}/dms` 기본값 제거; managed_root는 mount_path 아래여야 함). CSI/quota 등 비-filesystem은 제외.
> nsync는 source/destination의 storage별 managed_root가 각각 적용된다. managed_root를 산출 못 하면(비-filesystem
> 등) 잡이 **REJECTED**(`managed_root_unavailable`, fail-closed).
