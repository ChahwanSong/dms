# 7. DMS Portal 종합 운영 대시보드

운영자 콘솔의 **종합 대시보드** 탭은 DMS 컨트롤 플레인의 운영 상태를 한 화면에서 **읽기 전용**으로 모니터링한다:
스케줄러 상태 · 큐/작업 현황 · worker node 상태 · 요청 현황 · 조치 필요 이슈.

이 문서는 대시보드의 데이터 소스, 신규 DMS 엔드포인트, BFF 구조, 패널 구성, 범위/후속 단계, 트러블슈팅을
다룬다. 포탈 자체의 빌드·배포·접근은 `5.dms-portal-setup.md`를 먼저 따른다.

> **거의 전부 기존 API 재사용.** 대시보드는 DMS `operations/*` 읽기 API를 소비한다. 백엔드 변경은 정확한
> 잡 카운트를 위한 **read-only 집계 엔드포인트 1개**(`GET /operations/data-jobs/summary`)뿐이다. 신규 DB·env
> 없음(무상태 프록시/집계). 통신은 BFF `dms_client.py`에서만 일어나고 프론트는 BFF만 호출한다.

## 0. 데이터 소스 매핑 (패널 ↔ 엔드포인트)

`★` 1개만 신규 DMS 엔드포인트, 나머지는 모두 기존.

| 패널 | DMS 엔드포인트 | 핵심 필드 |
| --- | --- | --- |
| 스케줄러 카드 | `GET /operations/control-state` | maintenance_mode · drain_mode · scheduling_blocked · reason |
| 큐/작업 카드 | `GET /operations/work-summary` | plans/runs by state·role·worker_id · lease_expiring_soon · stale_or_recovery · requests.action_required |
| 노드 카드 + 워커 노드 테이블 | `GET /operations/agent-reports?freshness=` | cluster_name · node_name · worker_role · freshness_status(Fresh/Stale) · capability_summary{mounts,tools,csi_drivers,credential_count} · reported_at |
| 요청 카드 | ★`GET /operations/data-jobs/summary` | total · active_total · by_state · by_operation |
| 스케줄러 활동 테이블 | `GET /operations/runs/active` + `GET /operations/runs/stale` | run_id · worker_id · worker_role · state · lease_seconds_remaining · resource_key |
| 요청 테이블 | `GET /operations/data-jobs?state=&operation=&storage_name=&limit=` | job_id · operation · storage_name · state · selected_tool · updated_at |
| 조치 필요 패널 | `GET /operations/action-required` | issue_type + 컨텍스트 필드 |

> 요청 카드/테이블의 UI 라벨은 **'요청'**이지만, 데이터 소스는 DMS data-jobs(`data-jobs/summary` · `data-jobs`)이다.

## 1. 신규 DMS 엔드포인트 (★ 유일한 백엔드 변경)

데이터 잡을 **상태/operation별로 정확히 카운트**하기 위한 read-only 집계. 기존 `data-jobs` 리스트는
`limit`(최대 1000)에 걸려 대규모에서 카운트가 부정확하므로 서버측 `GROUP BY` 집계를 추가했다.

```
GET /api/v1/operations/data-jobs/summary ?storage_name=<opt>&operation=<opt>
→ 200
{
  "total": 93,
  "active_total": 0,                      // 비종료(non-terminal) 상태 합
  "by_state":     { "Succeeded": 46, "PreflightFailed": 20, "Failed": 16, "Cancelled": 11 },
  "by_operation": { "data.sync": 73, "data.scan": 17, "data.rm": 3 }
}
```

- 구현: `repositories/data_jobs.py`의 `data_job_summary()`(state/operation 두 `GROUP BY`), 종료 상태 집합은
  `domain.TERMINAL_DATA_JOB_STATES`로 단일 정의. 라우트는 `operations.py`에서 `/data-jobs/{job_id}` **앞에**
  선언(경로 충돌 방지). 쓰기/마이그레이션/스키마 변경 없음. SQLite/PostgreSQL 포터블.

## 2. BFF 구조

신규 `backend/routers/dashboard.py`, prefix `/api/operator/dashboard`, 전체 `require_role(operator)` 게이트.

| 라우트 | 동작 |
| --- | --- |
| `GET /summary` | 상단 카드용 **병렬 fan-in**(control-state · work-summary · data-jobs/summary · agent-reports 카운트). **부분 실패 허용** — 실패한 섹션은 `{data:null, error}`로 반환, 한 패널 오류가 전체를 깨지 않음. |
| `GET /nodes?freshness=` | agent-reports 프록시(워커 노드 테이블) |
| `GET /runs` | runs/active + runs/stale 합쳐 반환(스케줄러 활동) |
| `GET /requests?state=&operation=&storage_name=&limit=` | data-jobs 프록시(필터) |
| `GET /attention` | action-required 프록시 |

- `dms_client.py`에 read-only 메서드 추가: `get_control_state`, `get_work_summary`, `list_agent_reports`,
  `get_data_job_summary`, `list_active_runs`, `list_stale_runs`, `list_action_required`. 모두 `actor` 전달.
- 인증: 테스트베드 프로파일(bearer + `x-dms-actor`) 그대로. 대시보드는 privileged 불필요(일반 operator actor).

## 3. 화면 구성 / 자동 갱신

- 상단 **카드 4개**: 스케줄러(정상/차단·점검 + maintenance/drain/scheduling) · 큐/작업(활성 plan·run,
  lease 임박, stale/recovery, 주의 필요) · 노드(Fresh/Stale, 역할별 비율) · 요청(실행/대기/확인대기/실패,
  진행중 합).
- **드릴다운**: 조치 필요 패널 · 워커 노드 테이블(Fresh/Stale 필터) · 스케줄러 활동 테이블(stale 강조) ·
  요청 테이블(상태/operation 필터).
- `/summary` 카드는 **7초 자동 폴링**(일시정지 토글 + 수동 새로고침 + 마지막 갱신 시각). 드릴다운은 진입/필터
  변경 시 로드.

## 4. 범위 / 후속 단계

- **v1(현재)**: 읽기 전용. worker node는 **DMS 레벨 건강**(Fresh/Stale, mounts/tools/credentials/role)만.
- **후속 A — OS 메트릭**: CPU/메모리/디스크/load. DMS agent 프로브 + AgentReport 스키마 + DaemonSet 확장 필요
  (별도 작업). v1 노드 패널은 OS 자원 사용량을 포함하지 않는다.
- **후속 B — 스케줄러 제어 액션**: control-state `begin-drain`/`enter-maintenance`/`resume` 버튼(확인
  다이얼로그 + 감사). v1은 읽기 전용 모니터링만.

## 5. 자주 발생하는 문제

### 대시보드 카드가 비거나 한 섹션만 에러
`/summary`는 부분 실패를 허용하므로, 특정 DMS 엔드포인트가 일시 실패하면 그 카드만 값이 비고 나머지는 정상
표시된다. DMS 도달성(`5.dms-portal-setup.md` §1)과 해당 operations 엔드포인트 상태를 확인한다.

### 요청 카드 카운트가 안 보임
DMS가 신규 `GET /operations/data-jobs/summary`를 제공하는 이미지로 배포돼 있어야 한다. 미배포 시 그 카드만
비고 다른 카드는 정상. `curl .../api/v1/operations/data-jobs/summary`로 직접 확인한다.

### 워커 노드 테이블이 비었거나 Stale 다수
agent report freshness 문제다. 노드의 DM/RM agent DaemonSet 동작과 `agent_report_stale_seconds`를 확인한다
(DMS agent 운영은 `1.install-dms-on-pvs.md`/`README` agent 절 참고).
