# DMS Resource Management API — Kubernetes Namespace Quota

DMS의 **Kubernetes namespace quota** Resource Management API를 다룬다. Filesystem(GPFS/WekaFS/
CephFS) RM API는 [`2.dms-rm-api-fs.md`](2.dms-rm-api-fs.md), 설치 전체 과정은
[`1.install-dms-on-pvs.md`](1.install-dms-on-pvs.md)를 참조한다.

---

## 환경 변수 로드

모든 curl 예시는 아래를 먼저 실행한 상태를 전제로 한다 (`2.dms-rm-api-fs.md`와 동일).

```bash
source /mgmt_storage/cocoa.song/.dms-secrets/dms-env.sh
```

`DMS_CURL_OPTS` 배열에 `--resolve`, `--noproxy`, mTLS 인증서, Bearer token, `x-dms-actor` 헤더가 포함된다.

## 1. 동작 모델

DMS는 하나의 namespace quota 리소스를 대상 클러스터의 **단일 `ResourceQuota/dms-storage-quota`**
오브젝트로 렌더링한다.

- **대상 오브젝트**: `<namespace>/dms-storage-quota` (DMS 전용; 이름 고정)
  - 라벨 `dms.io/resource-kind: kubernetes-namespace-quota`
  - 어노테이션 `dms.io/resource-key: <cluster_name>:<namespace_name>`
- **`spec.hard` 키 매핑**:
  | DMS payload | ResourceQuota hard key |
  |---|---|
  | `quota.requests_storage_bytes` | `requests.storage` (namespace-wide) |
  | `quota.pvc_count` | `persistentvolumeclaims` (namespace-wide) |
  | `storage_class_quotas[].requests_storage_bytes` (또는 `capacity_bytes`) | `<sc>.storageclass.storage.k8s.io/requests.storage` |
  | `storage_class_quotas[].pvc_count` | `<sc>.storageclass.storage.k8s.io/persistentvolumeclaims` |
  - `requests.storage`는 bytes → k8s quantity(`Mi`/`Gi`)로 렌더링된다.
  - **최소 1개 hard key**가 있어야 한다 — namespace-wide `quota` 또는 `storage_class_quotas[]` 중 하나
    이상. hard key가 0개면 create는 `kubernetes_quota_hard_key_required`로 거부.
- **StorageClass 유도**: `storage_class_quotas[].storage_name`은 등록된 storage mapping에서
  `storage_class_name` + `cluster_name`을 derive한다(§2.2). 즉 호출자는 storage class 이름을 직접
  쓰지 않고 storage mapping 이름(`storage_name`)을 참조한다.
- **클러스터 라우팅**: payload의 `cluster_name`으로 `dms-cluster-kubeconfigs` Secret의 해당
  kubeconfig를 골라 그 클러스터의 API server에 ResourceQuota를 apply/read한다. 대상 클러스터는
  미리 DMS에 등록돼 있어야 한다(§2.1).
- **agentless**: namespace quota는 RM worker가 대상 클러스터 API server에 **kubectl로 직접 적용**한다.
  filesystem RM(노드에 SSH)과 달리 대상 클러스터에 DMS RM **agent가 없어도 된다** — storage mapping이
  RM-agent readiness를 요구하지 않으며, StorageClass 존재/`csi_driver` 일치(sanity)만 본다(§2.2).
- **read-only / 비파괴 원칙**:
  - DMS는 자기 `dms-storage-quota`만 관리한다. namespace 내 **non-DMS ResourceQuota는 변경하지
    않고**, effective quota 경고(아래)만 기록하며, DMS delete 시에도 보존한다.
  - DMS lifecycle delete는 **namespace를 삭제하지 않는다**(ResourceQuota만 제거).

## 2. 사전 설정

namespace quota를 적용하려면 **(2.1) 대상 클러스터 등록**과 **(2.2) storage mapping 등록**이 필요하다.

### 2.1 대상 클러스터 등록 (kubeconfig + RBAC)

ResourceQuota를 적용할 대상 클러스터는 미리 DMS에 등록한다. DMS control plane(`dms-api` /
`dms-planner` / `dms-rm-worker`)이 그 클러스터 API server로 kubectl을 실행할 수 있도록
**(a) 대상 클러스터 RBAC**, **(b) ServiceAccount kubeconfig**, **(c) DMS 측 등록**(Secret +
ConfigMap)이 필요하다. control plane이 도는 클러스터 자신은 설치 시 이미 등록돼 있다.

아래는 대상 클러스터 `ddz26`을 추가하는 예다(control plane은 `dms` 클러스터에서 동작).

**(a) 대상 클러스터에 DMS RBAC 적용** — `dms-remote` SA + ClusterRole(namespaces/resourcequotas/
storageclasses·csidrivers 권한):

```bash
kubectl --context ddz26 apply -f install/kubernetes/target-cluster-rbac.yaml
```

**(b) 그 SA용 kubeconfig 생성** (대상 클러스터 API server 주소·CA·토큰 임베드). kubectl이 대상
클러스터를 가리키는 상태에서 실행한다:

```bash
KUBECONFIG_OUT=/tmp/ddz26.kubeconfig
install/scripts/create-serviceaccount-kubeconfig.sh ddz26 "$KUBECONFIG_OUT"

# 동작 확인: 이 kubeconfig로 StorageClass가 보이고 resourcequota 생성 권한이 있어야 한다
KUBECONFIG="$KUBECONFIG_OUT" kubectl get storageclass
KUBECONFIG="$KUBECONFIG_OUT" kubectl auth can-i create resourcequota -n default   # -> yes
```

**(c) DMS에 등록** — control plane namespace(`dms`)의 Secret/ConfigMap에 추가 후 재시작:

```bash
# 1) kubeconfig을 dms-cluster-kubeconfigs Secret에 키 'ddz26.kubeconfig'로 추가
kubectl -n dms patch secret dms-cluster-kubeconfigs --type merge \
  -p "{\"data\":{\"ddz26.kubeconfig\":\"$(base64 -w0 "$KUBECONFIG_OUT")\"}}"

# 2) DMS_CLUSTER_KUBECONFIGS_JSON에 cluster_name -> 마운트 경로 추가
#    (Secret은 /etc/dms/kubeconfigs/ 아래에 '키 이름' 그대로 파일로 마운트된다)
kubectl -n dms patch configmap dms-runtime-config --type merge -p \
  '{"data":{"DMS_CLUSTER_KUBECONFIGS_JSON":"{\"dms\":\"/etc/dms/kubeconfigs/dms.kubeconfig\",\"ddz26\":\"/etc/dms/kubeconfigs/ddz26.kubeconfig\"}"}}'

# 3) ConfigMap env 반영을 위해 재시작
kubectl -n dms rollout restart deploy/dms-api deploy/dms-planner deploy/dms-rm-worker
```

**등록 확인** — inventory에 대상 클러스터의 StorageClass / CSI driver가 보이면 성공:

```bash
curl -sS "${DMS_CURL_OPTS[@]}" "$DMS_API_URL/api/v1/operations/inventory" \
  | jq '.clusters | to_entries[] | {cluster:.key, storage_classes:(.value.storage_classes|map(.name)), csi:(.value.csi_drivers|map(.name))}'
```

> - `DMS_CLUSTER_KUBECONFIGS_JSON`은 `cluster_name → 컨테이너 내부 kubeconfig 경로` 맵이다. 이 키가
>   namespace quota payload의 `cluster_name` 및 storage mapping의 `cluster_name`과 일치해야 한다.
> - 대상 클러스터 API server는 control plane pod에서 네트워크로 도달 가능해야 한다.
> - SA 토큰 유효기간은 `create-serviceaccount-kubeconfig.sh`의 `DMS_TOKEN_DURATION`(기본 `8760h`)으로 정한다.

### 2.2 storage mapping 등록 (CSI StorageClass)

namespace quota의 `storage_class_quotas[].storage_name`이 가리킬 storage mapping을 등록한다.
backend type과 무관하게 **`cluster_name` + `storage_class_name`** 만 있으면 namespace quota에
사용할 수 있다(filesystem RM과 mapping을 공유한다). `cluster_name`은 §2.1에서 등록한 클러스터여야 한다.

```bash
source /mgmt_storage/cocoa.song/.dms-secrets/dms-env.sh

curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/storage-mappings" \
  -d '{
    "storage_name": "longhorn-a",
    "backend_template": {
      "backend_type": "longhorn",
      "csi_driver": "driver.longhorn.io"
    },
    "cluster_name": "cluster-a",
    "storage_class_name": "longhorn"
  }' | jq '{storage_name, status}'
```

| 필드 | 설명 |
|---|---|
| `storage_name` | namespace quota가 참조할 mapping 이름 |
| `cluster_name` | ResourceQuota를 적용할 대상 클러스터(= kubeconfig key) |
| `storage_class_name` | live StorageClass 이름 (hard key prefix로 사용) |
| `backend_template.csi_driver` | live StorageClass의 provisioner와 일치해야 한다(불일치 시 sanity `Failed`) |

> **agentless / sanity 상태**: namespace quota는 대상 클러스터 API에 직접 적용되므로 RM agent가
> 필요 없다. 대상 클러스터에 DMS RM agent가 없으면 sanity는 `Degraded`로 남지만(누락 readiness 경고만),
> namespace quota 용도로는 **그대로 사용 가능**하다. namespace quota를 막는 것은 sanity `Failed`뿐이다 —
> 즉 대상 클러스터 미등록(§2.1) · StorageClass 부재 · `csi_driver` 불일치. (filesystem RM은 여전히
> RM-agent readiness가 `Ready`여야 한다.)
>
> 같은 mapping을 filesystem RM과 공유하려면 `backend_type`/mount 등 filesystem 필드도 채운다
> (예시는 `2.dms-rm-api-fs.md`). namespace quota만 쓰는 경우 위처럼 CSI 필드만으로 충분하다.

대상 클러스터의 DMS ServiceAccount는 해당 namespace의 `resourcequotas`에 대해
`get/list/create/update/patch/delete` 권한이 필요하다(§2.1의 `target-cluster-rbac.yaml`로 부여).

**실제 예** — 테스트베드 `ddz26`의 Ceph CSI 두 StorageClass(`ceph-rbd` / `ceph-cephfs`)를 등록:

```bash
# storage_name  storage_class  csi_driver
for row in "ceph-rbd-ddz26 ceph-rbd rbd.csi.ceph.com" \
           "ceph-cephfs-ddz26 ceph-cephfs cephfs.csi.ceph.com"; do
  set -- $row
  curl -sS "${DMS_CURL_OPTS[@]}" -X POST -H "content-type: application/json" \
    "$DMS_API_URL/api/v1/resource-management/storage-mappings" \
    -d "{\"storage_name\":\"$1\",\"backend_template\":{\"backend_type\":\"ceph-csi\",\"csi_driver\":\"$3\"},\"cluster_name\":\"ddz26\",\"storage_class_name\":\"$2\"}" \
    | jq '{storage_name, status, rm_readiness: .mapping.readiness.resource_management}'
done
# -> status "Degraded", rm_readiness "Missing"  (agentless 클러스터에서 정상; namespace quota 사용 가능)
```

> 등록 시점에 대상 클러스터가 아직 미등록(§2.1)이면 sanity는 `Failed`(`cluster_missing` /
> `storage_class_missing`)가 된다. §2.1 등록 후 `POST …/storage-mappings/<storage_name>:check`로
> 재검사하면 `Degraded`로 바뀐다.

## 3. Namespace Quota Resource Management API

### 3.1 API 엔드포인트 요약

| Method | Path | Behavior |
|---|---|---|
| `POST` | `/api/v1/resource-management/kubernetes/namespace-quotas` | 신규 생성: `dms-storage-quota` ResourceQuota apply (+ read-back) |
| `PATCH` | `/api/v1/resource-management/kubernetes/namespace-quotas/{cluster}/{namespace}` | 부분 변경: `quota` / `storage_class_quotas[]`(full replacement) / `expires_at` / `resource_type` |
| `POST` | `…/{cluster}/{namespace}:block` | 차단/해제: `{"block": true}` 모든 hard를 `0`으로(restore state 저장), `{"block": false}` 복원 |
| `DELETE` | `…/{cluster}/{namespace}` | DMS `dms-storage-quota`만 삭제(namespace/PVC/non-DMS RQ 보존) |
| `POST` | `…/{cluster}/{namespace}:check` | consistency check: DB desired vs live `spec.hard` + metadata drift (side-effect 없음) |
| `POST` | `…/{cluster}/{namespace}:sync` | live `spec.hard`를 역산해 DB `quota`/`storage_class_quotas[]` 갱신 (side-effect 없음) |
| `POST` | `…/{cluster}/{namespace}:import` | **DMS-managed** `dms-storage-quota`를 DB 관리로 (재)채택 (외부/비-DMS RQ 미지원 — §3.8) |
| `POST` | `/api/v1/resource-management/kubernetes/namespace-quotas:audit` | read-only audit: DB↔live drift + metadata drift 구조화 (Kubernetes 변경 없음) |
| `POST` | `/api/v1/resource-management/kubernetes/namespace-quotas:expiration-sweep` | 만료된 quota 일괄 차단 (`scope`/`expired_before`/`dry_run`) |
| `GET` | `/api/v1/operations/kubernetes/namespace-quotas/{cluster}/{namespace}` | 단건 조회 (DB desired + live + effective warning) |
| `GET` | `/api/v1/operations/kubernetes/namespace-quotas/expiring` | 만료 임박/만료 목록 |

> 모든 mutating 엔드포인트는 `202 Persisted` 반환 후 비동기 처리. 최종 상태는
> `GET /api/v1/operations/requests/{id}`로 폴링한다(상태값/`resolve`는 `2.dms-rm-api-fs.md` §4.2/§5 공통).

### 3.2 Create (생성)

```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/kubernetes/namespace-quotas" \
  -d '{
    "requester_id": "cocoa.song",
    "payload": {
      "cluster_name": "cluster-a",
      "namespace_name": "team-alpha",
      "quota": {"requests_storage_bytes": 107374182400, "pvc_count": 50},
      "storage_class_quotas": [
        {"storage_name": "longhorn-a", "requests_storage_bytes": 53687091200, "pvc_count": 20},
        {"storage_name": "cephfs-a",   "requests_storage_bytes": 53687091200, "pvc_count": 30}
      ],
      "expires_at": "2027-01-01T00:00:00Z"
    }
  }' | jq '{request_id, status}'
```

**payload 필드:**

| 필드 | 필수 | 설명 |
|---|---|---|
| `cluster_name` | 필수 | 대상 클러스터(kubeconfig key) |
| `namespace_name` | 필수 | 대상 namespace |
| `quota.requests_storage_bytes` | 조건부 | namespace-wide 저장 용량 → `requests.storage`. 값 주면 >0(아니면 `quota_requests_storage_bytes_invalid`). `quota`·`storage_class_quotas` 중 최소 하나로 hard key ≥1 |
| `quota.pvc_count` | 조건부 | namespace-wide PVC 수 → `persistentvolumeclaims`. 값 주면 >0(아니면 `quota_pvc_count_invalid`) |
| `storage_class_quotas[]` | 선택 | StorageClass별 quota 목록. **entry가 2개 이상이면 각 entry에 `requests_storage_bytes`(또는 `capacity_bytes`) 필수** |
| `storage_class_quotas[].storage_name` | 필수(entry) | 등록된 storage mapping 이름(→ SC/cluster derive) |
| `storage_class_quotas[].requests_storage_bytes` / `capacity_bytes` | 위 참고 | SC별 용량 → `<sc>.storageclass.storage.k8s.io/requests.storage` |
| `storage_class_quotas[].pvc_count` | 선택 | SC별 PVC 수 → `<sc>.storageclass.storage.k8s.io/persistentvolumeclaims` |
| `expires_at` | **필수** | 만료일(ISO8601). 생략 시 `Rejected` |
| `resource_type` | 선택 | `user`(기본)/`project`/`system`/`admin` (§3.9) |

> **hard key 최소 1개 규칙**: `quota` 또는 `storage_class_quotas[]` 중 하나로 hard key가 1개 이상이면
> 된다. `quota` 없이 `storage_class_quotas`만 보내도 정상 생성되고, `quota`만(SC 없이)도 가능. 둘 다
> 비어 hard key가 0개면 `kubernetes_quota_hard_key_required`로 `Rejected`. 제공한 `quota` 필드는 >0이어야 한다.

검증/거부(planner) — 괄호는 실제 `reason` 문자열:

- `expires_at` 누락 → `expires_at_required`.
- `storage_class_quotas`가 list 아님 → `storage_class_quotas_must_be_list`; entry `storage_name` 누락 →
  `storage_class_quota_storage_name_missing`; 중복 `storage_name` → `duplicate_storage_name`.
- `quota`/SC 값이 0 이하·비정수 → `quota_*_invalid` / `storage_class_quota_*_invalid`.
- multi-`storage_class_quotas`(2개 이상)인데 entry에 `requests_storage_bytes`/`capacity_bytes` 없음 →
  `storage_class_quota_requests_storage_bytes_required`.
- storage mapping의 `cluster_name`이 요청 `cluster_name`과 다르면 `storage_mapping_cluster_mismatch`.
- `cluster_name` 또는 `namespace_name` 누락 → **HTTP `422`**. 요청 미생성.
- hard key 0개(`quota`·`storage_class_quotas` 모두 비움) → `kubernetes_quota_hard_key_required`.
- 동일 resource(`{cluster}:{namespace}`)가 이미 존재(non-Deleted)하면 create는
  `kubernetes_namespace_quota_resource_already_exists`로 거부(갱신은 PATCH 사용).
  단 `Deleted` 상태면 재생성 허용.

**렌더링되는 `spec.hard` 예시** (위 요청):
```
requests.storage:                                          100Gi
persistentvolumeclaims:                                    50
longhorn.storageclass.storage.k8s.io/requests.storage:     50Gi
longhorn.storageclass.storage.k8s.io/persistentvolumeclaims: 20
cephfs-rwx.storageclass.storage.k8s.io/requests.storage:   50Gi
cephfs-rwx.storageclass.storage.k8s.io/persistentvolumeclaims: 30
```

### 3.3 PATCH (quota / storage_class_quotas / expires_at / resource_type 변경)

```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X PATCH -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/kubernetes/namespace-quotas/cluster-a/team-alpha" \
  -d '{
    "requester_id": "operator",
    "payload": {
      "quota": {"requests_storage_bytes": 214748364800, "pvc_count": 80},
      "storage_class_quotas": [
        {"storage_name": "longhorn-a", "requests_storage_bytes": 107374182400, "pvc_count": 40}
      ]
    }
  }' | jq '{request_id, status}'
```

- **`storage_class_quotas[]`는 full replacement**다 — PATCH에 보낸 목록이 통째로 새 상태가 된다
  (빠진 SC entry의 hard key는 제거됨). 일부만 바꾸려면 유지할 entry까지 모두 포함해 보낸다.
- **decrease guard**: 어떤 hard(`requests.storage`/`persistentvolumeclaims`/각 SC key)를 live
  `status.used` 아래로 낮추려 하면 `Rejected`(데이터 손실 방지). namespace-wide + StorageClass별
  `status.used`를 각각 확인한다.
- `expires_at`/`resource_type`만 단독 변경 가능(ResourceQuota 변화 없이 DB만 갱신).

### 3.4 차단 / 차단 해제 (`:block`)

namespace quota는 `:block` 하나로 차단/해제를 모두 처리한다(filesystem과 달리 별도 `:initialize`
없음). payload의 `"block"`(boolean)으로 방향을 지정한다.

```bash
# 차단 — 모든 hard key를 0으로(현재 hard는 restore_hard로 저장)
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/kubernetes/namespace-quotas/cluster-a/team-alpha:block" \
  -d '{"requester_id": "operator", "payload": {"block": true}}' | jq '{request_id, status}'

# 차단 해제 — block_state.restore_hard로 복원
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/kubernetes/namespace-quotas/cluster-a/team-alpha:block" \
  -d '{"requester_id": "operator", "payload": {"block": false}}' | jq '{request_id, status}'
```

- `block: true`는 모든 hard를 `0`으로 만들어 신규 PVC/용량 요청을 막는다(기존 사용량은 유지).
- `block: false`는 `block_state.restore_hard`에 저장된 직전 hard로 복원한다(저장 state 없으면
  `block_restore_state_missing`으로 reject).
- `resource_type`이 `system`/`admin`이면 차단 거부(`resource_type_cannot_be_blocked`).
- blocked 상태에서도 PATCH로 desired hard는 갱신 가능(복원 시 새 값 반영).
- 차단 시 hard가 `0`으로 바뀌고 `block_state.blocked=true` + **DB lifecycle `status`가 `Blocked`로 설정**
  된다. 차단 해제 시 `Succeeded`로 복귀. manual `:block`·expiration-sweep 경로 모두 일관
  (`:block` 후 `GET …/namespace-quotas/{c}/{ns}`의 `db.status`=`Blocked`).

### 3.5 삭제 (DMS ResourceQuota 제거)

```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X DELETE -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/kubernetes/namespace-quotas/cluster-a/team-alpha" \
  -d '{"requester_id": "operator", "payload": {}}' | jq '{request_id, status}'
```

- DMS `dms-storage-quota` ResourceQuota 오브젝트만 삭제한다. **namespace, PVC, non-DMS
  ResourceQuota는 보존**한다(DMS lifecycle delete ≠ namespace delete).

### 3.6 Consistency Check (`:check`)

DB `desired_state`(hard 키 set)와 live `ResourceQuota.spec.hard` + **metadata**를 대조한다.
side-effect 없음. drift는 `issues[]`로 보고.

```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/kubernetes/namespace-quotas/cluster-a/team-alpha:check" \
  -d '{"requester_id": "operator", "payload": {}}' | jq '{request_id, status}'
```

검사 대상:

| 항목 | drift 시 issue_type |
|---|---|
| hard 키별 값(`requests.storage`/`persistentvolumeclaims`/각 SC key) | `kubernetes_quota_drifted` |
| ResourceQuota 부재 | `kubernetes_quota_missing` |
| `metadata.labels.dms.io/resource-kind` 불일치 | `kubernetes_quota_metadata_drift` |
| `metadata.annotations.dms.io/resource-key` 불일치 | `kubernetes_quota_metadata_drift` |
| namespace 내 **non-DMS ResourceQuota** 존재(effective quota 영향) | `kubernetes_effective_quota_warning` |

> effective quota 경고: namespace에 DMS 외 다른 ResourceQuota가 있으면 실제 유효 quota는 모든
> RQ의 교집합(가장 엄격한 값)이 된다. DMS는 그 RQ를 변경하지 않고 경고만 남긴다.

### 3.7 Sync Live State (`:sync`)

live `ResourceQuota.spec.hard`를 읽어 DB `desired_state`(`quota` + 각 `storage_class_quotas[]`)로
**역산**해 맞춘다. live 오브젝트는 변경하지 않는다.

```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/kubernetes/namespace-quotas/cluster-a/team-alpha:sync" \
  -d '{"requester_id": "operator", "payload": {}}' | jq '{request_id, status}'
```

- `requests.storage`/`persistentvolumeclaims` → `quota`로, `<sc>.storageclass.storage.k8s.io/*`
  키 → 해당 `storage_class_quotas[]` entry로 역매핑한다(SC 이름 → storage mapping `storage_name`).

### 3.8 Import (`:import`) — DMS-managed ResourceQuota (재)채택

`:import`은 **이미 DMS-managed 라벨이 붙은** `dms-storage-quota` ResourceQuota를 DMS **DB 관리로
(재)채택**한다. live `spec.hard`만 읽어 DB desired에 반영하는 **DB-only** 동작이다(ResourceQuota
오브젝트 자체는 변경하지 않음 — `backend_side_effect:false`).

> **지원 범위 — DMS-managed RQ만.** 현재 구현은 **외부(비-DMS) ResourceQuota를 채택하지 않는다.**
> live RQ가 DMS 마커를 갖추고 있지 않으면 채택을 거부한다(아래 ⚠️). 주 용도는 "DMS가 만든 RQ는
> 그대로 있는데 DB row만 없거나 `Deleted`인 경우(예: DB 복구·재구축) → live RQ를 DB로 재채택". 새
> namespace에 quota를 도입하려면 `:import`가 아니라 create(§3.2)를 쓴다.

**채택 전제조건 — live RQ가 반드시 가져야 하는 것:**

| 항목 | 값 | 불일치 시 |
|---|---|---|
| `metadata.name` | `dms-storage-quota` | `unexpected ResourceQuota name` / payload 이름 지정 시 `kubernetes_resource_quota_name_unsupported` |
| label `app.kubernetes.io/managed-by` | `dms` | `refusing to mutate non-DMS ResourceQuota` |
| label/annotation `dms.io/resource-kind` | `kubernetes-namespace-quota` | `refusing to mutate ResourceQuota with invalid DMS resource kind` |
| annotation `dms.io/resource-key` | `<cluster>:<namespace>` (요청과 일치) | `refusing to mutate ResourceQuota for different DMS resource key` |
| DB resource | 없음 또는 `Deleted` | non-Deleted면 `kubernetes_namespace_quota_resource_already_exists` |

```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/kubernetes/namespace-quotas/cluster-a/team-beta:import" \
  -d '{
    "requester_id": "operator",
    "payload": {
      "expires_at": "2099-01-01T00:00:00Z",
      "storage_class_quotas": [{"storage_name": "longhorn-a"}]
    }
  }' | jq '{request_id, status}'
```

- live RQ가 없으면 실패(`ResourceQuota does not exist`).
- 채택 후 PATCH/check/sync/block 대상이 된다(full-managed). SC 키(`<sc>.storageclass.storage.k8s.io/*`)가
  있으면 `storage_class_quotas` 힌트로 역매핑하고, 힌트가 없으면 `storage_mapping_candidates`로 추론한다
  (모든 SC 키를 매핑하지 못하면 실패).
- **외부(비-DMS) RQ 시도 시 동작:** DMS 마커가 없는 RQ를 import하면 `refusing to mutate non-DMS
  ResourceQuota`로 거부되며, **부작용 없는 precondition 실패로 `BackendApplyFailed`**(error_category
  `backend_precondition`, `backend_side_effect:false`, issue_type `kubernetes_quota_import_preflight_failed`)로
  깔끔히 종료된다. 실패 기록은 action-required에 남으므로 필요 시 `:resolve abandon`으로 정리.

> **동작 요약:** DMS-라벨 `dms-storage-quota`(DB 미추적)를 import하면 `Succeeded`, diff `Consistent`.
> 채택 후 PATCH로 live hard를 갱신할 수 있고(full-managed), SC 키 포함 RQ도 `storage_class_quotas`
> 힌트로 역매핑해 채택한다. 라벨 없는 RQ는 거부된다(위 ⚠️).

### 3.9 On-demand Audit (`:audit`)

여러 namespace의 DMS-managed quota를 **read-only**로 한 번에 점검한다(Kubernetes 변경 없음).
`scope`로 범위를 지정한다 — 단일 namespace(`cluster_name`+`namespace_name`) 또는 부분 scope
(`cluster_name`만 / `resource_type`만). ⚠️ **`scope`를 완전히 비우면(`payload:{}`) `audit_scope_required`로
`Rejected`된다 — scope는 필수**.

```bash
# 단일 namespace
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/kubernetes/namespace-quotas:audit" \
  -d '{"requester_id":"operator","payload":{"scope":{"cluster_name":"cluster-a","namespace_name":"team-alpha"}}}' | jq

# 광범위(부분 scope) — cluster_name 또는 resource_type만으로 해당 범위 전체 audit
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/kubernetes/namespace-quotas:audit" \
  -d '{"requester_id":"operator","payload":{"scope":{"cluster_name":"ddz26"}}}' | jq
```

- DB desired ↔ live `spec.hard` drift, metadata drift(`dms.io/resource-kind` label /
  `dms.io/resource-key` annotation)를 구조화해 result에 담는다.
- 결과는 quota action-required aggregation(최신 audit/check 기반)에 반영된다.

### 3.10 만료 sweep (`:expiration-sweep`)

만료된 namespace quota를 일괄 차단한다(filesystem sweep과 동일 패턴).

```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/kubernetes/namespace-quotas:expiration-sweep" \
  -d '{"requester_id":"sweeper","payload":{"scope":{"resource_type":"user"},"dry_run":true}}' | jq
```

- `dry_run:true`는 대상/스킵 사유만 보고(side-effect 없음). 실제 실행은 만료 + 차단 가능한
  (`user`/`project`) resource를 `block`한다. `system`/`admin`은 자동 차단 제외.
- `scope.cluster_name`/`scope.resource_type`/`expired_before`로 범위를 좁힐 수 있다.

### 3.11 resource_type / default reset

- `resource_type`(`user`/`project`/`system`/`admin`)은 filesystem과 동일하게 만료 sweep/`:block`
  보호 정책에 영향을 준다(`system`/`admin`은 자동/명시 차단 거부). create/PATCH로 지정·변경.
- `reset_quota_to_default: true`(PATCH/create)는 등록된 default quota policy 값으로 hard를 재설정한다
  (default policy는 `POST /api/v1/resource-management/default-quota-policies`로 등록; 정책 미존재 시
  관련 검증에서 reject).

default quota policy 등록(설정) 예 — `resource_kind`+`resource_type` 조합당 1개:

```bash
curl -sS "${DMS_CURL_OPTS[@]}" -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/default-quota-policies" \
  -d '{
    "resource_kind": "kubernetes_namespace_quota",
    "resource_type": "user",
    "quota": {
      "requests_storage_bytes": 107374182400,
      "pvc_count": 20,
      "storage_class_quotas": [
        {"storage_name": "ceph-rbd-ddz26", "requests_storage_bytes": 53687091200, "pvc_count": 10}
      ]
    }
  }' | jq '{policy_id, status}'
```

> policy의 `storage_class_quotas[].storage_name`도 등록된 storage mapping이어야 하고, 그 mapping의
> `cluster_name`이 reset 대상 quota의 `cluster_name`과 일치해야 한다.

## 4. 결과 조회 (Operations API)

모든 mutating 호출은 `202 {request_id, status: "Persisted"}`만 돌려준다(§3.1). 적용 결과는
**(4.1) 요청 단위 진행/결과**와 **(4.2) namespace quota 리소스 상태(DB↔live)**로 조회한다.

### 4.1 요청 결과 폴링

```bash
source /mgmt_storage/cocoa.song/.dms-secrets/dms-env.sh

# 요청 단건: 상태 + 전이 이력 + 결과 요약
curl -sS "${DMS_CURL_OPTS[@]}" "$DMS_API_URL/api/v1/operations/requests/<request_id>" | jq

# requester별 최근 요청 목록 (since/until 지원)
curl -sS "${DMS_CURL_OPTS[@]}" \
  "$DMS_API_URL/api/v1/operations/requests?requester_id=cocoa.song" | jq
```

`status`가 terminal에 도달할 때까지 폴링한다 — 성공 `Succeeded`, 거부 `Rejected`, backend 실패
`BackendApplyFailed` / `UnknownAfterSideEffect`(후자는 부작용 불확실 → `…/requests/{id}:resolve`로
수동 처리, [`2.dms-rm-api-fs.md`](2.dms-rm-api-fs.md) §5).

```bash
# 간단 폴링 루프
REQ=<request_id>
until curl -sS "${DMS_CURL_OPTS[@]}" "$DMS_API_URL/api/v1/operations/requests/$REQ" \
  | jq -e '([.request.status] | inside(["Succeeded","Failed","Rejected","Conflict","BackendApplyFailed","UnknownAfterSideEffect"]))' >/dev/null
do sleep 2; done
curl -sS "${DMS_CURL_OPTS[@]}" "$DMS_API_URL/api/v1/operations/requests/$REQ" | jq '.request.status'
```

### 4.2 namespace quota 상태 조회 (DB desired + live + diff)

```bash
# 단건 조회 (DB desired_hard + live spec.hard + diff + effective warning)
curl -sS "${DMS_CURL_OPTS[@]}" \
  "$DMS_API_URL/api/v1/operations/kubernetes/namespace-quotas/ddz26/team-alpha" | jq

# 만료된 / 7일 내 만료 예정 목록
curl -sS "${DMS_CURL_OPTS[@]}" \
  "$DMS_API_URL/api/v1/operations/kubernetes/namespace-quotas/expiring?status=expired" | jq
curl -sS "${DMS_CURL_OPTS[@]}" \
  "$DMS_API_URL/api/v1/operations/kubernetes/namespace-quotas/expiring?status=expiring&within_seconds=604800" | jq
```

단건 응답 형태(요약):

```json
{
  "db":   { "status": "Succeeded", "desired_hard": { "requests.storage": "100Gi", "...": "..." } },
  "live": { "exists": true, "spec_hard": { "requests.storage": "100Gi", "...": "..." }, "status_used": { "...": "..." } },
  "diff": { "status": "Consistent", "issues": [] }
}
```

- `source=both|db|live`, `include_non_dms=true`(namespace 내 non-DMS RQ 목록), `include_status_used=true`
  (현재 사용량)으로 범위를 조절한다.
- `diff.status`: `Consistent` / `Drifted`(`issues[]`에 키별 차이) / `Missing`(live 없음) 등.
- `/namespace-quotas/expiring` 쿼리 파라미터는 filesystem의 `/filesystems/expiring`과 동일하다
  (`status`, `cluster_name`, `within_seconds`, `before`, `include_blocked`, `limit`).

## 5. 주의 / FAQ

- **namespace는 사전에 존재해야 한다.** DMS는 ResourceQuota만 만들고 namespace는 만들지/지우지 않는다.
- **effective quota**: namespace에 non-DMS ResourceQuota가 있으면 실제 한도는 모든 RQ의 가장 엄격한
  값이다. DMS는 그것을 변경하지 않고 경고만 남긴다(§3.6).
- **decrease guard**로 live `status.used` 아래로는 못 낮춘다 — 먼저 사용량을 줄이거나 PVC를 정리한다.
- **cross-cluster**: `storage_class_quotas[].storage_name`이 가리키는 mapping의 `cluster_name`이
  요청 `cluster_name`과 다르면 reject(한 quota는 한 클러스터/namespace에만 적용).
- filesystem RM과 달리 **LDAP/owner/group 개념이 없다**(quota는 namespace 단위 k8s 오브젝트).
- **agentless**: 대상 클러스터에 DMS agent가 없어도 된다(§2.2). 사전 조건은 ① 클러스터 등록(§2.1)과
  ② storage mapping의 sanity가 `Failed`가 아닐 것뿐이다. RM agent가 없어 mapping이 `Degraded`여도 사용 가능.

## 6. 전체 흐름 예 (ddz26 Ceph CSI)

control plane은 `dms` 클러스터, 대상은 CSI StorageClass(`ceph-rbd`/`ceph-cephfs`)를 가진 `ddz26`.

```bash
source /mgmt_storage/cocoa.song/.dms-secrets/dms-env.sh

# 1) 대상 클러스터 ddz26 등록 (§2.1: RBAC + SA kubeconfig + Secret/ConfigMap + 재시작) — 위 명령 참조
#    확인: inventory에 ddz26의 storage_classes/csi_drivers가 보여야 함

# 2) Ceph CSI storage mapping 등록 (§2.2) — sanity Degraded(agentless) = 정상

# 3) 대상 namespace는 미리 생성 (DMS는 ResourceQuota만 관리)
kubectl --context ddz26 create namespace dms-csi-validation

# 4) namespace quota 생성 (ceph-rbd + ceph-cephfs 동시 사용)
REQ=$(curl -sS "${DMS_CURL_OPTS[@]}" -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/kubernetes/namespace-quotas" \
  -d '{
    "requester_id": "cocoa.song",
    "payload": {
      "cluster_name": "ddz26",
      "namespace_name": "dms-csi-validation",
      "quota": {"requests_storage_bytes": 107374182400, "pvc_count": 20},
      "storage_class_quotas": [
        {"storage_name": "ceph-rbd-ddz26",    "requests_storage_bytes": 53687091200, "pvc_count": 10},
        {"storage_name": "ceph-cephfs-ddz26", "requests_storage_bytes": 53687091200, "pvc_count": 10}
      ],
      "expires_at": "2027-01-01T00:00:00Z"
    }
  }' | jq -r '.request_id')

# 5) 결과 폴링 (§4.1) → Succeeded
curl -sS "${DMS_CURL_OPTS[@]}" "$DMS_API_URL/api/v1/operations/requests/$REQ" | jq '.request.status'

# 6) 상태 조회 (§4.2) → diff Consistent
curl -sS "${DMS_CURL_OPTS[@]}" \
  "$DMS_API_URL/api/v1/operations/kubernetes/namespace-quotas/ddz26/dms-csi-validation" \
  | jq '{db: .db.status, diff: .diff.status, live_hard: .live.spec_hard}'

# 7) (참고) 대상 클러스터에서 직접 확인
kubectl --context ddz26 -n dms-csi-validation get resourcequota dms-storage-quota -o jsonpath='{.spec.hard}'
```

위 4)의 요청이 생성하는 live `spec.hard`:

```
requests.storage:                                              100Gi
persistentvolumeclaims:                                        20
ceph-rbd.storageclass.storage.k8s.io/requests.storage:         50Gi
ceph-rbd.storageclass.storage.k8s.io/persistentvolumeclaims:   10
ceph-cephfs.storageclass.storage.k8s.io/requests.storage:      50Gi
ceph-cephfs.storageclass.storage.k8s.io/persistentvolumeclaims: 10
```

라벨 `app.kubernetes.io/managed-by: dms`, `dms.io/resource-kind: kubernetes-namespace-quota` /
어노테이션 `dms.io/resource-key: ddz26:dms-csi-validation`,
`dms.io/storage-names: ceph-rbd-ddz26,ceph-cephfs-ddz26`가 함께 부여된다.
