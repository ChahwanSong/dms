# DMS 기본 설치 (base install)

> **먼저 [`0.prerequisites.md`](0.prerequisites.md)** 로 클러스터 사전 준비(Volcano, Queue/PriorityClass,
> PodSecurity=privileged, 공유 artifact FS, 노드 신원 해석, 스토리지 host-mount)를 끝낸 뒤 이 문서로 진행한다.
>
> Filesystem Resource Management API, Operations 조회 API, LDAP 설정, GPFS 환경 설정은
> [`2.dms-rm-api-fs.md`](2.dms-rm-api-fs.md), Kubernetes namespace quota API는
> [`3.dms-rm-api-k8s.md`](3.dms-rm-api-k8s.md), 데이터 잡(DM: scan/sync/rm)은
> [`4.dms-dm-api.md`](4.dms-dm-api.md)를 참조한다.

이 문서는 예시 클러스터 `cluster-a`(노드 `node1~node6`)에 DMS control plane을 설치하는 전체 과정을

### 1.4 connection pool 과 `max_connections` 사이징

DMS 프로세스는 PostgreSQL connection 을 **프로세스당 1개의 bounded pool**(URL 단위)로
관리한다(`src/dms/db.py`). pool 은 connection 단위로 `statement_timeout`(기본 30s)과
`idle_in_transaction_session_timeout`(기본 60s)을 설정하여, runaway 쿼리나 누수된 열린
트랜잭션이 backend 를 무한 점유해 `max_connections` 를 고갈시키는(=API 다운) 사고를 막는다.

**사이징 공식**

```
서버 전체 PG connection ≈ (#프로세스) × (op_max_size + obs_max_size)
```

기본값(`DMS_DB_POOL_MAX_SIZE=8`, `DMS_DB_OBSERVABILITY_POOL_MAX_SIZE=3` → 합 11)과 핵심
프로세스 수 ≈ `api×2 + planner + rm-worker + dm-worker + sanity-reconciler ≈ 6`(+ 일시적인
migrate Job) 기준:

```
6 × 11 = 66  (migrate Job + superuser_reserved_connections 여유 포함해도 < 100)
```

→ stock `postgres:16-alpine` 의 기본 `max_connections=100` 아래에 안전하게 머문다.

**100+ 노드로 확장할 때**: pool 크기와 `max_connections` 를 **반드시 함께** 올린다. 예를
들어 dm-worker/rm-worker 를 늘리거나 `DMS_DB_POOL_MAX_SIZE` 를 키우면, StatefulSet 의
postgres 컨테이너 args 에 다음을 추가해 `max_connections` 를 함께 상향한다.

```yaml
# StatefulSet/dms-postgres 의 컨테이너 spec
args: ["-c", "max_connections=300"]
```

상향 후 다시 위 공식으로 `(#프로세스) × (op_max_size + obs_max_size) < max_connections -
superuser_reserved_connections(기본 3)` 를 검산한다.

## 4. mTLS 인증서 및 API token

모든 인증서는 `/opt/dms-secrets/certs/`에 저장된다. 재설치 시 아래 명령으로 재생성한다.

```bash
CERTS=/opt/dms-secrets/certs
mkdir -p $CERTS

# Client CA (ingress mTLS 검증용)
openssl req -x509 -newkey rsa:4096 -nodes -days 3650 \
  -keyout /opt/dms-secrets/certs/dms-client-ca.key \
  -out /opt/dms-secrets/certs/dms-client-ca.crt \
  -subj "/CN=dms-client-ca/O=cluster-a"

# Server CA + server cert (dms.cluster-a.local)
openssl req -x509 -newkey rsa:4096 -nodes -days 3650 \
  -keyout /opt/dms-secrets/certs/dms-server-ca.key \
  -out /opt/dms-secrets/certs/dms-server-ca.crt \
  -subj "/CN=dms-server-ca/O=cluster-a"

openssl req -newkey rsa:2048 -nodes \
  -keyout /opt/dms-secrets/certs/dms-api-server.key \
  -out /opt/dms-secrets/certs/dms-api-server.csr \
  -subj "/CN=dms.cluster-a.local/O=cluster-a"

echo "subjectAltName=DNS:dms.cluster-a.local" > /opt/dms-secrets/certs/san.ext
openssl x509 -req -days 3650 \
  -in /opt/dms-secrets/certs/dms-api-server.csr \
  -CA /opt/dms-secrets/certs/dms-server-ca.crt \
  -CAkey /opt/dms-secrets/certs/dms-server-ca.key \
  -CAcreateserial -extfile /opt/dms-secrets/certs/san.ext \
  -out /opt/dms-secrets/certs/dms-api-server.crt

# Operator client cert
openssl req -newkey rsa:2048 -nodes \
  -keyout /opt/dms-secrets/certs/operator.key \
  -out /opt/dms-secrets/certs/operator.csr \
  -subj "/CN=operator/O=cluster-a"

openssl x509 -req -days 3650 \
  -in /opt/dms-secrets/certs/operator.csr \
  -CA /opt/dms-secrets/certs/dms-client-ca.crt \
  -CAkey /opt/dms-secrets/certs/dms-client-ca.key \
  -CAcreateserial \
  -out /opt/dms-secrets/certs/operator.crt
```

| 파일 | 용도 |
|---|---|
| `dms-client-ca.crt` | ingress mTLS client 검증 CA (`dms-client-ca` Secret) |
| `dms-server-ca.crt` | curl `--cacert`용 server CA |
| `dms-api-server.crt/key` | ingress TLS server cert (`dms-api-tls` Secret) |
| `operator.crt/key` | DMS API 호출용 operator client cert |

**API token**: `CHANGE_ME`

## 5. SSH backend credential

RM Worker가 CephFS quota 명령(`setfattr`/`getfattr`)을 노드의 root 계정으로 실행한다.

```bash
# build-host에서 key 생성
ssh build-host 'ssh-keygen -t ed25519 -f /opt/dms-secrets/dms-backend-ssh -C dms-rm-worker -N ""'

# 모든 노드 root 계정에 등록
for node in node1 node2 node3 node4 node5 node6; do
  PUBKEY=$(ssh build-host 'cat /opt/dms-secrets/dms-backend-ssh.pub')
  ssh $node "sudo mkdir -p /root/.ssh && echo '$PUBKEY' | sudo tee -a /root/.ssh/authorized_keys > /dev/null && sudo chmod 600 /root/.ssh/authorized_keys"
done

# known_hosts 수집
ssh build-host 'ssh-keyscan -H node1 node2 node3 node4 node5 node6 > /opt/dms-secrets/dms-known_hosts'
```

private key, known_hosts, SSH config는 `dms-ssh-client` Secret에 포함된다.

> **노드 SSSD 사전 설정**: RM이 만든 `dms-grp-*` 그룹 멤버십이 전 노드에서 제때
> 보이도록, 모든 노드 SSSD의 `entry_cache_timeout`을 60초로 낮춰야 한다(기본 90분).
> 절차/근거는 [`2.dms-rm-api-fs.md`](2.dms-rm-api-fs.md) §2.5 참조.

## 7. DMS control plane 배포

### 7.0 클러스터 사전 준비 (Volcano · Queue/PriorityClass · PSA)

세부 절차·근거는 [`0.prerequisites.md`](0.prerequisites.md). control-plane을 올리기 전에 최소한
아래가 갖춰져 있어야 한다(특히 DM 잡을 쓰려면 필수):

- **Volcano 설치** — DM 잡의 gang-scheduler이자 DMS가 쓰는 네이티브 잡 타입(`batch.volcano.sh`
  Job)·`Queue`·`PodGroup` CRD 제공. **하드 필수.** (Kubeflow MPI Operator는 **필요 없다** —
  `DMS_DM_SCHEDULER_BACKEND=volcano-job`으로 Volcano Job만 사용한다.)
- **Queue `dms-data` + PriorityClass `dms-low/normal/high`** — control-plane의 DM 잡이 이름으로
  참조하므로(`DMS_DM_POLICY_DEFAULT_QUEUE`/`DMS_DM_POLICY_DEFAULT_PRIORITY_CLASS`), 큐가 없으면 잡이
  **영구 Pending**, PriorityClass가 없으면 파드가 **admission에서 거부**된다. 별도 매니페스트로 제공한다:

  ```bash
  ssh node1 'kubectl apply -f /opt/dms/install/kubernetes/volcano-queue-priorityclasses.yaml'
  ssh node1 'kubectl get queue.scheduling.volcano.sh dms-data'   # STATE=Open
  ssh node1 'kubectl get priorityclass | grep dms'               # dms-low(50)/dms-normal(100)/dms-high(200)
  ```

- **PodSecurity** — DM 잡 파드는 root로 기동 후 `runuser`로 강하하므로 privileged가 필요하다.
  `dms` 네임스페이스의 `pod-security.kubernetes.io/enforce=privileged` 라벨은 `control-plane.yaml`에
  이미 포함되어 §7.3에서 함께 적용된다. DM 잡을 다른 네임스페이스에서 돌리면 그 네임스페이스에도
  동일 라벨을 붙인다.

## 9. Storage mapping 등록

Storage mapping은 DMS API로 직접 등록한다. DB가 source of truth이며 별도 파일을 유지하지 않는다. 현재 등록된 목록은 언제든 `GET /api/v1/operations/storage-mappings`로 조회할 수 있다.

```bash
source /opt/dms-secrets/dms-env.sh

# cephfs-cluster-a
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/storage-mappings" \
  -d '{
    "storage_name": "cephfs-cluster-a",
    "backend_template": {
      "backend_type": "cephfs",
      "cluster_name": "cluster-a",
      "mount_path": "/cephfs",
      "managed_root": "/cephfs/root",
      "rm_worker_nodes": ["node1","node2","node3","node4","node5","node6"],
      "ssh_host": "node1",
      "csi_driver": "rook-ceph.cephfs.csi.ceph.com"
    },
    "cluster_name": "cluster-a",
    "storage_class_name": "rook-cephfs"
  }' | jq '{storage_name, status}'

# gpfs-cluster-a
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/storage-mappings" \
  -d '{
    "storage_name": "gpfs-cluster-a",
    "backend_template": {
      "backend_type": "gpfs",
      "cluster_name": "cluster-a",
      "filesystem_name": "gpfs0",
      "mount_path": "/gpfs",
      "managed_root": "/gpfs/dms",
      "rm_worker_nodes": ["node4","node5","node6"]
    },
    "cluster_name": "cluster-a"
  }' | jq '{storage_name, status}'

# weka-cluster-a
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/storage-mappings" \
  -d '{
    "storage_name": "weka-cluster-a",
    "backend_template": {
      "backend_type": "wekafs",
      "cluster_name": "cluster-a",
      "filesystem_name": "weka0",
      "mount_path": "/weka",
      "managed_root": "/weka/dms",
      "rm_worker_nodes": ["node2","node3"]
    },
    "cluster_name": "cluster-a"
  }' | jq '{storage_name, status}'
```

> **WEKA 백엔드 주의사항:**
> - `weka fs quota set/list/reset` CLI는 cluster 인증 필요 (`weka user login` 또는 `WEKA_USERNAME`/`WEKA_PASSWORD`/`WEKA_ORG` 환경변수). 인증 안 된 RM worker에서 quota 작업 시 `BackendPreconditionError: WekaFS quota CLI not authenticated` 발생.
> - WEKA path quota는 capacity_bytes만 지원. `file_count`(inode quota) 미지원 — 지정 시 backend가 명시적으로 거절.
> - WEKA CSI 드라이버(`csi.weka.io`)는 현재 cluster-a 클러스터에 미설치. CSI 매핑 자체는 코드에 등록되어 향후 검증 가능.

등록 후 sanity check 결과:

## 10. Agent DaemonSet 배포

파일: `/opt/dms-secrets/dms-agent-daemonset.yaml` (backup: `.dms-secrets/dms-agent-daemonset.yaml`)

### 10.1 주요 설정값

| 키 | 값 |
|---|---|

| `DMS_AGENT_CLUSTER_NAME` | `cluster-a` |

| `DMS_AGENT_HOST_ROOT` | `/host` (호스트 root bind-mount — 디스크 metrics) |
| storage | `cephfs-cluster-a`, mount_paths: `[/cephfs]` |
| image | `registry.example.internal/dms:CHANGE_ME` |

### 10.2 트러블슈팅 및 수정사항

**1) control-plane 노드(node1) toleration 추가**
DaemonSet에 control-plane NoSchedule taint toleration이 없어 node1에 pod가 미배포됨.
```bash
kubectl -n dms patch daemonset dms-rm-agent --type=json -p '[{"op":"add","path":"/spec/template/spec/tolerations","value":[{"key":"node-role.kubernetes.io/control-plane","operator":"Exists","effect":"NoSchedule"}]}]'
```

**2) Agent API URL 변경**
agent가 `dms.cluster-a.local`을 DNS 조회할 수 없음 (pod 내부에서 /etc/hosts 미참조).<br>
`DMS_AGENT_API_URL`을 cluster-internal Service URL로 변경:
```bash
kubectl -n dms set env daemonset/dms-rm-agent DMS_AGENT_API_URL=http://dms-api.dms.svc.cluster.local:80
```

**3) mTLS 헤더 비활성화**
Agent는 ingress를 우회해 직접 API에 접근하므로 mTLS 헤더를 제공할 수 없음.<br>
`DMS_REQUIRE_MTLS_HEADER=false`, `DMS_REQUIRE_MTLS_VERIFIED_HEADER=false`로 변경.<br>
내부 보안은 NetworkPolicy + Bearer token으로 유지.
```bash
kubectl -n dms patch configmap dms-runtime-config --type=merge -p '{"data":{"DMS_REQUIRE_MTLS_HEADER":"false","DMS_REQUIRE_MTLS_VERIFIED_HEADER":"false"}}'
kubectl -n dms rollout restart deployment/dms-api
```

**4) NetworkPolicy 추가**
agent → dms-api(port 8080) 직접 접근을 허용하는 NetworkPolicy 추가:
```bash
kubectl -n dms apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: dms-api-from-agent
  namespace: dms
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: dms-api
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app.kubernetes.io/name: dms-rm-agent
      ports:
        - protocol: TCP
          port: 8080
EOF
```

**5) 마운트 readiness — 호스트 mountinfo bind-mount (필수)**
Agent는 컨테이너에서 돌아 기본 `DMS_AGENT_MOUNTINFO_PATH=/proc/self/mountinfo`(컨테이너 자신의
마운트)로는 워커 노드의 스토리지 마운트가 안 보인다. 그러면 **모든 storage가 Missing**으로 나오고
`resource_management`/`data_management` readiness가 **false**가 된다(증상: 대시보드 마운트 매트릭스
전부 ✗). `agent-daemonset.yaml`에 호스트 mount table을 bind-mount하고 그 경로를 가리켜야 한다
(`install/kubernetes/agent-daemonset.yaml`에 반영됨). 기존 배포에 인라인 패치하려면:

```bash
# ConfigMap: 호스트 mountinfo 경로 + 호스트 root 지정
kubectl -n dms patch configmap dms-agent-runtime-config --type=merge \
  -p '{"data":{"DMS_AGENT_MOUNTINFO_PATH":"/host/proc/1/mountinfo","DMS_AGENT_HOST_ROOT":"/host"}}'

# 두 DaemonSet에 호스트 root + proc mountinfo bind-mount 추가 (rm, dm 각각)
for ds in dms-rm-agent dms-dm-agent; do
  kubectl -n dms patch daemonset "$ds" --type=json -p '[
    {"op":"add","path":"/spec/template/spec/volumes/-","value":{"name":"host-root","hostPath":{"path":"/","type":"Directory"}}},
    {"op":"add","path":"/spec/template/spec/volumes/-","value":{"name":"proc-mountinfo","hostPath":{"path":"/proc/1/mountinfo","type":"File"}}},
    {"op":"add","path":"/spec/template/spec/containers/0/volumeMounts/-","value":{"name":"host-root","mountPath":"/host","readOnly":true}},
    {"op":"add","path":"/spec/template/spec/containers/0/volumeMounts/-","value":{"name":"proc-mountinfo","mountPath":"/host/proc/1/mountinfo","readOnly":true}}
  ]'
done
kubectl -n dms rollout status daemonset/dms-rm-agent daemonset/dms-dm-agent --timeout=180s
```

> `/proc`는 별도 마운트라 `host-root`(호스트 `/`) 아래로 안 딸려온다 → `proc-mountinfo`로
> `/proc/1/mountinfo`를 **따로** bind-mount해야 한다. per-storage hostPath를 개별 마운트하던 우회를
> 쓰고 있었다면 그 우회 볼륨/마운트를 제거하고 이 공식 방법으로 대체한다.
>
> 검증(Missing→Ready 전환 확인):
> ```bash
> POD=$(kubectl -n dms get pods -l app.kubernetes.io/name=dms-dm-agent -o jsonpath='{.items[0].metadata.name}')
> kubectl -n dms exec "$POD" -- dms agent-probe --once | jq '.mounts[] | {storage_name,status}'
> ```
> 노드에 실제 마운트된 storage만 `Ready`, 나머지는 `Missing`이면 정상.

### 10.3 API 인증 주의사항

## 12. 신원(Identity) 처리

**사전 등록은 필요 없다.** DM은 preflight 단계에서 LDAP을 직접(read-only) 조회해
요청자의 POSIX 신원(uid/gid/groups)을 확인한다. 별도의 mapping 테이블·등록 API·캐시는 없다.

동작하려면 다음 두 가지만 충족하면 된다:

- **(a) `DMS_LDAP_*` 환경변수 설정** — `DMS_LDAP_URI`, `DMS_LDAP_BASE_DN`, `DMS_LDAP_BIND_DN`,
  `DMS_LDAP_BIND_PASSWORD`, `DMS_LDAP_USER_SEARCH_BASE`, `DMS_LDAP_GROUP_SEARCH_BASE`,
  `DMS_LDAP_USER_FILTER`(기본 `(uid={username})`), `DMS_LDAP_TIMEOUT_SECONDS`. 제공자 라벨은
  `DMS_DM_IDENTITY_PROVIDER`(기본 `ldap`). 주요 값은 §7.1 ConfigMap 참고. RM이 쓰는 디렉터리와 동일.
- **(b) DM 잡 노드가 요청자 계정을 OS 레벨에서 해석**할 수 있을 것 — 잡은 요청자 uid/gid로
  실행되므로 각 DM 잡 노드가 **NSS/SSSD(또는 동등한 디렉터리 연동)** 로 요청자 계정을 `getpwnam`으로
  해석해야 한다(안 되면 `identity_not_ready_on_node` 또는 chown 실패). 상세는
  [`0.prerequisites.md`](0.prerequisites.md) §0.6.

요청 필드 `owner_username`은 RM의 파일시스템 owner 모델을 그대로 따른다. `requester_id`는
자유 형식 논리 id이며 `owner_username`의 기본값이다. 요청이 실제 POSIX 신원을 `owner_username`으로
override 할 수 있고, LDAP 조회는 `owner_username`을 사용한다.

### 12.1 개별 사용자 신원 확인 (LDAP 직접 조회)

특정 사용자의 uid/gid를 확인하려면 DM API가 아니라 LDAP을 직접 조회한다:

```bash
ldapsearch -x -H ldap://ldap.example.internal:389 \
  -D 'cn=dms,ou=service-accounts,dc=example,dc=internal' \
  -w 'CHANGE_ME' \
  -b 'ou=people,dc=example,dc=internal' \
  '(uid=alice)' uid uidNumber gidNumber
```

### 12.2 preflight 실패 사유 (fail-closed, 캐시 없음)

LDAP 조회가 실패하면 DM은 stale 신원을 제공하지 않고 작업을 중단한다(명확한 에러로 종료):

| 상황 | preflight reason |
|---|---|
| LDAP 미설정 | `ldap_not_configured` |
| LDAP 접속 불가 | `ldap_unavailable` |
| 사용자 미존재 | `ldap_identity_not_found` |
| denylist 차단 | `identity_denied` |

### 12.3 신원 차단 (denylist kill-switch)

유일하게 DM 측에 영속되는 신원 상태는 denylist다. 기본값은 비어 있어 모두 허용하며,
특정 requester/owner/group을 즉시 차단(admission block + kill-switch)할 때만 등록한다.

```bash
source /opt/dms-secrets/dms-env.sh

# 차단 등록 (subject_type ∈ {requester, owner, group})
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X PUT \
  -H 'content-type: application/json' \
  -d '{"reason":"offboarded"}' \
  "$DMS_API_URL/api/v1/data-management/identity-denylist/owner/alice" | jq

# 차단 해제
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X DELETE \
  "$DMS_API_URL/api/v1/data-management/identity-denylist/owner/alice" | jq

# 현재 차단 목록 조회
curl -sS "${DMS_CURL_OPTS[@]}" \
  "$DMS_API_URL/api/v1/data-management/identity-denylist" | jq
```

대량 시드가 필요하면 `install/scripts/apply-identity-denylist.sh`와
`install/config/identity-denylist.example.json`을 사용한다.

### 13.3 등록 (POST)

**backend_template 필드:**

| 필드 | 필수 | 설명 |
|---|---|---|
| `backend_type` | 필수 | `cephfs`, `gpfs`, `wekafs` 지원 |
| `cluster_name` | 필수 | DMS 클러스터 이름 |
| `mount_path` | 필수 | 각 노드에 마운트된 절대 경로 |
| `managed_root` | 필수 | DMS가 관리하는 루트 디렉터리 (mount_path 하위, **명시 필수** — 생략 시 등록 `422`; 과거의 `mount_path/dms` 암묵 기본값은 제거됨) |
| `filesystem_name` | **gpfs 필수** / wekafs 선택 | WEKA/GPFS filesystem(device) 이름 (예: `weka0`, `gpfs0`). **GPFS는 등록 시 필수** — `mm*`(fileset/quota) 명령 대상이며, 생략 시 등록 `422`(과거의 `storage_name` 암묵 기본값 제거). WEKA는 선택(생략 시 `storage_name`) |
| `rm_worker_nodes` | 권장 | RM 작업 대상 노드 목록. Agent가 이 노드들에서 마운트 증거를 수집해 `rm_readiness` 판단에 사용 |
| `ssh_host` | 선택 | RM Worker가 `setfattr`/`mkdir`/`weka` 등을 실행하기 위해 SSH로 접속할 노드. **생략 시 agent 보고 기반 `rm_candidates` 중 Ready 노드를 자동 선택.** rm_candidates가 없으면 `rm_worker_nodes[0]`으로 fallback |
| `csi_driver` | 선택 | Kubernetes PVC provisioning용 CSI 드라이버. 생략 시 `csi_driver_matches` sanity check 제외. backend_type에 따라 기본값 적용: `cephfs`→`rook-ceph.cephfs.csi.ceph.com`, `gpfs`→`spectrumscale.csi.ibm.com`, `wekafs`→`csi.weka.io` |
| `weka_profile` | 선택 (wekafs) | `weka --profile <name>` 옵션. 멀티 클러스터 환경에서 사용 |

```bash
source /opt/dms-secrets/dms-env.sh

curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/storage-mappings" \
  -d '{
    "storage_name": "cephfs-cluster-a",
    "backend_template": {
      "backend_type": "cephfs",
      "cluster_name": "cluster-a",
      "mount_path": "/cephfs",
      "managed_root": "/cephfs/root",
      "rm_worker_nodes": ["node1","node2","node3","node4","node5","node6"],
      "ssh_host": "node1",
      "csi_driver": "rook-ceph.cephfs.csi.ceph.com"
    },
    "cluster_name": "cluster-a",
    "storage_class_name": "rook-cephfs"
  }' | jq '{storage_name, status}'
```

실제 실행 결과:
```json
{"storage_name": "cephfs-cluster-a", "status": "Degraded"}
```

이미 존재하면 upsert(덮어쓰기)로 동작한다.

### 13.4 수정 (PATCH)

backend_template 필드나 cluster_name, storage_class_name 변경 시 사용한다.

```bash
source /opt/dms-secrets/dms-env.sh

# 예: ssh_host를 명시적으로 node2로 변경
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X PATCH -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/storage-mappings/cephfs-cluster-a" \
  -d '{
    "storage_name": "cephfs-cluster-a",
    "backend_template": {
      "backend_type": "cephfs",
      "cluster_name": "cluster-a",
      "mount_path": "/cephfs",
      "managed_root": "/cephfs/root",
      "rm_worker_nodes": ["node1","node2","node3","node4","node5","node6"],
      "ssh_host": "node2",
      "csi_driver": "rook-ceph.cephfs.csi.ceph.com"
    },
    "cluster_name": "cluster-a",
    "storage_class_name": "rook-cephfs"
  }' | jq '{storage_name, status, ssh_host: .mapping.backend_template.ssh_host}'
```

실제 실행 결과:
```json
{"storage_name": "cephfs-cluster-a", "status": "Degraded", "ssh_host": "node2"}
```

`ssh_host`를 생략하면 RM 작업 실행 시 agent 보고 기반으로 Ready 노드가 자동 선택된다.

제약:
- body의 `storage_name`은 path와 반드시 일치해야 함 → 불일치 시 HTTP 400
- 존재하지 않는 스토리지 → HTTP 404
- 진행 중인 request/data_job이 있으면 → HTTP 409

### 13.7 Agent DaemonSet ConfigMap 자동 동기화

POST/PATCH/DELETE API 호출 시 `dms-agent-storages` ConfigMap이 **자동으로 동기화**된다.
수동으로 ConfigMap을 편집할 필요가 없다.

- POST/PATCH → ConfigMap `storages` 배열에 해당 storage_name 항목 upsert
- DELETE → ConfigMap에서 해당 storage_name 항목 제거
- K8s 접근이 실패하면 코드가 예외를 **삼키고 warning 로그만** 남긴다(API 응답은 200으로 정상). 즉
  아래 RBAC이 없으면 patch가 `Forbidden`으로 **조용히 무시**되어 ConfigMap이 갱신되지 않는다 →
  새로 등록한 파일시스템 스토리지가 에이전트에 전달되지 않아 mount readiness가 Missing으로 남고,
  planner가 파일시스템 RM을 `missing_rm_readiness`로, DM을 `no_ready_dm_candidate`로 거부한다.
  그래서 이 RBAC은 **best-effort가 아니라 사실상 필수**다.

**RBAC (control-plane.yaml에 포함 — 별도 수동 적용 불필요):**

이 동기화에 필요한 Role/RoleBinding `dms-agent-storages-sync`(`configmaps`에 대해 get/update/patch,
resourceName `dms-agent-storages`)는 이제 `install/kubernetes/control-plane.yaml`에 포함되어 §7.3에서
함께 적용된다. RoleBinding은 `dms-api`와 `dms-remote` **둘 다**에 바인딩돼 있다 — dms-api가 control
클러스터에 in-cluster(pod SA=`dms-api`)로 접근하든, kubeconfig(`DMS_CLUSTER_KUBECONFIGS_JSON`)로 접근해
그 identity(`dms-remote`)로 동작하든 어느 경로에서도 patch가 통과하도록 하기 위함이다. 따로 apply할
필요는 없고, 만약 위 증상(신규 스토리지가 에이전트에 안 뜸)이 보이면 이 RBAC이 누락된 것이므로
`control-plane.yaml`을 재적용한다:

```bash
ssh node1 'kubectl -n dms get role,rolebinding dms-agent-storages-sync'   # 존재 확인
```

**동기화 확인:**

```bash
ssh node1 "kubectl -n dms get configmap dms-agent-storages -o jsonpath='{.data.storages\.json}'" | jq '.storages[].storage_name'
```

**ConfigMap 변경 후 Agent rollout (Agent가 시작 시 한 번만 파일을 읽으므로 재시작 필요):**

RM·DM **둘 다** 재시작한다 — 새 storage의 `resource_management` readiness는 RM agent,
`data_management` readiness는 DM agent가 채우므로, 하나만 재시작하면 나머지 축이 Missing으로 남는다.

```bash
ssh node1 "kubectl -n dms rollout restart daemonset/dms-rm-agent daemonset/dms-dm-agent && \
  kubectl -n dms rollout status daemonset/dms-rm-agent daemonset/dms-dm-agent --timeout=180s"
```

POST → ConfigMap에 항목이 추가되고, DELETE → ConfigMap에서 항목이 제거되며, PATCH → ConfigMap 내용이 갱신된다.
