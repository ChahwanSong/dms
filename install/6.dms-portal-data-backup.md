# 6. DMS Portal 데이터 백업(Data Backup) 운영

운영자 콘솔의 **데이터 백업** 탭은 DMS의 **DM `sync`** 를 이용해 스토리지 간 **미러 백업**을 수행한다.
운영자가 동기화할 요청(출발/대상 스토리지·경로)의 목록을 **배치(batch)** 로 등록하면(한 배치당 최대 수천 건),
포탈이 각 요청을 **미리보기(비파괴 dry-run) → 승인 → 실행** 흐름으로 자동 구동한다.

이 문서는 데이터 백업 기능의 **설치 의존성(포탈 DB), 동작 원리, 운영자 사용법, 경로 규칙, 보안, 트러블슈팅**을
다룬다. 포탈 자체의 빌드·배포·접근은 `5.dms-portal-setup.md`를 먼저 따른다.

> **DMS 소스 무변경 원칙.** 이 기능은 DMS `/api/v1/data-management/...`(scan/sync preview·confirm·cancel)와
> `operations/data-jobs` **읽기 전용 조회 API만** 사용한다. DMS 백엔드/스키마/엔드포인트는 일절 바꾸지 않으며,
> 모든 상태(배치·요청)는 **포탈 자신의 DB**에 저장한다. 데이터 자체는 포탈을 거치지 않고 DMS 워커(MPI dsync)가
> 노드에서 직접 옮긴다.

## 0. 개요 · 아키텍처

```
[브라우저 SPA]  --세션쿠키-->  [Portal BFF]
                                 │
                 ┌───────────────┼────────────────────────────┐
                 │               │                            │
        [Portal DB (portal       │  orchestrator(단일 async    │  DMS HTTP API
        스키마): batches/requests/│  루프): 미리보기/승인후      │  /api/v1/data-management
         operator_users]         │  실행을 자동 구동           │  (sync preview/confirm/cancel)
                                 ▼                            ▼
                          상태 영속화                    실제 dsync 실행(DMS 워커)
```

- **BFF orchestrator**(`src/portal/backend/orchestrator.py`) — 단일 백그라운드 asyncio 루프. 활성 배치를
  주기적으로(`PORTAL_BACKUP_POLL_SECONDS`) 훑으며, `previewing` 배치는 각 요청을 DMS에 sync(미리보기)로 제출하고
  `ConfirmPending`까지 폴링해 결과를 저장한다. `running` 배치는 미리보기가 끝난 요청을 fingerprint로 confirm하고
  종료 상태까지 폴링한다. **단일 루프 == 단일 writer**라 행 잠금이 필요 없고, 상태가 전부 DB에 있어 재기동에도
  진행 중 요청을 그대로 이어받는다(크래시 내성).
- **Portal DB**(`src/portal/backend/db.py`) — 포탈 전용 영속 저장소. 배치/요청과 **운영자 로그인 계정**을 담는다.
  DMS Postgres를 **전용 스키마(`portal`)** 로 재사용할 수 있다(§2).
- **DMS DM sync** — 미러 백업의 실제 일꾼. `4.dms-dm-api.md`의 preview/confirm 플로우를 그대로 따른다.

### 0.1 상태 머신

| 배치 상태 | 의미 |
| --- | --- |
| `draft` | 요청만 등록된 초안. 미리보기 시작 전. |
| `previewing` | orchestrator가 각 요청의 미리보기(비파괴 dry-run)를 진행 중. |
| `previewed` | 모든 요청의 미리보기가 끝남(준비 또는 실패). **운영자 승인 대기**. |
| `running` | 승인됨. orchestrator가 요청을 confirm·실행 중. |
| `done` | 모든 요청이 종료 상태. |
| `cancelled` | 운영자가 배치를 취소(진행 중 DMS 잡도 best-effort 취소). |

| 요청 상태 | 의미 |
| --- | --- |
| `registered` | 등록만 됨. |
| `preview_pending` | DMS에 미리보기 제출됨, 결과 대기. |
| `preview_ready` | 미리보기 완료(`ConfirmPending`). files/bytes/fingerprint 확보. |
| `preview_failed` | 미리보기 단계 실패(사유를 요청 행 비고에 표시). |
| `running` | confirm 후 실제 dsync 실행 중. |
| `succeeded` / `failed` | 실행 종료. |
| `cancelled` | 취소됨. |

### 0.2 requester=root + 소유권 보존

백업 요청은 **`root` requester**로 실행되며, **chown을 지정하지 않는다**. dsync가 root로 돌면서 chown 오버라이드가
없으므로 **대상 파일/디렉터리의 uid/gid가 원본 그대로 보존된다**(소유자 변경 없음). 이는 "백업본의 소유권을
원본과 동일하게 유지"하기 위한 의도된 동작이다.

> DMS는 **privileged(root) 데이터 잡을 mTLS-검증 운영자에게만** 허용한다(`allow_root_requester` +
> `privileged_requesters`). 그래서 BFF는 DM 호출 시 actor를 `PORTAL_BACKUP_ACTOR_PREFIX`(기본 `mtls:`)로
> 접두해 보낸다. **테스트베드(shared token profile)에서는 `mtls:` 접두 actor를 검증된 것으로 취급**하지만,
> 이는 운영 환경의 실제 mTLS client certificate을 대신하는 **테스트베드 근사**다(§5, `5.dms-portal-setup.md` §9).

## 1. 사전 조건

- `5.dms-portal-setup.md`의 기본 배포가 끝나 있고 DMS DM API에 도달 가능해야 한다.
- **포탈 DB가 설정되어 있어야 한다**(`PORTAL_DB_URL`). 미설정이면 데이터 백업 route가 전부 `503`이고,
  로그인은 env 저장소(`PORTAL_OPERATOR_USERS`)로 폴백한다(§2).
- 백업 대상 스토리지들이 **DM readiness = Ready**여야 한다(인벤토리 탭에서 RM·DM·INV 점 확인). DM 워커가 도는
  filesystem 매핑(cephfs/gpfs/wekafs)만 sync 가능하며, CSI(namespace-quota) 매핑은 대상이 아니다.
- `--delete`(미러) 옵션을 쓰려면 DMS에 **`DMS_DM_SYNC_ALLOW_DELETE=true`** 가 켜져 있어야 한다.
- DMS가 **root requester 데이터 잡을 허용**하도록 구성돼 있어야 한다. 두 축이 모두 만족돼야 한다.
  - **requester 축**: `DMS_DM_ALLOW_ROOT_REQUESTER=true` + `DMS_DM_PRIVILEGED_REQUESTERS`에 `root` 포함(기본값).
  - **caller(운영자) 축**: 호출 actor가 privileged 운영자로 인가돼야 한다(`DMS_DM_PRIVILEGED_OPERATORS`/scope 또는
    mTLS-검증 운영자). 테스트베드는 `mtls:` 접두 actor를 검증된 것으로 취급해 이 축을 만족한다(§0.2, §5).

  자세한 내용은 `4.dms-dm-api.md`의 privileged(root) 잡 절을 본다.

## 2. 포탈 DB 프로비저닝

데이터 백업과 (DB 사용 시) 운영자 로그인은 포탈 DB에 저장된다. 별도 Postgres를 두거나, **DMS Postgres를 전용
스키마로 재사용**할 수 있다. 테스트베드는 후자다(앱 롤 `dms_app`이 createdb 권한이 없어 별도 DB를 만들 수 없으므로
`dms` DB 안에 `portal` 스키마를 사용).

### 2.1 스키마 준비

DMS Postgres를 재사용하는 경우, 앱 롤 소유의 스키마를 한 번 만든다(슈퍼유저/소유자 권한으로 1회).

```sql
-- DMS Postgres에 접속(소유자/superuser)하여:
CREATE SCHEMA IF NOT EXISTS portal AUTHORIZATION dms_app;
```

포탈은 기동 시 `PORTAL_DB_SCHEMA`(기본 `portal`)에 필요한 테이블을 **자동 생성(bootstrap)** 한다. 생성 대상:

| 테이블 | 용도 |
| --- | --- |
| `operator_users` | 운영자 로그인(username, password_hash). 비면 `PORTAL_OPERATOR_USERS`에서 1회 시드. |
| `backup_batches` | 배치(상태, --delete, options, requester_id, created_by, note, 타임스탬프). |
| `backup_requests` | 요청(출발/대상 스토리지·경로, 상태, dms_request_id/job_id, fingerprint, preview, result, error). |

> 비밀번호는 stdlib PBKDF2(`pbkdf2_sha256$iters$salt$hash`)로 해시 저장한다. `operator_users`가 비어 있을 때만
> `PORTAL_OPERATOR_USERS`로 시드하며, 이후에는 **DB가 로그인의 source of truth**가 된다.

### 2.2 연결 문자열

`PORTAL_DB_URL`은 표준 Postgres URL이며, 스키마는 URL이 아니라 `PORTAL_DB_SCHEMA`로 지정한다(연결 시
`search_path`로 적용). 테스트베드에서는 DMS와 **같은 값**을 쓴다.

```bash
# 테스트베드: DMS Postgres 재사용 (= dms-secrets/DMS_DATABASE_URL 값)
PORTAL_DB_URL="postgresql://dms_app:<pw>@<pg-host>:5432/dms"
PORTAL_DB_SCHEMA="portal"
```

## 3. 환경변수

전체 변수는 `src/portal/backend/config.py`가 정의한다. 데이터 백업 관련:

| 변수 | 기본값 | 설명 |
| --- | --- | --- |
| `PORTAL_DB_URL` | (없음) | 포탈 DB Postgres URL. **미설정이면 백업 route가 503**, 로그인은 env로 폴백. Secret으로 주입. |
| `PORTAL_DB_SCHEMA` | `portal` | 포탈 테이블이 사는 스키마(연결 `search_path`). |
| `PORTAL_BACKUP_REQUESTER` | `root` | 백업 요청 requester. root여야 chown 없이 소유권 보존(§0.2). |
| `PORTAL_BACKUP_ACTOR_PREFIX` | `mtls:` | DM 호출 actor 접두. DMS privileged 게이트 통과용(§0.2, §5). |
| `PORTAL_BACKUP_CONCURRENCY` | `8` | 배치당 동시에 in-flight 시키는 DMS 잡 수 상한(미리보기/실행 각각). |
| `PORTAL_BACKUP_POLL_SECONDS` | `5` | orchestrator 폴링 주기(초). |

> `PORTAL_DB_URL`은 비밀번호를 포함하므로 **Secret으로** 주입한다(`5.dms-portal-setup.md` §3.3/§4.2와 동일 패턴).
> `portal.yaml`의 `Secret/portal-secrets`에 placeholder `PORTAL_DB_URL: "REPLACE_WITH_DB_URL"`이 있고, 실값은
> 라이브 Secret에 patch한다. **`kubectl apply`는 placeholder로 되돌리므로 apply마다 재패치 + 재기동**한다.

라이브 Secret 주입 예(테스트베드 — DMS DB URL 재사용):

```bash
DBURL="$(kubectl --context dms -n dms get secret dms-secrets -o jsonpath='{.data.DMS_DATABASE_URL}' | base64 -d)"
kubectl --context dms -n dms-portal patch secret portal-secrets --type merge \
  -p "{\"stringData\":{\"PORTAL_DB_URL\":\"${DBURL}\"}}"
kubectl --context dms -n dms-portal rollout restart deploy/dms-portal
```

기동 확인 — `/healthz`에 `db_configured: true`가 떠야 한다.

```bash
curl -fsS http://<node-ip>:30090/healthz; echo
# {"status":"ok","dms_configured":true,"db_configured":true}
```

## 4. 운영자 사용법

**운영자 콘솔 → 데이터 백업** 탭에서 수행한다.

### 4.1 배치 생성

`+ 새 배치`에서 이름, (선택) 메모, `--delete` 여부, **요청 목록(CSV/TSV)** 을 입력한다. 요청 목록은 한 줄에 한 요청:

```text
src_storage, src_path, dst_storage, dst_path
```

- 구분자는 **쉼표 또는 탭**. 빈 줄과 `#` 주석은 무시되고, 첫 줄이 컬럼명처럼 보이면 헤더로 건너뛴다.
- 한 배치에 **최대 수천 건**까지 등록 가능하다.
- 생성 시 `▸ sync 옵션`으로 배치 전체 sync 옵션(chmod/chown/contents 등)을 함께 지정할 수 있다(§4.6). 생성 후에도 `draft`인 동안 메타·옵션·요청을 편집할 수 있다.

예:

```text
cephfs-dms, project/alpha,  cephfs-secondary, backup/alpha
cephfs-dms, project/beta,   cephfs-secondary, backup/beta
```

### 4.2 ⚠️ 경로 규칙 (중요)

`src_path`/`dst_path`는 **해당 스토리지의 `managed_root` 기준 상대경로**다. 두 가지를 반드시 지킨다.

1. **`managed_root` 세그먼트를 경로에 넣지 않는다.** 예를 들어 매핑의 `managed_root`가 `/cephfs/dms`면, 실제
   디렉터리 `/cephfs/dms/project/alpha`는 경로 `project/alpha`로 적는다. `dms/project/alpha`처럼 적으면 DMS가
   `/cephfs/dms/dms/project/alpha`로 해석해 **존재하지 않는 경로**가 된다.
2. **대상(dst)의 부모 디렉터리가 미리 존재해야 한다.** DMS 미리보기(preflight)는 대상 부모에 대한
   `write`/`execute` 권한을 검사하므로, 부모가 없으면 미리보기가 **`posix_permission_denied`로 실패**한다.
   예: `backup/alpha`로 보내려면 `backup/`이 이미 있어야 한다(최종 leaf `alpha`는 dsync가 만든다).

> 즉 새 백업 루트로 처음 보낼 때는 대상 스토리지에 **상위 디렉터리(예: `backup/`)를 먼저 만들어 둔다**. 이는
> DMS/dsync의 preflight 동작이며 포탈이 그 실패 사유를 요청 행 비고에 그대로 표시한다.

### 4.3 미리보기 → 승인 → 실행

1. **미리보기 시작** — orchestrator가 각 요청을 비파괴 dry-run으로 돌린다. 요청별로 `미리보기 완료(files · 크기)`가
   채워지고, 상단 요약 칩에 **총 파일 수 · 총 바이트**가 집계된다. 실패한 요청은 `미리보기 실패` + 사유를 보인다.
2. **검토** — 영향 규모(파일/용량)와 실패 요청을 확인한다. `--delete` 배치라면 dst에서 삭제될 범위를 특히 주의한다.
3. **승인 (선택/전체)** — `preview_ready` 항목을 체크박스로 골라 **`선택 승인`**, 또는 **`전체 승인`**. 승인한 항목만
   `approved`가 되고 orchestrator가 fingerprint로 confirm→실제 dsync 실행, 종료까지 폴링한다. **미승인 항목은
   `미리보기 완료`로 남고 실행되지 않는다.**
4. **단계적 승인 / 마감** — 승인분이 끝나도 `미리보기 완료`가 남아 있으면 배치는 다시 `미리보기 완료`로 돌아가
   추가 승인할 수 있다. 남은 항목을 실행하지 않고 종료하려면 **`마감`**(미승인 항목 제외) → 배치 `done`. 더 승인할
   게 없으면 자동으로 `done`.

미리보기/실행 중에는 상세 화면이 4초마다 자동 갱신된다. 요청이 많으면 상태별 칩을 눌러 필터링하고, 각 행의
**`상세`**로 미리보기 내역(파일·디렉터리·바이트·에러·도구)을 펼쳐 본다.

### 4.4 `--delete`(미러) 의미

`--delete`를 켜면 dsync가 **dst에서 src에 없는 파일을 삭제**해 dst를 src의 정확한 미러로 만든다(파괴적).
켜면 생성/승인 시 경고가 뜨고, 승인 시 한 번 더 확인을 요구한다. 미리보기로 영향 범위를 먼저 확인한 뒤 승인한다.

### 4.5 취소 / 마감

- **배치 취소**(`배치 취소` 버튼): `previewing`/`previewed`/`running` 배치를 `cancelled`로 내리고 모든 비종료 요청을
  취소하며, 이미 DMS에 떠 있는 요청은 best-effort로 DM cancel(종료된 요청은 무시).
- **항목별 취소**(요청 행의 `취소`): 비종료 요청 **하나만** `cancelled`로(실행 중이면 해당 DMS job 취소). 배치는 유지되고
  나머지 요청은 그대로 진행된다.
- **마감**(`마감` 버튼): 승인하지 않은 `미리보기 완료` 항목을 실행 없이 제외하고 배치를 완료(§4.3).

### 4.6 초안(draft) 배치 편집 + sync 옵션

배치가 **`draft` 상태일 때만** 편집할 수 있다(미리보기 시작 이후에는 잠긴다). 상세 화면에서:

- **`✎ 편집`** — 이름·메모·`--delete`·**배치 전체 sync 옵션**을 수정한다. 같은 모달의 `▸ 요청 추가 (CSV)`로 요청을 더 붙일 수도 있다.
- **`+ 요청`** — 위 편집 모달을 CSV 추가 섹션이 열린 채로 띄운다.
- 각 요청 행의 **`수정`** — 출발/대상 스토리지·경로를 고친다(경로는 §4.2 규칙대로 재정규화·검증되며 `..`·널바이트는 거부).
- 각 요청 행의 **`삭제`** — 해당 요청을 배치에서 제거한다.

비-`draft` 배치에서 편집 API를 호출하면 `409`로 거부된다.

**sync 옵션**(`✎ 편집` 또는 생성 폼의 `▸ sync 옵션`)은 배치 전체에 적용된다. `delete`는 여기 두지 않고 `--delete` 체크박스로 관리한다.

| 옵션 | 의미 |
|---|---|
| `chmod` | 대상 권한 강제 (`0750` 또는 `D0750,F0640`). |
| `chown` | 대상 소유자 강제 (`user:group`). ⚠️ 백업 기본인 **원본 소유권 보존을 덮어쓴다**(root 요청자라 적용됨). |
| `contents` | 내용(체크섬) 기반 비교. |
| 고급 | `batch_files`·`bufsize`(정수), `direct`·`open_noatime`·`quiet`(불리언) — 성능/동작 튜닝. |

chmod/chown은 입력 시 가볍게 형식 검증하지만, **권위 있는 검증은 DMS 미리보기**다(잘못된 값은 해당 요청이 `미리보기 실패` + `422` 사유로 표시).

## 5. 보안 주의사항

- **root requester의 권한.** 백업 요청은 root로 실행되어 소스의 모든 파일을 읽고 대상에 쓴다(소유권 보존을 위해).
  배치 등록은 운영자 콘솔(operator 역할)로 게이트되며, 출발/대상 경로는 위 §4.2 규칙으로 정규화된다(`..`·널바이트
  거부, managed_root 상대).
- **`mtls:` actor 접두는 테스트베드 근사다.** shared token profile에서는 bearer 보유자가 `mtls:` actor를
  주장할 수 있다. **운영에서는 BFF가 실제 client certificate으로 mTLS를 제시**해 DMS의 privileged 게이트를
  통과해야 한다(`5.dms-portal-setup.md` §9의 (a)/(b) 경로). 운영 전환 시 이 접두를 실제 mTLS 신원으로 대체한다.
- **시크릿 취급.** `PORTAL_DB_URL`은 DB 비밀번호를 포함하므로 다른 포탈 시크릿과 동일하게 Secret으로만 주입하고
  git에 남기지 않는다(§3).

## 6. 검증 예시(worked example)

테스트베드(cephfs-dms, `managed_root=/cephfs/dms`)에서의 1회 검증 흐름.

```text
# 대상 부모(chownx/ , chmodchk/)가 이미 존재하는 위치로 sync (§4.2 규칙)
배치 요청 목록:
  cephfs-dms, chownx/src_alice,  cephfs-dms, chownx/portal_bk_alice
  cephfs-dms, chmodchk/src,      cephfs-dms, chmodchk/portal_bk_chmod
```

1. 배치 생성 → 요청 2건 `등록됨`.
2. 미리보기 시작 → 두 요청 `미리보기 완료`(예: `2 · 15 B`, `2 · 21 B`), 요약 `4 파일 · 36 B`. 배치 `미리보기 완료`.
3. 승인 후 실행 → 두 요청 `Confirmed → Running → 성공`. 배치 `완료`, 요약 `2 성공`.
4. 소유권 보존 확인 — 원본 `src_alice`가 uid/gid `10000:10001`이면 동기화된 `portal_bk_alice`도 동일하게
   `10000:10001`(root로 chown 없이 실행 → 보존).

부정 케이스(참고): 경로에 managed_root 세그먼트를 중복으로 넣거나(예: `dms/chownx/...`) 대상 부모가 없으면
미리보기가 `posix_permission_denied`로 실패하고, 그 사유가 요청 행 비고에 표시된다(§4.2).

## 7. 자주 발생하는 문제

### 데이터 백업 탭/route가 `503`
`PORTAL_DB_URL` 미설정이다. Secret/env를 확인하고(§3) 재기동한다. `/healthz`의 `db_configured`가 `true`인지 본다.

### 미리보기가 `preview_failed` + `posix_permission_denied`
대부분 §4.2 위반이다. (a) 경로에 `managed_root` 세그먼트를 중복 입력했거나, (b) **대상(dst)의 부모 디렉터리가
없다**. 대상 부모를 먼저 만들고, 경로는 managed_root 상대로 적는다.

### 미리보기/실행이 root 권한으로 `403`(DMS)
DMS의 privileged(root) 잡 게이트를 통과하지 못했다. requester 축(`DMS_DM_ALLOW_ROOT_REQUESTER`/
`DMS_DM_PRIVILEGED_REQUESTERS`)과 caller 축(`DMS_DM_PRIVILEGED_OPERATORS`/scope 또는 mTLS-검증 운영자)을 모두
확인한다(§1, `4.dms-dm-api.md`). 운영에서는 BFF가 실제 mTLS client cert으로 검증된 운영자 신원을 제시해야 한다(§5).

### `미리보기 완료`인데 승인 버튼이 비활성
`preview_ready` 요청이 하나도 없다(전부 `preview_failed`). 실패 사유를 고쳐 `다시 미리보기` 한다.

### 미리보기가 `PreviewExpired`로 실패
미리보기 후 너무 오래 confirm되지 않으면 DMS가 만료시킨다. `다시 미리보기`로 새 fingerprint를 받는다.

### rollout 후 화면이 끊김
port-forward는 pod에 고정되어 rollout 시 끊긴다. `5.dms-portal-setup.md` §5.2의 명령을 다시 실행한다.
