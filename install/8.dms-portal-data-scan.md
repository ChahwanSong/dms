# 8. DMS Portal 데이터 스캔(Data Scan) 운영

운영자 콘솔의 **데이터 스캔** 탭은 DMS의 **DM `scan`**(`dscan`)을 이용해 스토리지 경로의 **읽기 전용 통계**
(파일 수·디렉터리 수·총 용량·오류 수)를 수집한다. 운영자가 스캔할 경로 목록을 **배치(batch)** 로 등록하고
`스캔 실행`을 누르면, 포탈이 각 경로를 DMS에 scan 잡으로 제출하고 종료까지 폴링해 결과를 모아 보여준다.

데이터 백업(`6.dms-portal-data-backup.md`)과 **상위 구조가 동일**하지만, **scan은 읽기 전용이고 DMS에
preview/confirm 단계가 없다**(`POST /scan`이 곧장 실행). 그래서 라이프사이클이 백업보다 단순하다 —
**미리보기·승인 단계가 없고**, 배치가 `draft → scanning → done`으로 흐른다. 데이터를 일절 변경하지 않는다.

> **DMS 소스 무변경 원칙.** 이 기능은 DMS `/api/v1/data-management/scan`(+ `jobs/{id}:cancel`,
> `jobs/{id}` DELETE)와 `operations/data-jobs` **읽기 전용 API만** 사용한다. DMS 백엔드/스키마/엔드포인트는
> 바꾸지 않으며(scan API는 이미 존재), 모든 상태(배치·요청)는 **포탈 자신의 DB**에 저장한다. 실제 스캔은
> 포탈을 거치지 않고 DMS 워커(MPI dscan)가 노드에서 직접 수행한다.

## 0. 개요 · 아키텍처

```
[브라우저 SPA]  --세션쿠키-->  [Portal BFF]
                                 │
                 ┌───────────────┼────────────────────────────┐
                 │               │                            │
        [Portal DB (portal       │  scan orchestrator(단일     │  DMS HTTP API
        스키마): scan_batches/    │  async 루프): scanning      │  /api/v1/data-management/scan
         scan_requests]          │  배치를 자동 구동           │  (제출·폴링)
                                 ▼                            ▼
                          상태 영속화                    실제 dscan 실행(DMS 워커)
```

- **BFF scan orchestrator**(`src/portal/backend/scan_orchestrator.py`) — 단일 백그라운드 asyncio 루프.
  `scanning` 배치를 주기적으로(`PORTAL_BACKUP_POLL_SECONDS` 재사용) 훑으며, `registered` 요청을 DMS에 scan으로
  제출하고(→ `running`), `request_id`를 `job_id`로 재조정한 뒤, 종료 상태까지 폴링해 결과 요약을 저장한다.
  **단일 phase**(백업의 preview/execute 2-phase 대비)이며, 상태가 전부 DB에 있어 재기동에도 진행 중 요청을
  그대로 이어받는다(크래시 내성). 백업 오케스트레이터와 독립된 별도 루프다.
- **Portal DB**(`src/portal/backend/db.py`) — `scan_batches`/`scan_requests` 테이블을 기동 시 자동 생성한다
  (백업과 같은 `portal` 스키마, **신규 마이그레이션·신규 env 없음**).
- **DMS DM scan** — 실제 일꾼. `4.dms-dm-api.md`의 scan(읽기 전용, preview 불필요) 동작을 따른다.

### 0.1 상태 머신

| 배치 상태 | 의미 |
| --- | --- |
| `draft` | 경로만 등록된 초안. 스캔 시작 전. |
| `scanning` | orchestrator가 각 요청을 DMS scan으로 제출·폴링 중. |
| `done` | 모든 요청이 종료 상태. |
| `cancelled` | 운영자가 배치를 취소(진행 중 DMS 잡도 best-effort 취소). |

| 요청 상태 | 의미 |
| --- | --- |
| `registered` | 등록만 됨. |
| `running` | DMS에 scan 제출됨, 종료 대기. |
| `succeeded` | 스캔 완료. files/dirs/bytes/errors·scan_root·tool 확보. |
| `failed` | 스캔 실패(사유를 요청 행 비고에 표시). |
| `cancelled` | 취소됨. |
| `held` | 선택 실행 시 미선택분이 잠깐 빠지는 내부 상태(완료 후 `registered`로 복원). |

### 0.2 requester=root

스캔 요청은 백업과 동일하게 **`root` requester**로 실행된다(읽기 전용이라 소유권 변경과 무관). DMS는 privileged
잡을 mTLS-검증 운영자에게만 허용하므로(`allow_root_requester` + `privileged_requesters`), BFF는 DM 호출 시
actor를 `PORTAL_BACKUP_ACTOR_PREFIX`(기본 `mtls:`)로 접두해 보낸다. 테스트베드(shared token profile)는 `mtls:`
접두 actor를 검증된 것으로 취급하지만, 이는 운영 환경의 실제 mTLS client certificate을 대신하는 근사다
(`6.dms-portal-data-backup.md` §0.2, `5.dms-portal-setup.md` §9 참고).

## 1. 사전 조건

- `5.dms-portal-setup.md` 기본 배포 + `6.dms-portal-data-backup.md` §2의 **포탈 DB(`PORTAL_DB_URL`)** 가
  설정돼 있어야 한다. 미설정이면 스캔 route가 전부 `503`이다.
- 스캔 대상 스토리지가 **DM readiness = Ready**여야 한다(인벤토리 탭 RM·DM·INV 점 확인). DM 워커가 도는
  filesystem 매핑(cephfs/gpfs/wekafs)만 스캔 가능하며, CSI(namespace-quota) 매핑은 대상이 아니다.
- DMS가 **root requester 데이터 잡을 허용**해야 한다(`DMS_DM_ALLOW_ROOT_REQUESTER` + caller 인가 — 백업과 동일,
  `6.dms-portal-data-backup.md` §1). 스캔은 `--delete` 같은 파괴적 옵션이 없으므로 `DMS_DM_SYNC_ALLOW_DELETE`와는
  무관하다.

## 2. 환경변수

**스캔 전용 신규 변수는 없다.** 백업과 같은 포탈 DB + orchestrator 설정을 재사용한다.

| 변수 | 기본값 | 설명 |
| --- | --- | --- |
| `PORTAL_DB_URL` / `PORTAL_DB_SCHEMA` | (없음) / `portal` | 포탈 DB. 스캔 테이블도 여기에 자동 생성(§0). |
| `PORTAL_BACKUP_REQUESTER` | `root` | 데이터 잡 requester(스캔도 root로 제출). |
| `PORTAL_BACKUP_ACTOR_PREFIX` | `mtls:` | DM 호출 actor 접두(privileged 게이트 통과용). |
| `PORTAL_BACKUP_CONCURRENCY` | `8` | 배치당 동시에 in-flight 시키는 scan 잡 수 상한. |
| `PORTAL_BACKUP_POLL_SECONDS` | `5` | orchestrator 폴링 주기(초). |

> 스캔의 Volcano 큐/우선순위 기본값은 DMS의 per-tool 정책(`dscan`)에서 온다. 정책이 없으면(`null`) Volcano
> 기본 큐로 폴백한다. 폼의 `병렬 노드 수 = 자동`은 이 `dscan` 정책 기본값을 따른다.

## 3. 운영자 사용법

**운영자 콘솔 → 데이터 스캔** 탭에서 수행한다.

### 3.1 배치 생성

`+ 새 배치`에서 이름, (선택) 메모, **스케줄러 우선순위**(Low/Mid/High), **병렬 노드 수**(자동/1~16),
**스토리지**(fs 매핑만), 그리고 **스캔 경로 목록**을 입력한다. 경로는 한 줄에 하나(인라인 테이블 또는 CSV/텍스트
팝업):

```text
path
project/alpha
project/beta
```

- 구분자는 쉼표/탭(2열 `storage,path`도 허용). 빈 줄과 `#` 주석은 무시, 첫 줄이 컬럼명처럼 보이면 헤더로 건너뛴다.
- `▸ 스캔 옵션`으로 배치 전체 옵션을 지정한다(§3.4).
- 배치는 `scanning`이 아닌 동안(초안/완료/취소) 메타·옵션·경로를 자유롭게 편집할 수 있다.

### 3.2 ⚠️ 경로 규칙

`path`는 **해당 스토리지의 `managed_root` 기준 상대경로**다. `managed_root` 세그먼트를 경로에 넣지 않는다
(매핑 `managed_root`가 `/cephfs/dms`면 `/cephfs/dms/project/alpha`는 `project/alpha`로 적는다). `..`·널바이트는
거부된다. 백업과 달리 **대상 부모 디렉터리 요건은 없다**(읽기 전용 — 그 경로가 존재하고 읽을 수만 있으면 된다).
존재하지 않거나 읽을 수 없는 경로는 해당 요청이 `실패` + 사유(예: `source_not_found`)로 표시된다.

### 3.3 스캔 실행 → 결과

1. **스캔 실행**(`스캔 실행` 버튼) — 배치를 `scanning`으로 전환하고, orchestrator가 각 경로를 DMS scan으로
   제출한다. 항목을 체크해 **선택 실행**하면 미선택분은 `held`로 빠졌다가 완료 후 복원된다.
2. **진행/결과** — 상세 화면이 4초마다 자동 갱신된다. 각 요청이 `running → 성공/실패`로 바뀌고, 성공 시
   **결과(파일 · 크기)** 가 채워진다. 상단 **합계** 줄에 배치 전체의 파일·디렉터리·용량·오류 수가 집계된다.
3. **항목 상세** — 행을 펼치면 절대경로, **스캔 결과**(파일·디렉터리·크기·오류·도구·`scan_root`), 식별자
   (DMS job/request id)를 본다.

> 포탈은 DMS scan의 **요약 통계만** 표시한다(파일/디렉터리/바이트/오류 수). 개별 파일 목록 등 상세 리포트는
> 워커 노드의 artifact 파일(`dscan-report.json`)에 있으며 포탈/BFF로는 노출되지 않는다.

### 3.4 스캔 옵션

`▸ 스캔 옵션`(생성·편집 폼)에서 배치 전체에 적용한다. DMS scan이 받는 네 가지만 노출한다.

| 옵션 | 의미 |
|---|---|
| `summary_only` | 개별 파일 목록 없이 집계만 — 더 빠름(기본 켜짐). |
| `max_depth` | 탐색 최대 깊이(0 이상). 비우면 무제한. |
| `follow_symlinks` | 심볼릭 링크를 따라 탐색. |
| `one_file_system` | 마운트 경계를 넘지 않음(동일 파일시스템만). |

### 3.5 재스캔 / 재시도 / 취소

- **재스캔**(완료 배치 헤더 `재스캔`): 모든 종료 요청(성공/실패/취소)을 `등록됨`으로 리셋하고 전체를 다시 스캔한다
  — 시간에 따른 사용량 증가 모니터링에 유용하다.
- **실패 재시도** / 행별 `재시도`: 실패 항목만 `등록됨`으로 리셋 후 다시 `스캔 실행`.
- **편집**(행 `편집`): 경로를 고치면 그 항목이 `등록됨`으로 리셋된다.
- **취소**: 배치 `배치 취소`(비종료 요청 + 떠 있는 DMS 잡 best-effort 취소) / 행별 `취소`(하나만).
- **삭제**: 종료된 배치는 목록/상세에서 삭제할 수 있다(`scanning` 중에는 `409`).

## 4. 검증 예시(worked example)

테스트베드(cephfs-a, `managed_root=/cephfs/dms`)에서의 1회 검증 흐름.

```text
배치 경로 목록(storage=cephfs-a):
  e2e/src
  e2e
```

1. 배치 생성 → 요청 2건 `등록됨`.
2. `스캔 실행` → 배치 `scanning`, 두 요청 `running`.
3. orchestrator가 DMS에 제출·폴링 → 두 요청 `성공`(`dscan`), 결과 예: `e2e/src = 100 파일 · 3.6 KB`,
   `e2e = 200 파일 · 7.2 KB`. 배치 `완료`, **합계 `파일 300 · 디렉터리 80 · 10.8 KB · 오류 0`**.
4. 행 펼침 → 절대경로 `/cephfs/dms/e2e/src`, `scan_root`·도구·job/request id 확인.

## 5. 자주 발생하는 문제

### 데이터 스캔 탭/route가 `503`
`PORTAL_DB_URL` 미설정이다(`6.dms-portal-data-backup.md` §2~3). `/healthz`의 `db_configured`가 `true`인지 본다.

### 요청이 `실패` + `source_not_found` / `source_not_readable`
§3.2 경로 규칙 위반(없거나 못 읽는 경로). managed_root 상대경로로 다시 적고 `재시도`한다.

### 스캔 잡이 `insufficient_eligible_nodes`로 실패
적격 DM 노드 수가 정책 요구치보다 적다. 폼의 **병렬 노드 수**를 적격 노드 수 이하로 낮춰 다시 실행한다
(`6.dms-portal-data-backup.md`의 교차 스토리지 제약과 동일 원리).

### root 권한으로 `403`(DMS)
DMS privileged(root) 잡 게이트 미통과. requester/caller 축을 확인한다(§1, `4.dms-dm-api.md`). 운영에서는 BFF가
실제 mTLS client cert으로 검증된 운영자 신원을 제시해야 한다.
