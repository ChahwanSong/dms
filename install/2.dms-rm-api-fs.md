# DMS Resource Management API — Filesystem (GPFS / WekaFS / CephFS)

DMS의 **Filesystem** Resource Management API(GPFS/WekaFS/CephFS), Operations 조회 API, LDAP 설정, GPFS 환경 사전 설정을 다룬다.  
Kubernetes namespace quota Resource Management API는 [`3.dms-rm-api-k8s.md`](3.dms-rm-api-k8s.md)를 참조한다.  
설치 전체 과정은 `1.install-dms-on-pvs.md`를 참조한다.

모든 curl 예시는 아래를 먼저 실행한 상태를 전제로 한다.

source /mgmt_storage/cocoa.song/.dms-secrets/dms-env.sh

## 1. GPFS 환경 사전 설정

### 1.1 SSH PATH 주입

DMS RM worker가 ion 노드에 SSH로 접속해 GPFS 명령을 실행할 때 non-login shell이 열리므로 `/usr/lpp/mmfs/bin`이 PATH에 없다. 코드가 `PATH=/usr/lpp/mmfs/bin:$PATH` 를 자동으로 주입하므로 별도 심볼릭 링크는 불필요하다.

### 1.2 per-fileset quota 활성화

GPFS filesystem에 per-fileset quota가 비활성화되어 있으면 `BackendApplyFailed`가 발생한다. 최초 1회 활성화.

```bash
ssh ion2404 "sudo /usr/lpp/mmfs/bin/mmchfs pvs --perfileset-quota"
# 확인
ssh ion2404 "sudo /usr/lpp/mmfs/bin/mmlsfs pvs --perfileset-quota -Y | grep perfileset"
# → perfilesetQuotas:yes
```

### 1.3 managed_root 디렉토리 생성

GPFS fileset junction의 부모 디렉토리를 미리 생성한다. **권한은 `0711`**(world-traversable, not
world-listable)로 만든다 — 임의 uid의 리소스 소유자가 자기 디렉토리(각 `0750`/`0770`)로 `cd` 할 수 있도록
traverse(`o+x`)는 열되, `ls`로 **리소스 디렉토리 이름이 노출**되지 않도록 list(`o+r`)는 막는다. `0755`(기본
umask)는 이름을 노출하므로 피한다.

```bash
ssh ion2404 "sudo mkdir -p /pvs/dms && sudo chmod 0711 /pvs/dms"
```

> CephFS는 DMS가 managed_root를 **자동 생성할 때 `0711`로** 만든다(사전 생성돼 있으면 운영자가 정한 권한
> 유지). GPFS/WEKA는 managed_root를 운영자가 사전 생성하므로 위처럼 `0711`로 만든다.

### 1.4 GPFS storage mapping 등록

```bash
source /mgmt_storage/cocoa.song/.dms-secrets/dms-env.sh

curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/storage-mappings" \
  -d '{
    "storage_name": "gpfs-pvs-dms",
    "backend_template": {
      "backend_type": "gpfs",
      "cluster_name": "pvs-dms",
      "filesystem_name": "pvs",
      "mount_path": "/pvs",
      "managed_root": "/pvs/dms",
      "rm_worker_nodes": ["ion2404","ion2405","ion2406"],
      "command_runner": "ssh-host-exec",
      "ssh_host": "75.23.118.28"
    },
    "cluster_name": "pvs-dms"
  }' | jq '{storage_name, status}'
```

> **`managed_root`는 filesystem backend(cephfs/wekafs/gpfs) 등록 시 필수**다 — 생략하면 등록이 `422`로 거부된다
> (과거의 암묵 `{mount_path}/dms` 기본값은 제거됨). `managed_root`는 반드시 `mount_path` 아래여야 한다. RM의
> 디렉토리 연산과 DM의 `DMS_DM_PATH_BASE=managed_root` 모드가 모두 이 값을 경계/기준점으로 쓴다.

**필수 사전 조건:**

| 조건 | 내용 |
|---|---|
| SSH key | `ssh_host`(`75.23.118.28` = ion2404)의 `root` 계정에 rm-worker SSH key 등록 |
| known_hosts | `dms-ssh-client` Secret에 `75.23.118.28~30` IP **평문** 등록 (해시화 `-H` 옵션 사용 금지) |
| SSH config | `dms-ssh-client` Secret의 config에 `User root` 포함 |
| per-fileset quota | `mmchfs pvs --perfileset-quota` 활성화 |
| managed_root | `/pvs/dms` 디렉토리 사전 생성 |

### 1.5 GPFS quota 단위

GPFS는 block quota를 내부적으로 **8 MiB(8192 KiB) 단위로 올림**한다. DMS는 `render_gpfs_block_limit`에서 set 값을 8 MiB 경계로 사전 정렬한다.

예: `capacity_bytes=10000000000` → `9773056K` (≈9.32 GiB, 8 MiB 올림)

read-back 비교는 추가로 **100 MiB capacity tolerance**를 허용한다 (모든 백엔드 공통; 자세한 정책은 §3.6 참고).

## 2. 로컬 OpenLDAP 셋업

서비스용 LDAP(`75.23.118.14`)은 read-only replica이고 pod 내부에서 master 호스트명 DNS 조회가 실패한다. DMS 전용 로컬 OpenLDAP을 rts2411에서 운영한다.

### 2.1 OpenLDAP 컨테이너 실행 (rts2411)

데이터는 CephFS에 영구 저장되므로 rts2411 재부팅 후에도 유지된다.

```bash
sudo mkdir -p /mgmt_storage/cocoa.song/.dms-secrets/openldap/data
sudo mkdir -p /mgmt_storage/cocoa.song/.dms-secrets/openldap/config

sudo docker run -d \
  --name dms-openldap \
  --restart unless-stopped \
  -p 3389:389 \
  -e LDAP_ORGANISATION='supercom' \
  -e LDAP_DOMAIN='supercom.samsung' \
  -e LDAP_BASE_DN='dc=supercom,dc=samsung' \
  -e LDAP_ADMIN_PASSWORD='dms-ldap-admin' \
  -e LDAP_CONFIG_PASSWORD='dms-ldap-config' \
  -e LDAP_READONLY_USER=true \
  -e LDAP_READONLY_USER_USERNAME='dms-readonly' \
  -e LDAP_READONLY_USER_PASSWORD='dms-readonly-pass' \
  -v /mgmt_storage/cocoa.song/.dms-secrets/openldap/data:/var/lib/ldap \
  -v /mgmt_storage/cocoa.song/.dms-secrets/openldap/config:/etc/ldap/slapd.d \
  osixia/openldap:1.5.0
```

| 항목 | 값 |
|---|---|
| URI (pod 내부) | `ldap://75.23.118.45:3389` |
| admin bind DN | `cn=admin,dc=supercom,dc=samsung` |
| admin password | `dms-ldap-admin` |
| base DN | `dc=supercom,dc=samsung` |
| 데이터 저장 경로 | `/mgmt_storage/cocoa.song/.dms-secrets/openldap/` |

OU 구조 초기화 (최초 1회):

```bash
ldapadd -x -H ldap://localhost:3389 -D 'cn=admin,dc=supercom,dc=samsung' -w 'dms-ldap-admin' <<'EOF'
dn: ou=groups,dc=supercom,dc=samsung
objectClass: top
objectClass: organizationalUnit
ou: groups

dn: ou=people,dc=supercom,dc=samsung
objectClass: top
objectClass: organizationalUnit
ou: people
EOF
```

### 2.2 서비스 LDAP → 로컬 OpenLDAP sync

스크립트: `install/scripts/sync-ldap-to-local.py`

- 소스: `ldap://75.23.118.14` (서비스 LDAP read-only)
- 대상: `ldap://localhost:3389` (로컬 OpenLDAP)
- posixAccount 사용자 + posixGroup 그룹 단방향 복제. 비표준 objectClass(inetuser 등) 제거.

```bash

# 실제 실행 (~2분 30초, 11,180명 + 448개 그룹)

```

### 2.4 LDAP 운영 정책

서비스 LDAP은 read-only 접근만 허용. 로컬 OpenLDAP은 DMS 전용이며 다음 제약이 코드로 강제된다:

| 허용 | 금지 |
|---|---|
| `ou=groups` 내 `cn=dms-*` 그룹 생성/멤버 수정 | 사용자(`posixAccount`) 추가/삭제/수정 |
| `cn=dms-*` 그룹 삭제 (filesystem 삭제 시) | `dms-` prefix 아닌 그룹 삭제 |

**GID 범위**: 9000000~9999999 (기존 시스템 GID 최대값 901437과 충돌 없음).

### 2.5 ion 노드 SSSD 캐시 설정 (그룹 멤버십 교차노드 일관성) — 사전 필수

filesystem RM은 `dms-grp-*` 그룹/멤버십을 (로컬 OpenLDAP에) 만든 뒤, 디렉토리 소유권·접근
검증을 위해 ion 노드가 그 그룹/멤버를 즉시 resolve할 수 있어야 한다. ion 노드는 SSSD로 LDAP
사용자/그룹을 조회·캐싱하는데, **RM은 작업이 실제 실행된 executor 노드 1대에서만 `sss_cache -E`로
캐시를 무효화**한다(§3.2 생성 순서 4단계). 따라서 나머지 ion 노드는 새 멤버십을 자기 SSSD 캐시가
만료될 때까지(`entry_cache_timeout`, 기본 **90분**) 보지 못해, 작업이 다른 노드로 스케줄되면
그룹 권한이 한동안 안 보이는 **교차노드 불일치**가 생긴다.

→ **모든 ion(DMS backend) 노드의 SSSD에서 `entry_cache_timeout`을 60초로 낮춘다.** 그러면
`sss_cache -E`를 못 받은 노드도 길어야 60초 안에 LDAP을 재조회해 새 멤버십을 본다.
(트레이드오프: LDAP 조회 빈도가 다소 늘지만 노드/유저 규모에서 무시 가능. 테스트베드·운영 동일 적용.)

```bash
# dms-* 그룹을 서빙하는 SSSD 도메인 섹션([domain/...])에 entry_cache_timeout=60 추가 후
# sssd 재시작 + 캐시 DB 초기화 (전 ion 노드)
for node in ion2401 ion2402 ion2403 ion2404 ion2405 ion2406; do
  ssh $node 'sudo grep -q "^entry_cache_timeout" /etc/sssd/sssd.conf \
    || sudo sed -i "/^\[domain\//a entry_cache_timeout = 60" /etc/sssd/sssd.conf; \
    sudo systemctl stop sssd && sudo rm -f /var/lib/sss/db/* && sudo systemctl start sssd'
done

# 확인 (각 노드에서 60이어야 함)
for node in ion2401 ion2402 ion2403 ion2404 ion2405 ion2406; do
  echo -n "$node: "; ssh $node 'sudo grep entry_cache_timeout /etc/sssd/sssd.conf'
done
```

> 참고: 다중 SSSD 도메인이 있으면 dms-* 그룹을 조회하는 도메인 섹션에 넣어야 한다.
> 근본 해결(소스)은 RM이 access_group이 걸린 전 노드에 `sss_cache -E`를 fan-out하는 것이며,
> 위 설정은 소스 무수정으로 같은 증상을 막는 인프라 측 조치다.

## 3. Filesystem Resource Management API

### 3.1 API 엔드포인트 요약

| Method | Path | Behavior |
|---|---|---|
| `POST` | `/api/v1/resource-management/filesystems` | 신규 생성: fileset/디렉토리 + quota + LDAP `dms-grp-{dir}` 그룹을 한 번에 처리 (full-managed) |
| `PATCH` | `/api/v1/resource-management/filesystems/{storage}/{dir}` | 부분 변경: `quota` (GPFS 8 MiB 정렬), `owner_username` (LDAP uid lookup → `chown`), `resource_type` (DMS DB만), `expires_at` |
| `DELETE` | `/api/v1/resource-management/filesystems/{storage}/{dir}` | soft-delete: 디렉토리 잠금(`chown root:root` + `chmod 000`) + LDAP 그룹 삭제. 데이터/디렉토리 보존, 파괴적 명령(mmdelfileset/rm-rf) 안 함. 백엔드별 세부는 §3.5 |
| `POST` | `/api/v1/resource-management/filesystems/{storage}/{dir}:block` | 차단: `chmod 0000` (`previous_mode` 저장) |
| `POST` | `/api/v1/resource-management/filesystems/{storage}/{dir}:initialize` | 차단 해제: `previous_mode`(없으면 `desired_state.mode`)로 복원 |
| `POST` | `/api/v1/resource-management/filesystems/{storage}/{dir}:check` | consistency check: 백엔드 quota/존재 상태 read-back, drift는 `issues[]`로 보고 (side-effect 없음) |
| `POST` | `/api/v1/resource-management/filesystems/{storage}/{dir}:sync` | 백엔드 live state → DMS `desired_state.quota` 갱신 (drift fix용; side-effect 없음) |
| `POST` | `/api/v1/resource-management/filesystems/{storage}/{dir}:import` | 외부에서 미리 만든 fileset/디렉토리를 full-managed로 채택 (LDAP 그룹은 사전 존재 필요) |
| `POST` | `/api/v1/resource-management/filesystems/{storage}/{dir}:assign-quota` | 외부 디렉토리에 quota만 적용 (`management_mode: quota_only`; 그룹/소유권 건드리지 않음, delete 거부됨) |
| `POST` | `/api/v1/resource-management/filesystems:expiration-sweep` | 만료된 모든 resource를 일괄 차단 (`scope`/`expired_before`/`dry_run`) |
| `GET` | `/api/v1/operations/filesystems/{storage}/{dir}` | 단건 조회 |
| `GET` | `/api/v1/operations/filesystems/{storage}` | storage별 목록 조회 |
| `GET` | `/api/v1/operations/filesystems/expiring` | 만료 임박/만료 목록 (`status`, `storage_name`, `within_seconds`, `brief`) |
| `GET` | `/api/v1/operations/requests/{request_id}` | request 단건 조회 (transition history 포함) |
| `GET` | `/api/v1/operations/requests?requester_id=` | requester별 request 목록 (`limit`, `since`, `until`) |
| `POST` | `/api/v1/resource-management/requests/{id}:resolve` | stuck request 수동 해소 (`abandon`/`succeeded`) |

> 모든 mutating 엔드포인트(`POST`/`PATCH`/`DELETE`)는 `202 Persisted` 반환 후 비동기 처리. 최종 상태는 `GET /operations/requests/{id}`로 폴링한다.

### 3.2 Create (생성)

GPFS fileset 생성 + quota + LDAP access group이 한 번에 처리된다.

```bash
source /mgmt_storage/cocoa.song/.dms-secrets/dms-env.sh

curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/filesystems" \
  -d '{
    "requester_id": "cocoa.song",
    "payload": {
      "storage_name": "gpfs-pvs-dms",
      "directory_name": "pvs-test-project1",
      "users": ["cocoa.song", "seongje.jang"],
      "quota": {
        "capacity_bytes": 10000000000,
        "file_count": 1000000
      },
      "expires_at": "2027-01-01T00:00:00Z"
    }
  }' | jq '{request_id, status}'
```

**payload 필드:**

| 필드 | 필수 | 설명 |
|---|---|---|
| `storage_name` | 필수 | 등록된 storage mapping 이름 |
| `directory_name` | 필수 | fileset/디렉토리 이름 (영숫자, 하이픈) |
| `users` | 필수 | 최소 1명. 각 user는 **LDAP에 `uid`로 존재**해야 한다(RM은 `(uid={user})`로 LDAP을 직접 조회해 `dms-grp-{dir}`의 `memberUid`로 등록). **RM·DM 모두 identity-mapping 테이블을 사용하지 않는다** — RM은 `(uid={user})` LDAP 직접 조회로 충분하며 별도 매핑 등록이 불필요하다 |
| `expires_at` | **필수** | 만료일 (ISO8601). 생략 시 `Rejected` |
| `quota.capacity_bytes` | 선택 | 용량 제한 (bytes) |
| `quota.file_count` | 선택 | inode 수 제한. **CephFS/GPFS만 지원** — **WEKA는 `file_count`가 있으면 요청이 `BackendApplyFailed`로 실패한다**(조용히 무시하지 않음). WEKA에는 `capacity_bytes`만 보낼 것 |
| `access_group` | 선택 | 그룹명. 생략 시 `dms-grp-{directory_name}` 자동 생성 |
| `mode` | 선택 | 디렉토리 권한. 생략 시 `0750` (`0750`/`0770` 만 허용) |
| `owner_username` | 선택 | 디렉토리 소유자(POSIX/LDAP user). 생략 시 `requester_id` 사용. **owner는 백엔드 노드에서 해석 가능한 POSIX/LDAP 사용자여야 한다**(uid 범위 제한 없음) — 아니면 side effect 이전에 `BackendApplyFailed`(아래 전제조건). 명시적 override는 `root`/`nobody` 및 안전하지 않은 이름을 planner에서 거부 |
| `resource_type` | 선택 | `user` (기본) / `project` / `system` / `admin` — §3.10 참고 |

> **identity 해석 = LDAP 직접 조회 (identity-mapping 계층은 DMS에서 완전히 제거됨).** RM·DM 어느 쪽도
> `identity_mappings` 테이블/계층을 사용하지 않으며, 양쪽 모두 LDAP 직접 조회로 identity를 해석한다.
> 차이는 **해석 시점·위치**에 있다.
> - **RM(quota/access-group 적용) = NODE 측 해석.** `requester_id`/`owner_username`/`users`를 **LDAP
>   `uid`(POSIX 유저명) 그 자체로 간주**하고, side effect를 적용하는 백엔드 노드에서 해석한다 — owner는
>   `pwd.getpwnam`(CephFS, 워커 NSS/SSSD) 또는 `(uid={username})` LDAP 검색(GPFS/WEKA), `users`는
>   `(uid={user})` LDAP 검색. 따라서 owner/`users`는 반드시 LDAP에 존재하는 실제 사용자여야 한다(없으면
>   owner는 `BackendApplyFailed`, `users`는 그룹 생성 단계 실패).
> - **DM(scan/sync/rm) = CONTROL-PLANE preflight 해석.** dm-worker가 preflight에서 요청자의
>   `owner_username`을 **read-only LDAP 조회**해 uid/gid를 미리 확보하고, 이를 data-job 파드의
>   securityContext(`runAsUser`/`runAsGroup`)로 주입한다. LDAP이 다운이면 fail-closed로 `ldap_unavailable`,
>   사용자가 없으면 `ldap_identity_not_found`으로 거부한다. `owner_username`은 RM의 owner 모델과 동일하게
>   기본 `requester_id`(자유 형식 논리 id)이며 실제 POSIX 유저명으로 override할 수 있다.
> - **DM-side denylist (RM에는 없음).** DM은 requester/owner/group 단위 즉시 kill-switch 겸 admission
>   차단용 denylist를 추가로 가진다(기본 비어 있음). `PUT/DELETE/GET
>   /api/v1/data-management/identity-denylist/{subject_type}/{subject}`로 운영한다.

응답: `{"request_id": "req_...", "status": "Persisted"}` (비동기, 최종 상태는 request 조회로 확인)

**디렉토리 권한/소유권 설정 순서 (GPFS):**

*부작용 이전 (precondition — 실패 시 `BackendApplyFailed`, 어떤 GPFS 명령도 실행 안 함):*

- **P1. LDAP access group 확보** — `dms-grp-{dir}`(없으면 생성) + `users`를 `memberUid`로 등록
- **P2. owner 해석 (fail-closed)** — `owner_username`(없으면 `requester_id`)을
  LDAP에서 `uidNumber`로 조회. 해석되면 그 uid를 저장하고, **해석 불가면 여기서 거부**(`mmcrfileset`
  이전 — fileset 미생성). uid 범위 제한 없음. (LDAP resolver가 미구성이면 enforce 불가라 owner를
  비우고 group-only로 폴백 — 운영은 항상 resolver를 구성하므로 운영은 strict.)

*부작용 (`mmcrfileset`부터):*

1. `mmcrfileset` — fileset 생성 (inode space 신규)
2. `mmsetquota` — capacity/file_count quota 설정
3. `mmlinkfileset` — junction path에 마운트
4. `sss_cache -E` — SSSD 캐시 갱신 (**executor 노드에서만** 실행 — 타 노드 일관성은 §2.5의 `entry_cache_timeout=60` 설정에 의존)
5. `chown {owner_uid}:{gid} {junction_path}` — **P2에서 해석한 owner uid** + P1 access group gid를 함께 설정. (owner_uid가 없으면 `chown :{gid}` group-only로 폴백)
6. `chmod {mode} {junction_path}` — 권한 설정

> **주의:** P2(owner 해석)가 P1(그룹 생성) *이후*에 실행되므로, owner 미해결로 거부되면 GPFS
> fileset은 생성되지 않지만 LDAP `dms-grp-{dir}`는 남는다(고아 그룹). 정정 후 재시도 시
> 같은 그룹을 idempotent하게 재사용한다(무해). 필요 시 `ldapdelete`로 수동 정리.

**CephFS(host-mounted)도 동일하게 owner=requester를 설정한다.** RM
Worker가 워커 노드에서 실행하는 호스트 스크립트가 `mkdir` **이전에** `pwd.getpwnam(owner)`로
owner를 해석하고, 디렉토리를 `chown {owner_uid}:{group_gid}`로 설정한다(group은 DMS access
group). **전제조건 (부작용 이전, `PRECONDITION:` → `BackendApplyFailed`, 디렉토리 미생성):**
owner가 POSIX 사용자로 해석돼야 한다(**uid 범위 제한 없음**). owner가 허용 사용자
목록(`users`)에 포함될 필요는 없다 — owner는 owner 권한 비트로, 그 외 허용 사용자는 group
권한으로 접근한다(따라서 비-owner 허용 사용자가 써야 하면 `mode:"0770"`).

> **세 백엔드(CephFS/GPFS/WEKA) 모두 strict(fail-closed)** 다. owner가
> 지정됐는데 해석 불가면 부작용 이전에 `BackendApplyFailed`로 거부한다. GPFS/WEKA는 LDAP
> resolver가 **미구성**인 경우에 한해 owner를 set하지 못하고 group-only로 폴백한다(운영은 항상
> resolver를 구성하므로 운영은 strict). 참고: owner 전제조건은 access group 생성 이후에 실행되어,
> 미해결 owner 실패 시 고아 `dms-grp-<dir>`가 LDAP에 남을 수 있다(재시도 시 재사용).

**기본값:**

| 항목 | 값 |
|---|---|
| owner (user) | `requester_id`의 LDAP `uidNumber` (또는 `owner_username` 명시 시 그 값) |
| owner (group) | LDAP 그룹 GID (`dms-grp-{directory_name}`의 gidNumber) |
| mode | `0750` (`rwxr-x---`) |

**예시 (owner-test-2):**
```
GPFS fileset:  dms-owner-test-2  Linked  /pvs/dms/owner-test-2
quota:         1 GiB / 100K files
LDAP group:    cn=dms-grp-owner-test-2, gidNumber=9000005
LDAP user:     cocoa.song, uidNumber=903436
directory:     (0750/drwxr-x---)  Uid=903436(cocoa.song)  Gid=9000005
```

### 3.3 PATCH (quota / owner / resource_type / expires_at 변경)

PATCH는 quota, owner_username, resource_type, expires_at 중 하나 이상을 부분적으로 갱신할 수 있다. 한 요청에 동시에 여러 필드를 보내도 된다.

**(A) Quota 변경:**
```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X PATCH -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/filesystems/gpfs-pvs-dms/pvs-test-project1" \
  -d '{
    "requester_id": "cocoa.song",
    "payload": {
      "quota": {"capacity_bytes": 107374182400, "file_count": 2000000}
    }
  }' | jq '{request_id, status}'
```

**(B) 디렉토리 owner 변경 (`owner_username`):**

LDAP에서 user의 `uidNumber`를 조회해 `chown {uid}` 적용. **그룹은 변경하지 않는다.**

```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X PATCH -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/filesystems/gpfs-pvs-dms/owner-test-2" \
  -d '{
    "requester_id": "operator",
    "payload": {"owner_username": "seongje.jang"}
  }' | jq '{request_id, status}'
```

응답의 `verification_summary.owner_change`로 적용 결과 확인:
```json
{"owner_change": {"owner_username": "seongje.jang", "uid": 900930}}
```

**(C) resource_type 변경:**
```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X PATCH -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/filesystems/gpfs-pvs-dms/pvs-test-project1" \
  -d '{"requester_id":"operator","payload":{"resource_type":"project"}}' | jq
```

**(D) 그룹 멤버 변경**: PATCH로는 직접 지원하지 않는다. LDAP의 `dms-grp-{dir}` 그룹을 수정하거나 (`ldapmodify`) DMS create 시 `users` 필드로 등록한 멤버십을 그대로 사용한다. 그룹 멤버 drift는 §3.6 `:check`로 발견할 수 있다.

**허용 필드 요약:**

| 필드 | 효과 | 백엔드 명령 |
|---|---|---|
| `quota` | 용량/inode quota 변경 | `mmsetquota` (GPFS) / `weka fs quota set` (WEKA) |
| `owner_username` | 디렉토리 user 소유자 변경 | `chown {uid}` |
| `resource_type` | DMS DB의 태그 변경 (백엔드 변화 없음) | — |
| `expires_at` | 만료일 변경 (백엔드 변화 없음) | — |

### 3.4 차단 / 차단 해제

`:block`과 `:initialize` 엔드포인트는 `"block": true/false`를 내부적으로 자동 주입한다. payload에 별도로 포함할 필요 없다.

```bash
# 차단 (chmod 0000 — 모든 접근 불가)
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/filesystems/gpfs-pvs-dms/pvs-test-project1:block" \
  -d '{"requester_id": "cocoa.song", "payload": {}}' | jq '{request_id, status}'

# 차단 해제 (생성 시 mode로 복원 — 기본 0770)
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/filesystems/gpfs-pvs-dms/pvs-test-project1:initialize" \
  -d '{"requester_id": "cocoa.song", "payload": {}}' | jq '{request_id, status}'
```

**동작:**

| 엔드포인트 | GPFS 처리 | 결과 |
|---|---|---|
| `:block` | `chmod 0000 {junction_path}` | `d---------` (접근 불가) |
| `:initialize` | `chmod {previous_mode} {junction_path}` | 이전 mode 복원 (기본 `0770`) |

이전 mode는 `block_state.previous_mode`에 저장된다. 저장된 값이 없으면 resource 생성 시 지정한 `mode`(기본 `0770`)로 fallback 복원한다.

**예시:**
```bash
# 차단 후
stat /pvs/dms/pvs-test-project4 | grep Access
# → Access: (0000/d---------)  Uid: (0/root)  Gid: (9000003/dms-grp-pvs-test-project4)

# 차단 해제 후
stat /pvs/dms/pvs-test-project4 | grep Access
# → Access: (0770/drwxrwx---)  Uid: (0/root)  Gid: (9000003/dms-grp-pvs-test-project4)
```

### 3.5 삭제 (soft-delete)

데이터를 즉시 삭제하지 않고 안전하게 잠근다(보존 기본, 영구 삭제는 수동). 백엔드마다 세부 순서/단계가 다르다(코드 기준):

| Backend | soft-delete 동작(순서) | quota reset | 영구 삭제(운영자 수동) |
|---|---|---|---|
| **GPFS** | `chown root:root` → `chmod 000` → LDAP 그룹(`dms-grp-{dir}`) 삭제 | **안 함** | `mmunlinkfileset` + `mmdelfileset` |
| **WEKA** | `weka fs quota reset` → `chown root:root` → `chmod 000` → LDAP 그룹 삭제 | **함** | `rm -rf` |
| **CephFS** | `chown root:root` + `chmod 000` → LDAP 그룹 삭제 | **안 함** | `rm -rf` |

공통:
- 디렉토리/fileset과 데이터는 filesystem에 그대로 남고 **root만 접근 가능**(`d---------`). DMS DB resource 상태 → `Deleted` 마킹.
- `mmunlinkfileset`/`mmdelfileset`/`rm -rf` 같은 파괴적 명령은 **실행하지 않는다**. 영구 삭제는 위 표의 수동 절차로만 가능.
- `management_mode: quota_only` 또는 import로 등록된 리소스는 삭제 거부(외부 자산 보호; planner가 `Rejected`, 백엔드 어댑터도 precondition으로 재차 거부).
- (CephFS) 디렉토리 안에 사용자 파일이 있어도 보존되며 삭제가 거부되지 않는다(하드 삭제가 아니므로).

```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X DELETE -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/filesystems/gpfs-pvs-dms/pvs-test-project1" \
  -d '{"requester_id": "cocoa.song", "payload": {}}' | jq '{request_id, status}'
```

**soft-delete 후 action-required 조회:**

```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  "$DMS_API_URL/api/v1/operations/action-required" \
  | jq '[.[] | select(.issue_type == "filesystem_soft_deleted") | {resource_key, fileset_name, recommended_action}]'
```

응답 예시:
```json
[{
  "issue_type": "filesystem_soft_deleted",
  "severity": "INFO",
  "resource_key": "gpfs-pvs-dms:pvs-test-project1",
  "fileset_name": "dms-pvs-test-project1",
  "recommended_action": "GPFS fileset is locked (chown root:root + chmod 000, data preserved, fileset remains linked). To permanently remove: mmunlinkfileset {fs} {fileset} then mmdelfileset {fs} {fileset}."
}]
```

> `recommended_action`은 백엔드별로 다르다. CephFS/WEKA는 fileset이 아니라 디렉토리이므로
> "rm -rf the managed directory on a backend node"를 안내한다(`fileset_name`은 GPFS에서만 채워짐).

**수동 데이터 완전 삭제 (필요 시):**

```bash
# GPFS — fileset은 Linked 상태이므로 unlink 후 삭제
ssh ion2404 "sudo /usr/lpp/mmfs/bin/mmunlinkfileset pvs dms-{directory_name}"
ssh ion2404 "sudo /usr/lpp/mmfs/bin/mmdelfileset pvs dms-{directory_name}"

# CephFS / WEKA — managed_root 아래 잠긴 디렉토리를 백엔드 노드에서 직접 제거
ssh <backend-node> "sudo rm -rf {managed_root}/{directory_name}"
```

**예시 (GPFS):**
```
chown root:root: /pvs/dms/{dir} 소유권 root:root 변경
chmod 000:       d---------  (root 외 접근 불가, 디렉토리 filesystem에 유지)
LDAP group:      dms-grp-{dir} 삭제됨
fileset:         Linked 상태 유지 (데이터 보존)
action-required: filesystem_soft_deleted (INFO) 노출
```

### 3.6 Consistency Check (`:check`)

DMS가 기억하는 `desired_state`(quota / owner / mode / group 멤버십)와 **백엔드 + LDAP** 의 실제 상태를 대조한다. **side-effect 없음**. drift가 있으면 `issues[]`로 보고.

검사 대상:

| 항목 | 비교 방법 | drift 시 issue_type |
|---|---|---|
| quota.capacity_bytes | 백엔드 read-back vs `desired_state.quota.capacity_bytes` (100 MiB tolerance) | `filesystem_quota_drifted` |
| quota.file_count (GPFS) | 정확 비교 | `filesystem_quota_drifted` |
| 디렉토리 존재 | `mmlsfileset` / `test -d` | `filesystem_quota_missing` |
| ownership.uid | `stat -c %u` vs LDAP `owner_username` 의 uidNumber | `filesystem_owner_drifted` |
| ownership.gid | `stat -c %g` vs LDAP `access_group` 의 gidNumber | `filesystem_owner_drifted` |
| permission.mode | `stat -c %a` vs `desired_state.mode` | `filesystem_mode_drifted` |
| access_group.members | LDAP `dms-grp-{dir}` 의 `memberUid` ⊇ `desired_state.users` | `filesystem_group_membership_drifted` |

```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/filesystems/gpfs-pvs-dms/pvs-test-project1:check" \
  -d '{"requester_id": "operator", "payload": {}}' | jq '{request_id, status}'
```

옵션 (payload):

| 필드 | 기본값 | 설명 |
|---|---|---|
| `include_quota` | `true` | quota 비교 포함 |
| `include_permission` | `true` | 소유권/모드/그룹멤버십 비교 포함 |
| `record_action_required` | (false) | drift 발견 시 action-required로도 게시 |

**예시 (owner-test-2):**
```json
{
  "quota_status": "Consistent",
  "issues": [],
  "ownership_state": {
    "desired_uid": 900930, "observed_uid": 900930,
    "desired_gid": 9000005, "observed_gid": 9000005
  },
  "permission_state": {"desired_mode": "0750", "observed_mode": "0750"},
  "group_membership_state": {
    "group_name": "dms-grp-owner-test-2",
    "expected_members": ["cocoa.song"],
    "observed_members": ["cocoa.song"],
    "missing_members": []
  }
}
```

mode를 외부에서 `0700`으로 변경한 뒤 호출하면:
```json
{
  "quota_status": "Drifted",
  "issues": [{
    "issue_type": "filesystem_mode_drifted",
    "field": "permission.mode",
    "desired": "0750",
    "observed": "0700"
  }]
}
```

**Capacity tolerance 정책 (모든 백엔드 공통):**

| 비교 | 판정 |
|---|---|
| `observed < desired` | `Drifted` (quota under-applied — 위험) |
| `desired ≤ observed ≤ desired + 100 MiB` | `Consistent` |
| `observed > desired + 100 MiB` | `Drifted` |

- GPFS는 `desired`를 8 MiB 단위로 올린 값과 비교한다 (백엔드 내부 round-up 반영).
- WEKA는 desired 그대로 비교 (내부 round-up은 보통 4 KiB 안쪽).
- CephFS는 `setfattr`로 정확히 적용되지만 동일 정책을 따른다.
- `file_count`는 정수 카운터라 **정확 일치**를 요구 (tolerance 없음).

**tolerance 정책 적용 예시:**

| Backend | desired | live drift | quota_status |
|---|---|---|---|
| GPFS | 20 GiB / 2M files | 0 | `Consistent` |
| GPFS | 20 GiB | +56 MiB | `Consistent` |
| GPFS | 20 GiB | +200 MiB | `Drifted` |
| WEKA | 50 GB | +3 KiB (백엔드 내부 round) | `Consistent` |
| WEKA | 100 GB | +50 MiB | `Consistent` |
| WEKA | 100 GB | +200 MiB | `Drifted` |

응답 예시 (Consistent):
```json
{
  "verification_summary": {
    "quota_status": "Consistent",
    "issues": [],
    "quota_state": {
      "capacity": {
        "desired_bytes": 100000002048,
        "observed_bytes": 100052430848,
        "backend_key": "hard_limit_bytes"
      }
    }
  }
}
```

응답 예시 (Drifted):
```json
{
  "verification_summary": {
    "quota_status": "Drifted",
    "issues": [
      {
        "issue_type": "filesystem_quota_drifted",
        "field": "quota",
        "reason": "WekaFS quota capacity read-back mismatch"
      }
    ],
    "quota_state": {
      "capacity": {
        "desired_bytes": 100000002048,
        "observed_bytes": 100209717248,
        "backend_key": "hard_limit_bytes"
      }
    }
  }
}
```

### 3.7 Sync Live State (`:sync`)

백엔드의 실제 quota를 읽어 DMS `desired_state.quota`를 갱신한다. `:check`가 drift를 보고만 하는 데 반해 `:sync`는 DMS 쪽 기록을 백엔드 진실에 맞춘다. **백엔드 quota는 건드리지 않는다.**

```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/filesystems/gpfs-pvs-dms/pvs-test-project1:sync" \
  -d '{"requester_id": "operator", "payload": {}}' | jq '{request_id, status}'
```

옵션 (payload):

| 필드 | 기본값 | 설명 |
|---|---|---|
| `source` | `live` | 데이터 출처 (현재 `live`만 지원) |
| `include_quota` | `true` | quota를 sync 대상에 포함 |

**예시:**

GPFS — DMS 우회로 quota를 10 GB/1M → 20 GB/2M로 변경 후 `:sync` 호출:
```
synced_desired_state.quota: {"capacity_bytes": 21474836480, "file_count": 2000000}
```
→ `GET /operations/filesystems/gpfs-pvs-dms/pvs-test-project1`의 `quota` 필드가 즉시 새 값으로 갱신됨.

WEKA — `weka fs quota set` 직접 호출로 100 GB로 변경 후 `:sync`:
```
synced_desired_state.quota: {"capacity_bytes": 100000002048}
```
WEKA는 file_count quota 미지원 → `capacity_bytes`만 갱신.

### 3.8 Import 외부 fileset/디렉토리 (`:import`)

이미 외부에서 만든 fileset(GPFS) 또는 디렉토리(WEKA/CephFS)를 DMS 관리 영역으로 채택한다. `management_mode: full`로 등록.

**자동 그룹 채택 (GPFS/WEKA/CephFS 공통):**

`stat`으로 디렉토리의 현재 gid를 읽고 NSS/LDAP에서 그룹 이름을 알아낸 뒤:

| 현재 그룹 | 동작 |
|---|---|
| `dms-grp-*` (이미 DMS 명명규약) | 그대로 채택. LDAP에서 `memberUid` 가져와 `desired_state.users` / `access_group` 자동 등록. 디렉토리 chown 안 함. |
| 그 외 외부 그룹 | DMS가 `dms-grp-{directory_name}` 새로 생성, 외부 그룹의 LDAP `memberUid` 들을 그대로 멤버로 추가, 디렉토리를 새 gid로 chown. |

따라서 호출자는 `access_policy.expected_group` / `users` 를 명시할 필요 없다 (선택). quota만 보내면 충분. (CephFS도 GPFS/WEKA와 동일하게 stat 자동발견을 사용한다.)

**사전 조건:**

| Backend | 사전에 준비할 것 |
|---|---|
| GPFS | `mmcrfileset` + `mmlinkfileset -J {managed_root}/{dir}` 완료. group은 외부/dms-grp 둘 다 가능 |
| WEKA | `mkdir -p {managed_root}/{dir}` + 의도한 group으로 `chown :{gid}` 완료 |
| CephFS | `mkdir -p {managed_root}/{dir}` + 의도한 group으로 `chgrp`/`chown :{gid}` 완료 (WEKA와 동일) |

**Case A — 이미 `dms-grp-*` 그룹이 적용된 외부 fileset (GPFS):**
```bash
ssh ion2404 "sudo /usr/lpp/mmfs/bin/mmcrfileset pvs ext-bar --inode-space=new"
ssh ion2404 "sudo /usr/lpp/mmfs/bin/mmlinkfileset pvs ext-bar -J /pvs/dms/import-bar"
# LDAP에 dms-grp-import-bar 사전 존재, gid 9001000, memberUid: cocoa.song
ssh ion2404 "sudo chown :9001000 /pvs/dms/import-bar && sudo chmod 0750 /pvs/dms/import-bar"

curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/filesystems/gpfs-pvs-dms/import-bar:import" \
  -d '{
    "requester_id": "operator",
    "payload": {"expires_at": "2099-01-01T00:00:00Z", "quota": {"capacity_bytes": 1073741824}}
  }' | jq
```

응답 `verification_summary.group_adoption`:
```json
{
  "live_group": "dms-grp-import-bar",
  "live_gid": 9001000,
  "adopted_members": ["cocoa.song"],
  "changed_group": false,
  "mode": "adopt_existing_dms_group"
}
```

**Case B — 외부(`dms-grp-*` 아님) 그룹이 적용된 외부 fileset:**
```bash
# 외부에 ext-team-foo (gid=8500001, memberUid: cocoa.song, seongje.jang) 가 이미 있다고 가정
ssh ion2404 "sudo /usr/lpp/mmfs/bin/mmcrfileset pvs ext-foo --inode-space=new"
ssh ion2404 "sudo /usr/lpp/mmfs/bin/mmlinkfileset pvs ext-foo -J /pvs/dms/import-foo"
ssh ion2404 "sudo chown :8500001 /pvs/dms/import-foo && sudo chmod 0750 /pvs/dms/import-foo"

curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/filesystems/gpfs-pvs-dms/import-foo:import" \
  -d '{
    "requester_id": "operator",
    "payload": {"expires_at": "2099-01-01T00:00:00Z", "quota": {"capacity_bytes": 2147483648}}
  }' | jq
```

응답 `verification_summary.group_adoption`:
```json
{
  "live_group": "ext-team-foo",
  "live_gid": 8500001,
  "new_group": "dms-grp-import-foo",
  "new_gid": 9000006,
  "adopted_members": ["cocoa.song", "seongje.jang"],
  "changed_group": true,
  "mode": "create_dms_group_from_external"
}
```

**payload 필드:**

| 필드 | 필수 | 설명 |
|---|---|---|
| `expires_at` | 선택 (생략 시 1년 후 자동) | ISO8601 |
| `quota` | 선택 | 등록 시 quota도 같이 적용 |
| `import_mode` | `full` | (현재 `full`만 지원) |
| `access_policy.expected_group` | 선택 (검증용 hint) | 명시 시 backend가 발견한 live group과 일치하는지 확인 |
| `access_policy.expected_mode` | 선택 (`0750`) | 디렉토리 mode hint (`0750` / `0770`) |
| `access_policy.users` | 선택 | 명시 시 LDAP 멤버 검증 hint |

**예시:**

| 시나리오 | live_group | new/adopted | changed_group |
|---|---|---|---|
| import-bar (dms-grp-* 그대로) | `dms-grp-import-bar` | adopted gid 9001000 | `False` |
| import-foo (외부 그룹) | `ext-team-foo` | new `dms-grp-import-foo` gid 9000006 | `True` |

WEKA도 동일한 흐름 (mkdir + chgrp 후 `:import` 호출).

### 3.9 Assign Quota Only (`:assign-quota`)

외부 디렉토리에 **quota만 적용**한다. DMS는 그룹/소유권/mode를 건드리지 않으며, `management_mode: quota_only`로 표시되어 **이후 DELETE는 거부**된다 (외부 자산 보호).

```bash
# 사전 작업: 외부에서 fileset/디렉토리 만들고 link
ssh ion2404 "sudo /usr/lpp/mmfs/bin/mmcrfileset pvs ext-quota-only-1 --inode-space=new"
ssh ion2404 "sudo /usr/lpp/mmfs/bin/mmlinkfileset pvs ext-quota-only-1 -J /pvs/dms/import-quota-only"

curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/filesystems/gpfs-pvs-dms/import-quota-only:assign-quota" \
  -d '{
    "requester_id": "operator",
    "payload": {
      "expires_at": "2099-01-01T00:00:00Z",
      "quota": {"capacity_bytes": 4294967296, "file_count": 300000}
    }
  }' | jq '{request_id, status}'
```

**payload 필드:**

| 필드 | 필수 | 설명 |
|---|---|---|
| `expires_at` | 선택 (생략 시 1년) | ISO8601 |
| `quota` | 필수 | `capacity_bytes` 필요. **WEKA는 `file_count`를 주면 `BackendApplyFailed`로 실패**(무시 아님) — WEKA에는 `capacity_bytes`만 |
| `management_mode` | `quota_only` | (다른 값은 거부) |

**예시:**

| Backend | management_mode | quota observed | DELETE 시도 |
|---|---|---|---|
| GPFS (4 GB / 300K) | `quota_only` | `4194304K`, `300000` | `Rejected` (정상) |
| WEKA (1.5 GB) | `quota_only` | `1610612736` | `Rejected` (정상) |

> import vs assign-quota: **import**는 LDAP 그룹/사용자 멤버십까지 DMS가 관리(full); **assign-quota**는 quota만 등록(외부 그룹/소유권 손대지 않음). 후자는 DMS가 만들지 않은 외부 자산을 보호하기 위해 DELETE를 거부한다.

### 3.10 resource_type 카테고리 (resource tag)

리소스에 분류 태그를 부여한다. 만료 sweep / `:block` 호출 시 카테고리에 따라 보호 정책이 달라진다.

| 값 | 의미 | 만료 sweep 자동 차단 | `:block` 명시 호출 |
|---|---|---|---|
| `user` (기본) | 개인 작업 영역 | 대상 | 허용 |
| `project` | 프로젝트/팀 공유 영역 (분류용; user와 동일하게 동작) | 대상 | 허용 |
| `system` | 시스템 운영용 디렉토리 | 자동 차단 안 함 (`resource_type_not_auto_blocked`) | 거부 (`resource_type_cannot_be_blocked`) |
| `admin` | 관리자 전용 디렉토리 | 자동 차단 안 함 | 거부 |

**지정 방법 — create 시:**
```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/filesystems" \
  -d '{
    "requester_id": "cocoa.song",
    "payload": {
      "storage_name": "gpfs-pvs-dms",
      "directory_name": "shared-project-x",
      "users": ["cocoa.song", "seongje.jang"],
      "quota": {"capacity_bytes": 107374182400, "file_count": 1000000},
      "expires_at": "2027-01-01T00:00:00Z",
      "resource_type": "project"
    }
  }' | jq
```

**수정 방법 — PATCH:**
```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X PATCH -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/filesystems/gpfs-pvs-dms/shared-project-x" \
  -d '{"requester_id":"operator","payload":{"resource_type":"system"}}' | jq
```

**현재 값 조회:**
```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  "$DMS_API_URL/api/v1/operations/filesystems/gpfs-pvs-dms/shared-project-x" \
  | jq '{directory_name, status, resource_type}'
```

resource_type 변경은 백엔드 명령을 실행하지 않고 DMS DB의 `desired_state.resource_type`만 갱신한다 (디렉토리 권한/quota 변화 없음).

만료 sweep에서 특정 카테고리만 대상으로 하고 싶을 때는 sweep payload의 `scope.resource_type`으로 좁힐 수 있다:
```bash
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/filesystems:expiration-sweep" \
  -d '{"requester_id":"sweeper","payload":{"scope":{"resource_type":"user"},"dry_run":true}}' | jq
```

### 4.2 Request 조회

```bash
# 단건 조회 (전환 이력 포함)
curl -sS "${DMS_CURL_OPTS[@]}" \
  "$DMS_API_URL/api/v1/operations/requests/{request_id}" \
  | jq '{status: .request.status,
         results: [.results[] | {terminal_status, error_category, message}],
         transitions: [.transitions[] | {to_state, reason, actor}]}'

# requester별 목록 (requester_id 필수)
curl -sS "${DMS_CURL_OPTS[@]}" \
  "$DMS_API_URL/api/v1/operations/requests?requester_id=cocoa.song" \
  | jq '[.[] | {request_id, operation, resource_key, status, requested_at}]'

# 최신 N건
curl -sS "${DMS_CURL_OPTS[@]}" \
  "$DMS_API_URL/api/v1/operations/requests?requester_id=cocoa.song&limit=5" \
  | jq '[.[] | {request_id, status, resource_key}]'

# 날짜 범위 (since/until) — YYYY-MM-DD 또는 ISO8601 모두 허용
# 날짜만 주면 UTC 기준으로 since는 그날 00:00:00, until은 그 다음 날 00:00:00로 확장돼 양쪽 끝 날짜를 포함한다.
# 즉 since=2025-05-01 & until=2025-05-31 은 2025-05-01 00:00 ~ 2025-06-01 00:00 (5월 한 달).
curl -sS "${DMS_CURL_OPTS[@]}" \
  "$DMS_API_URL/api/v1/operations/requests?requester_id=cocoa.song&since=2025-05-01&until=2025-05-31" \
  | jq '[.[] | {request_id, status, requested_at}]'

# 시·분·초 단위 정밀 필터
curl -sS "${DMS_CURL_OPTS[@]}" \
  "$DMS_API_URL/api/v1/operations/requests?requester_id=cocoa.song&since=2025-05-15T00:00:00Z&until=2025-05-15T13:00:00Z" \
  | jq '[.[] | {request_id, requested_at}]'

# 특정 resource 이력
curl -sS "${DMS_CURL_OPTS[@]}" \
  "$DMS_API_URL/api/v1/operations/requests?requester_id=cocoa.song" \
  | jq '[.[] | select(.resource_key == "gpfs-pvs-dms:pvs-test-project1") | {request_id, status, requested_at}]'

# non-terminal request만 (진행 중 + stuck)
curl -sS "${DMS_CURL_OPTS[@]}" \
  "$DMS_API_URL/api/v1/operations/requests?requester_id=cocoa.song" \
  | jq '[.[] | select(.status | IN("Persisted","Planned","Applying","Verifying","UnknownAfterSideEffect","Conflict"))]'
```

**Request 상태값:**

| 상태 | 의미 | terminal |
|---|---|---|
| `Persisted` | 접수됨, planner 대기 | |
| `Planned` | planner가 실행 계획 수립 | |
| `Applying` | rm-worker가 백엔드 실행 중 | |
| `Verifying` | 실행 결과 검증 중 | |
| `Succeeded` | **정상 완료** | ✓ |
| `Failed` | 실패 처리됨 | ✓ |
| `BackendApplyFailed` | 백엔드 실행 실패 | ✓ |
| `Rejected` | validation 실패 (issues 필드에 원인) | ✓ |
| `UnknownAfterSideEffect` | side effect 발생 후 결과 불명 → resolve API 사용 | ✓ |
| `Conflict` | 동일 resource에 non-terminal request 존재 → 선행 request 해소 필요 | ✓ |

> `Rejected` 응답의 `issues[0].status`가 `"Succeeded"`이면 해당 resource가 이미 정상 존재한다는 의미다. create 대신 PATCH를 사용해야 한다.

## 5. Stuck Request 해소 (resolve API)

`UnknownAfterSideEffect` 또는 `BackendApplyFailed` 상태의 request가 있으면 동일 resource에 새 request 시 `Conflict`가 발생한다.

**엔드포인트:** `POST /api/v1/resource-management/requests/{request_id}:resolve`

| resolution | 전환 상태 | 사용 시점 |
|---|---|---|
| `abandon` | `Failed` | side effect가 없었거나 수동 롤백 완료한 경우 |
| `succeeded` | `Succeeded` | 백엔드에서 직접 확인해 실제 성공 상태인 경우 |

```bash
source /mgmt_storage/cocoa.song/.dms-secrets/dms-env.sh

# 1단계: stuck request 확인
curl -sS "${DMS_CURL_OPTS[@]}" \
  "$DMS_API_URL/api/v1/operations/requests?requester_id=cocoa.song" \
  | jq '[.[] | select(.status | IN("UnknownAfterSideEffect","BackendApplyFailed")) | {request_id, status, resource_key}]'

# 2단계: 백엔드 실제 상태 확인
# GPFS fileset: ssh ion2404 "sudo /usr/lpp/mmfs/bin/mmlsfileset pvs | grep dms-<name>"
# LDAP group:   ldapsearch -x -H ldap://localhost:3389 -D 'cn=admin,...' -w '...' -b 'ou=groups,...' '(cn=dms-grp-<name>)'

# 3단계-A: side effect 없음 → abandon
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/requests/{request_id}:resolve" \
  -d '{
    "resolution": "abandon",
    "reason": "verified no GPFS fileset or LDAP group was created"
  }' | jq

# 3단계-B: 실제로 생성됐음을 확인 → succeeded
curl -sS "${DMS_CURL_OPTS[@]}" \
  -X POST -H "content-type: application/json" \
  "$DMS_API_URL/api/v1/resource-management/requests/{request_id}:resolve" \
  -d '{
    "resolution": "succeeded",
    "reason": "GPFS fileset confirmed linked at /pvs/dms/<name>"
  }' | jq
```

응답:
```json
{
  "request_id": "req_...",
  "previous_status": "UnknownAfterSideEffect",
  "resolved_to": "Failed",
  "resolution": "abandon",
  "actor": "operator",
  "reason": "verified no GPFS fileset or LDAP group was created"
}
```

**에러:**
- `422` — resolution 값 오류 또는 reason 누락
- `404` — request_id 없음
- `409` — 이미 다른 terminal 상태 또는 resolve 불가 상태

## 6. 주의사항 / FAQ

운영·디버깅 시 먼저 확인할 항목(코드 기준):

- **`managed_root` 명시 필수 (cephfs/wekafs/gpfs).** 등록 시 없으면 `422`(암묵 `{mount_path}/dms` 기본값
  제거). 반드시 `mount_path` 아래여야 한다. RM 디렉토리 연산과 DM의 `DMS_DM_PATH_BASE=managed_root` 모드가
  모두 이 값을 경계/기준점으로 쓴다(§1.4).
- **WEKA quota CLI 인증.** `weka fs quota set/list/reset`는 cluster 인증이 필요하다(`weka user login` 또는
  `WEKA_USERNAME`/`WEKA_PASSWORD`/`WEKA_ORG`). 미인증 RM worker에서 quota 작업 시 `BackendPreconditionError`.
- **WEKA는 `file_count`(inode quota) 미지원.** 값을 주면 조용히 무시가 아니라 `BackendApplyFailed`로 거절한다 —
  WEKA에는 `capacity_bytes`만 보낸다(§3.2).
- **owner 해석은 fail-closed.** owner(`owner_username`, 생략 시 `requester_id`)가 LDAP/NSS로 해석되지 않으면
  부작용 이전에 `BackendApplyFailed`로 거부한다. 단 access group(P1)이 owner 해석(P2)보다 **먼저** 생성되므로,
  owner 실패 시 고아 `dms-grp-{dir}` 그룹이 LDAP에 남을 수 있다(정정 후 재시도 시 idempotent 재사용; §3.2).
- **삭제는 비파괴(soft-delete).** `chown root:root` + `chmod 000` + LDAP 그룹 삭제로 잠그고 데이터/디렉토리는
  보존한다. `mmdelfileset`/`rm -rf` 같은 영구 삭제는 운영자가 수동으로만 실행한다(§3.5).
- **import / `quota_only` 리소스는 DELETE 거부.** DMS가 만들지 않은 외부 자산을 보호한다(planner `Rejected` +
  백엔드 precondition 재차 거부; §3.8/§3.9).
- **모든 mutating은 비동기.** `POST`/`PATCH`/`DELETE`는 `202 Persisted`만 반환한다 → `GET
  /operations/requests/{id}`로 terminal 상태까지 폴링한다(§4.2). side effect 후 결과 불명
  (`UnknownAfterSideEffect`)이나 `BackendApplyFailed`로 멈춘 request는 `:resolve`로 정리한다(§5).
- **그룹 멤버십 교차노드 일관성.** RM은 작업이 실행된 executor 노드 1대에서만 `sss_cache -E`를 호출하므로,
  전 backend 노드의 SSSD `entry_cache_timeout`을 60초로 낮춰 둬야 새 멤버십이 제때 보인다(§2.5).
- **quota 비교 허용오차.** GPFS는 capacity를 8 MiB 단위로 올림한 뒤 비교하고, 모든 백엔드 capacity 비교는
  `+100 MiB` tolerance를 둔다(`observed < desired`는 항상 Drifted). `file_count`는 정확 일치를 요구한다(§1.5/§3.6).
