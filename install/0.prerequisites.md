# 0. 클러스터 사전 준비 (Prerequisites)

DMS를 설치하기 **전에** 클러스터에 갖춰야 하는 것들을 정리한다. 특히 **DM(데이터 잡:
scan/sync/rm)** 은 여기 항목들이 하나라도 빠지면 잡이 스케줄되지 않거나 후보 노드가 전부
거부되어 **조용히 미실행**된다(에러 없이 큐에 머물거나 preflight에서 rejected). RM(파일시스템·
쿼터)만 쓸 경우 §1, §5만 필요하다.

설치 순서: **이 문서(0) → 1.install(base) → 2/3(RM) → 4(DM) → 5(포탈)**.

---

## 0.0 한눈에 (체크리스트)

| # | 항목 | 대상 | 없으면 |
|---|---|---|---|
| 1 | Kubernetes ≥ 1.26, `kubectl` 접근 | 컨트롤/데이터 클러스터 | — |
| 2 | **PodSecurity**: DM 잡 네임스페이스가 `privileged` 허용 | DM 잡 클러스터 | DM 잡 파드 admission 거부 |
| 3 | **Volcano** 설치 (scheduler+controller+admission+CRD) | DM 잡 클러스터 | DM 잡 스케줄 불가 |
| 4 | **Queue `dms-data`** + **PriorityClass `dms-low/normal/high`** | DM 잡 클러스터 | 잡 영구 Pending / 파드 admission 거부 |
| 5 | **공유 RWX 파일시스템**(artifact) — dm-worker·DM 잡 노드에 **동일 경로** 마운트 | DM 잡 노드 | dm-worker가 summary.json 못 읽어 잡 실패 |
| 6 | DM 잡 노드에서 **요청자 POSIX 신원 해석**(NSS/SSSD) | DM 잡 노드 | `identity_not_ready_on_node` / chown 실패 |
| 7 | 관리 대상 **스토리지가 RM/DM 워커 노드에 host-mount** | 워커 노드 | mount readiness Missing / 잡 파드 기동 실패 |
| 8 | PostgreSQL 2개 DB (operational + observability) | 외부 | API/워커 기동 불가 |
| 9 | (RM k8s 쿼터) 타깃 클러스터 kubeconfig + RBAC | 타깃 클러스터 | 쿼터 RM 불가 |

> **MPI Operator는 필요 없다.** DMS는 `DMS_DM_SCHEDULER_BACKEND=volcano-job`으로 **Volcano
> 네이티브 Job**만 사용한다(Volcano가 MPI 워커를 gang-schedule). Kubeflow MPI Operator를
> 설치하지 말 것 — `auto` 백엔드는 MPIJob을 먼저 시도해 매 잡마다 실패 후 폴백하므로 쓰지 않는다.

## 0.1 Kubernetes / kubectl

- 컨트롤플레인(`dms-api`·`dms-planner`·워커·`dms-dm-worker`)이 도는 클러스터에 `kubectl`
  cluster-admin 접근.
- DM 잡은 **`dms-dm-worker`가 도는 클러스터**에서 실행된다(워커가 `--kubeconfig` 없이 in-cluster
  로 잡을 만든다, `DMS_DM_KUBERNETES_MODE=cluster`). 따라서 아래 §0.2~0.4(Volcano/큐/PSA)는
  **`dms-dm-worker`와 같은 클러스터**에 적용한다. 이 클러스터의 노드가 관리 대상 스토리지를
  host-mount 해야 한다(§0.5).

## 0.2 PodSecurity (DM 잡 네임스페이스 = privileged)

DM 잡 파드(Volcano MPI 워커)는 **root로 기동 → `SYS_CHROOT` capability 추가 → `runuser`로
요청자 uid/gid 강하** 하여 데이터를 다룬다. 클러스터 기본 Pod Security Admission이
`baseline`/`restricted`면 이 파드를 **거부**한다.

`install/kubernetes/control-plane.yaml`의 `dms` 네임스페이스에 이미 라벨이 있다:

```yaml
metadata:
  name: dms
  labels:
    pod-security.kubernetes.io/enforce: privileged
```

DM 잡을 **다른 네임스페이스**(`DMS_DM_NAMESPACE`)에서 돌린다면 그 네임스페이스에 동일 라벨을
붙인다:

```bash
kubectl label namespace <dm-namespace> pod-security.kubernetes.io/enforce=privileged --overwrite
```

## 0.3 Volcano 설치

Volcano는 (1) DM 잡의 gang-scheduler이자 (2) DMS가 쓰는 네이티브 잡 타입(`batch.volcano.sh`
Job)·`Queue`·`PodGroup` CRD를 제공한다. **하드 필수**.

```bash
# 버전은 조직 표준에 맞춰 핀한다(테스트베드 검증 버전 = v1.15.0). ⚠️ 확인 필요.
VOLCANO_VERSION=v1.15.0
kubectl apply -f https://raw.githubusercontent.com/volcano-sh/volcano/${VOLCANO_VERSION}/installer/volcano-development.yaml
```

검증:

```bash
kubectl -n volcano-system get deploy          # volcano-admission / -controllers / -scheduler 가 Ready
kubectl api-resources | grep -E 'volcano'     # jobs.batch.volcano.sh, queues.scheduling.volcano.sh, podgroups...
```

## 0.4 Queue + PriorityClass

DMS가 만드는 모든 DM 잡은 이름으로 참조한다: `spec.queue = DMS_DM_POLICY_DEFAULT_QUEUE`(기본
`dms-data`), `spec.priorityClassName = DMS_DM_POLICY_DEFAULT_PRIORITY_CLASS`(기본 `dms-normal`).
**큐가 없으면 잡이 영구 Pending**, **PriorityClass가 없으면 kube-apiserver가 파드를 admission에서
거부**한다. 별도 매니페스트로 제공한다:

```bash
kubectl apply -f install/kubernetes/volcano-queue-priorityclasses.yaml
kubectl get queue.scheduling.volcano.sh dms-data          # STATE=Open
kubectl get priorityclass | grep dms                      # dms-low(50)/dms-normal(100)/dms-high(200)
```

이름을 바꾸려면 매니페스트와 `control-plane.yaml`의 `DMS_DM_POLICY_DEFAULT_*` 값을 함께 맞춘다
(그리고 DMS API로 per-tool policy를 등록했다면 그쪽도).

## 0.5 공유 RWX 파일시스템 (artifact)

DM 잡 파드는 결과(`summary.json`)와 로그를 `DMS_DM_ARTIFACT_BASE_URI`(기본
`file:///artifacts/dms`) 아래에 쓰고, **`dms-dm-worker`가 그 파일을 로컬로 읽어** 잡을 분류한다.
따라서 artifact 경로는 **하나의 공유 RWX 파일시스템**이 **`dms-dm-worker` 노드와 모든 DM 잡
노드에 동일한 경로**로 마운트돼 있어야 한다(노드별 로컬 hostPath면 워커와 잡이 다른 노드에 뜰 때
깨진다).

- `control-plane.yaml`의 `dms-dm-worker` Deployment는 `dm-artifacts` hostPath(`path: /artifacts`,
  `type: Directory`, `HostToContainer` 전파)로 이 공유 FS **마운트포인트**를 붙인다 — 서브디렉터리가
  아니라 마운트포인트 자체여야 host 재마운트가 전파된다. 설치 시 실제 마운트포인트로 치환한다
  (예: CephFS `/cephfs`).
- 잡 파드도 같은 경로를 hostPath로 붙인다(워커가 자동 생성하는 매니페스트가 처리).

## 0.6 노드 신원 해석 (NSS/SSSD)

DM 잡은 요청자의 POSIX 신원(uid/gid)으로 실행된다. 그래서 **DM 잡 노드**에서:

- `dms-dm-agent`가 `DMS_AGENT_IDENTITY_USERS`에 나열된 사용자를 `getpwnam`으로 확인할 수 있어야
  한다(안 되면 `identity_not_ready_on_node`).
- 잡 이미지 안에서 `runuser`/chown이 그 사용자를 해석할 수 있어야 한다.

→ DM 노드 OS에 **NSS/SSSD(또는 동등한 디렉터리 연동)** 를 구성해 요청자 계정이 해석되게 한다.
(LDAP는 preflight에서 dm-worker가 read-only로 조회하지만, 노드/이미지 레벨 해석은 별도다.)

## 0.7 스토리지 host-mount

관리 대상 파일시스템 스토리지(cephfs/gpfs/wekafs)는 **RM/DM 워커 노드에 host-mount** 돼 있어야
한다(스토리지 매핑의 `mount_path`). 에이전트가 host mountinfo로 mount readiness를 판정하고, DM
잡 파드는 이 경로를 hostPath(`type: Directory`)로 붙인다 — 마운트가 없으면 파드가 기동 실패한다.

## 0.8 PostgreSQL

operational DB(`dms`)와 observability DB(`dms_observability`) 2개가 필요하다. 스키마는
`install/postgresql/init.sql`. 자세한 건 `1.install-dms-on-pvs.md`.

## 0.9 (선택) k8s 쿼터 RM 타깃 클러스터

Kubernetes namespace-quota RM을 쓰면 타깃 클러스터에 `dms-remote` SA + RBAC
(`install/kubernetes/target-cluster-rbac.yaml`)와 그 kubeconfig가 필요하다. `3.dms-rm-api-k8s.md`.

## 0.10 사전 준비 검증 (설치 전 빠른 확인)

```bash
# Volcano
kubectl -n volcano-system get deploy
kubectl get queue.scheduling.volcano.sh dms-data
kubectl get priorityclass | grep dms

# PSA
kubectl get ns dms -o jsonpath='{.metadata.labels.pod-security\.kubernetes\.io/enforce}{"\n"}'   # = privileged

# 공유 FS (dm-worker 예정 노드에서)
mount | grep <artifact-mountpoint>     # 예: /cephfs

# 노드 신원 (DM 노드에서)
getent passwd <requester-user>         # 해석돼야 함
```

이 항목들이 준비되면 `1.install-dms-on-pvs.md`로 진행한다.
